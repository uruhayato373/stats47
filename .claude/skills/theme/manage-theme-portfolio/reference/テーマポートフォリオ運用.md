# テーマポートフォリオ運用 (theme-portfolio-manager 設計)

現行ThemeCatalogの全テーマを対象に、**ThemeCatalog を SSOT としてテーマの維持・統合・分割・
改名・廃止候補を継続評価し、GSC・GA4・公式統計・データ品質を根拠に改善サイクルを回す**ための
運用設計書。オーケストレータ agent `theme-portfolio-manager` と state
`data/themes/{portfolio,experiments,quality}.json` を運用する。2026-07-13時点の監査・実装履歴は下記に保持し、現在の実行契約は末尾の「継続改善の実行契約」と、台帳 `themes.portfolio` / `themes.experiments` の Schema を参照する。

> **正典の役割分担**: 再編 (keep/split/merge/parent-hub) の**判定基準と URL/SEO 移行原則**は
> `.claude/skills/theme/manage-theme-portfolio/reference/theme-taxonomy-reorganization.md`、
> 指標×チャート**改善の実行方法** (採択ゲート・プロポーザル書式) は
> `.claude/skills/theme/manage-theme-portfolio/reference/theme-improvement-execution.md`、カタログの**編集規約**は
> `.claude/rules/theme-catalog-standards.md` が持つ。本書はそれらを**回すための計測・判定・記録
> レイヤ** (ポートフォリオ管理) だけを新設し、既存正典を重複定義しない。

## 1. PR-0 監査結果 (2026-07-13)

### 1.1 既存機能との重複マップ

| 提案責務 | 既存の担い手 | 重複度 | 判定 |
|---|---|---|---|
| テーマ別 KPI 評価 (GSC/GA4) | gsc-analyst / ga4-analyst (計測のみ・テーマ別集計なし) | partial | 集計は新設スクリプト、取得は既存 snapshot を read |
| keep/merge/retire ライフサイクル判定 | **なし** (taxonomy referenceに基準はあるが運用者・計測根拠なし) | none | 新設の中核 |
| テーマインベントリ管理 | theme-designer (IndicatorSet) / theme-component-builder (page_components) が分散 | none | portfolio.json で一元可視化 (SSOT は ThemeCatalog のまま) |
| 実験 baseline・効果測定管理 | improvement-triage (effect ラベルのみ) / blog-seo-strategist (ブログ限定) | none | experiments.json 新設 |
| researcher/designer への統括委譲 | 個別起動のみ (統括者なし) | none | 新設の中核 |
| triage への改善候補引き渡し | (逆向きの read はあり) | none | 引き渡し形式を定義 |
| レビュー文書とカタログの差分監査 | なし | none | 新設 |

**結論: 新規 agent は正当。** テーマの「戦略オーケストレーション層」は空白で、既存 4 テーマ agent
(researcher/designer/component-builder/ui-manager) はいずれも単一テーマの実行層。前例パターンは
`blog-seo-strategist` (ブログの戦略ハブ + 自前 state SSOT + 実行は既存オーナーに委譲) であり、
同じ構造をテーマに適用する。**既存 agent の責務拡張で足りない理由**: theme-designer に載せると
「設計者が自分の設計を評価する」自己採点構造になる (blog の author/critic 分離と同じ理由で不可)。

## 2. アーキテクチャ (SSOT 分離)

```
ThemeCatalog (git TS)                       ← テーマ定義の唯一の SSOT (変動値を入れない)
  ↑ 編集: theme-designer (採択) / 生成: generate:catalog
data/themes/portfolio.json          ← テーマ別評価の決定的 JSON (派生・再構築可能)
data/themes/experiments.json        ← 実験台帳 (baseline / 判定期日 / verdict)
  ↑ 書き込み: theme-portfolio-manager (build スクリプト経由) のみ
.claude/state/metrics/ + analytics snapshots ← 実測の read 元 (書かない)
.claude/todo/improvements.md               ← 書き込みは improvement-triage のみ (不変)
.claude/skills/theme/manage-theme-portfolio/reference/ ← 監査・効果判定のagent用履歴
```

- 計測値 (GSC/GA4) は **snapshot への参照 (`gscSnapshotRef` 等) + 集計値のコピー**を portfolio.json
  に持ち、ThemeCatalog には一切書かない。
- portfolio.json は**既存 snapshot + ThemeCatalog + レビュー文書から常に再構築できる派生物**
  (blog remediation-queue と同じ思想)。手編集しない。

### 責務境界 (統括であって実装ではない)

| 工程 | 担当 (既存) | theme-portfolio-manager の関与 |
|---|---|---|
| 公式資料・競合・検索需要の調査 | theme-researcher | 調査依頼を発行 (対象テーマ・調査観点を指定) |
| カタログ設計・採択 | theme-designer | 採択済み提案の設計依頼を発行 |
| チャート props / UI | theme-component-builder / theme-ui-manager | (直接関与しない) |
| GSC / GA4 の取得 | gsc-analyst / ga4-analyst (既存 cron) | snapshot を read するのみ |
| 改善バックログへの登録・effect 判定 | **improvement-triage (排他 writer)** | 改善候補を所定形式で引き渡すのみ |
| テーマ URL 再編の実装 | (`theme-taxonomy-reorganization.md`に従う) | 影響評価 (URL/canonical/redirect/関連記事/OGP/sitemap) を添えた提案まで |
| R2 push / deploy | CI / r2-publisher | **行わない** |

### ライフサイクル判定の規律

- `lifecycleStatus`: keep / improve / merge-candidate / split-candidate / rename-candidate /
  retire-candidate / insufficient-data
- **判定基準は `theme-taxonomy-reorganization.md` §再編の判定基準を正典**とし、本 agent はそれに**計測根拠を付ける**。
- 根拠なし判定の禁止: merge/retire 候補は「56 日以上の観測 + 最低標本数 + evidenceRefs ≥ 2」が
  ない限り付与できない (validator が enforce)。
- 観測期間: 7 日 = 異常検知のみ / 28 日 = 暫定 / **56 日 = 基本判定**。impressions・sessions が
  最低標本数 (初期値: GSC impressions 200/期間・GA4 views 100/期間) 未満は `insufficient-data`。
- **データ不足 (計測が無い/標本不足) と需要不足 (計測があり低い) を区別する** — 前者は
  insufficient-data、後者のみ retire-candidate の根拠になる。
- 季節性・順位変動・サイト全体変動は experiments.json の `notes` に注記必須。

## 継続改善の実行契約（2026-09-08）

現行ThemeCatalogを母集団とし、各テーマの問い別章を運用単位とする。
週次の既存 `quality-suite-weekly.yml` の theme job は公開R2のrecipe/取得と、章・単年/共通年・
有限値coverage・重複・履歴退行を監査する。状態はquality.jsonへ再生成し、
エラーの固定Issueは内容が変わる時だけ更新、復旧時に閉じる。

Codexのこのタスクに付けた週次フォローは、機械結果の差分を確認し、定義/表示の不具合を
担当ownerへ割り当てて修正・ローカル検証まで進める。毎月最初の確認では全テーマの公式新年も確認する。
変化のない週に報告を増やさず、新規課題・修正完了・復旧・判断依頼だけ知らせる。
本番反映日は公開完了後に実験へscheduleし、d7品質、d28暫定、d56継続・改善判断の順に確認する。
新規URLは `changeType=launch` で初回公開観測を登録し、公開前baselineを捏造しない。
登録・日付固定・28日窓・launch review・次の改善baselineへの引継ぎは
下の「新規URLの初回公開観測 (launch)」を正典とする。
初回観測だけでeffectを確定せず、次の変更は独立した改善実験としてbefore/afterを保存する。

効果判断用GA4はJapan-only成功メタ付きpages-clean、内部導線はtheme-navigation。
rawを混ぜず実日付が連続した28日窓2本を用いる。未測定や低標本を需要消失と扱わない。

## 新規URLの初回公開観測 (launch)

新規URLは公開前トラフィックが無いので、`changeType=launch` で登録し、公開前baselineを0で代用しない。

1. 公開前に登録する。`baseline=null`・`baselineStatus=not-applicable-new-url`、`startedAt/evaluateAt/result=null`、`verdict=pending`:
   `node .claude/scripts/themes/evaluate-theme-experiments.mjs --register '{"experimentId":"THEME-LAUNCH-<YYYYMMDD>-<themeKey>","themeKey":"<themeKey>","changeType":"launch","hypothesis":"<公開後に何を観測して何を判断するか>","primaryKpi":"ga4.pageViews","guardrailKpis":["gsc.impressions","internalNav.eventCount"],"baseline":null,"baselineStatus":"not-applicable-new-url","evidenceRefs":["<参照>"]}'`
2. 実際の公開と本番のHTTP・表示の確認が済んだ日だけ `--schedule <id> <YYYY-MM-DD>` で公開日を記録する。
   ローカル検証やPR作成日は公開日ではない。公開をやり直すときは既存観測を動かさず別実験にする。
3. d7は品質の実測のみ（未取得はunknownで記録し、正常と補完しない）。d28は `portfolio.metrics28d`
   の公開後だけの完全窓で `launch-provisional`、d56の完全窓は `launch-observed`。低標本の実カウントは保持し、
   比率や効果は推定しない。欠測・低標本・guardrail不足は `reasons/constraints` に残る。期日は取得開始の目安で、
   窓が揃うまで週次監査の `--check` が再観測を追記する。
4. launchは `effect-*` を確定しない。d56後に
   `--launch-review <id> continue|improve|hold --evidence <ref> --note '<判断理由と次の検証>'`
   で判断を保存する（`verdict=launch-reviewed`）。窓不足なら計測修復のimproveかholdを記録する。
5. 初回公開の有効な56日窓で主KPIがmeasuredなら `result.baselineCandidate` が保存される。これは**次の改善**の
   baseline候補で、launch自身のbaselineを置換しない。次の改善は別IDで登録し、変更公開前の56日窓・scope・statusと照合する。
   期間不明または変更日以降を含むbaselineではeffectを確定しない。
6. 未開始pendingの改善実験のbaselineを直すときは `--update-baseline <id> '<json>'`
   （baseline・baselinePeriod・baselineScopes・baselineStatuses・evidenceRefsのみ）。修正前後の値と公式APIの
   期間・条件・SHAは台帳 `themes.rollout-evidence` に残し、欠測を0で補完しない。
7. **実績を数える範囲は登録時に決める**（2026-11-14）。`"metricScope":"all-routes"` を付けた実験は、全国版・県別・
   市区町村別の合計（`portfolio.metricsAllRoutes` / `metricsAllRoutes28d`）で観測する。検索の表示の94%は県別ページに
   あり、省略時の全国版1 URLだけでは大半のテーマが標本不足になるので、新しい改善実験は `all-routes` で登録する。
   baselineも同じ範囲の値で登録し、範囲の違う値どうしは比べない。全ルートの集計が無いときは全国版の値で代用せず
   `insufficient-data` になる。

改善作業はownerと検証条件付きで既存台帳へ渡し、変更後も新しい実験IDで同じ確認を繰り返す。

- 機械観測の証拠（raw HTML・応答・cf-ray・スクリーンショット）は実行runのartifact（`theme-followup-evidence`・

## 別PCでテーマ拡充の検証を再開する

進捗と再現コマンドは台帳 `themes.rollout-evidence` の全体記録（`data/themes/evidence/2026-09-10-all-expansion.json` の
`reproduction`）、残工程は `.claude/todo/backlog.md` の `THEME-EXPANSION-*` カードを正典とする。
構造の接続、原典・データの確認、主問の充足、実画面の検証、公開は別々に記録し、保留候補を公開済みに数えない。

`.local` のステージ・原典・ブラウザ画面・詳細ログはgit対象外。新PCでは `npm ci` と正規の環境設定が要り、
秘密情報は移行しない。復元の順序:

1. `node --import tsx packages/data-configs/scripts/build-registry.ts` と
   `generate-theme-catalog.ts` / `generate-theme-dependency-mirror.ts` を同じscriptsディレクトリで実行する。
2. `node --env-file=apps/web/.env.development --import tsx .claude/scripts/themes/verify-theme-expansion.mjs --artifacts /tmp/stats47-theme-expansion-api`
   で明記系列のAPI応答とhashを復元する。原典が変わったときは再評価し、旧証拠を流用しない。
3. e-Statの新規指標は `page-data-batch.ts --metric <keys> --kind prefecture`、公式ファイルの指標は
   全体記録の `reproduction.sourceCommands` でローカルに取り込む。すべて `--write-local` までとし、
   原典SHA・県・期間・単位・欠測集合を検査する。PDF抽出には `pdftotext` が要る。
   ジニ係数は原表の値を使い、整数に丸められたSSDS値で代用しない。
4. 既存指標の公式更新は `packages/data-configs/scripts/refresh-official-theme-data.ts`
   （Python依存は同scriptsの `lib/requirements-official-theme-data.txt`）。
5. 全体記録の `reproduction.stageArguments` で `stage-theme-expansion.mjs` を実行する。
   `--local-metrics` は検証済みのcanonical値、`--refresh-items` は公開観測値を変えないメタデータ更新、
   `--all-components` は全テーマ、`--repair-laspeyres-unit` は観測値・順位を保持した単位是正、
   `--tourism-seasonality` は月次専用schemaと照合記録の検査。月次をrankingの年コードへ格納しない。
   `app/ranking-items/all.json` は公開在庫に検証済み差分を重ねて作る。

公開対象は生成後のmanifestにあるkey・bytes・SHAだけ。ranking追加時のOGPとlight/darkカードは別の画像生成manifestで
検証・公開し、canonical itemの配色を使う。旧manifestのSHAは生成日時が変わるので流用しない。manifestだけをコピーした
検証用stageを用意し、古いローカルミラーを監査に混ぜない。

### localhostでの表示検証

```bash
node .claude/scripts/themes/preview-theme-release.mjs --manifest <release manifest> --port 4778
```

ゲートウェイは起動時と配信時にmanifest内のSHAを検査し、必要なファイルだけを読む。巨大GIS原典を常駐メモリへ
複製しない。未収録のappキーは公開R2をGETする。**stageを更新したらゲートウェイを再起動する。** Nextのbuild/startに
`R2_PUBLIC_FETCH_URL=http://127.0.0.1:4778` と `NEXT_PUBLIC_R2_PUBLIC_URL=http://127.0.0.1:4778`、
空の `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` / `R2_S3_ENDPOINT` を指定する。Turbo経由では `--env-mode=loose` が要る。
公開品質baselineへstaged監査を書き込まない。

全テーマをPC・mobileで確認し、章のカード数、値・年・単位、県切替、横はみ出し、JS例外を検査する。
財政の専用章、駅800m人口のGIS、津波対象外県のnull、観光の公式全国月次と10費目支出構成は別途照合する。
修正後の全量結果は全体記録の最新buildと結び付け、古いPASSで置換しない。

### 公開と計測

本番コード・R2の公開は検証済み差分をまとめて行う。新規テーマは公開前baselineを0で補完せず、
実際に公開した日からlaunch実験のd7/d28/d56を設定する（上の「新規URLの初回公開観測」）。
