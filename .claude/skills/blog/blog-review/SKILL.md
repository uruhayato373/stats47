ブログ記事を 2 モードでレビューする。 旧 `/expert-review` と `/proofread-article` を統合した skill。

## 引数

```
$ARGUMENTS — [--mode <expert|proofread>] <記事パスまたは slug>
             --mode expert    : 専門家視点で事実・統計的妥当性をレビュー (デフォルト)
             --mode proofread : 公開前校正 (frontmatter / 本文 / 出典 / リンク 4 領域)
```

### 引数の解決ルール

1. URL が渡された場合: `/blog/{slug}` から slug を抽出
2. slug のみの場合: 以下の優先順で探索
   - `docs/21_ブログ記事原稿/{slug}/article.md` (下書き)
   - `.local/r2/blog/{slug}/article.md` (公開済み)
3. フルパスの場合: そのまま使用

専門家のペルソナ (expert モード) は記事のテーマから自動判定する。 必要に応じて引数に追記してもよい (例: `article.md 交通工学の研究者として`)。

---

## --mode expert: 専門家レビュー

統計データを扱うブログ記事において、**事実の正確性・統計的妥当性・読者への誤解リスク**を専門家の立場から批判的に評価する。

### ペルソナ (自動判定)

記事のテーマ・データ出典・使用指標から最も適切な専門家像を設定する。例:

| 記事テーマ | 専門家ペルソナ |
|---|---|
| 通勤・交通 | 交通工学・都市計画の研究者 |
| 人口・少子化 | 人口学・社会学の研究者 |
| 経済・賃金 | 労働経済学の研究者 |
| 医療・健康 | 公衆衛生・疫学の研究者 |
| 教育 | 教育社会学の研究者 |
| 環境・気候 | 環境科学の研究者 |
| 農業・食料 | 農業経済学の研究者 |

### レビュー構造

1. **専門家ペルソナ** (1 行): どの立場でレビューするかを明示する
2. **総評** (1 段落): 記事全体の信頼性・有用性を率直に述べる
3. **個別指摘** (3〜6 項目): `⚠️ 指摘N` 形式で問題点を挙げる
   - 何が問題か (具体的な箇所・数値・表現)
   - なぜ問題か (読者の誤解・統計的誤り・エビデンスの欠如)
4. **修正提案** (指摘と同数): `✅ 修正提案N` 形式で実行可能な改善策を示す
5. **全体評価スコア** (5 点満点): 正確性・バランス・有用性の 3 軸で採点

### 評価の観点

- **データの正確性**: 引用した数値・統計が出典と一致しているか
- **因果 vs 相関**: 相関関係を因果と誤解させる表現がないか
- **出典の適切性**: データの調査年・定義・対象が記事の主張に合っているか
- **数値の文脈**: 「高い・低い」の基準が示されているか、 比較対象は適切か
- **サンプリング・定義の説明**: 指標の定義が読者に伝わるか
- **過度な一般化**: 都道府県単位の統計を個人レベルに誤適用していないか

### 手順 (expert モード)

1. 引数で指定された記事を読み込む
2. frontmatter の `tags` と本文の見出しからテーマを把握し、 ペルソナを設定する
3. 記事本文・チャート説明・データ出典を確認する
4. 上記の構造・観点に従いレビューを作成する
5. レビュー全文はセッション内で提示し、別ファイルには保存しない。横断的な未完了施策だけを
   `.claude/todo/04_改善バックログ.md` へID付きで統合する。
5b. **★公開ゲート用 `review.md` は必ず書き出す**: `docs/21_ブログ記事原稿/{slug}/review.md` に下記を Write。
   `quality-gate.mjs` は `published:true` の記事でこの `review.md` (verdict: PASS・実体200字以上) が
   無いと公開を blocker で止める (自己採点公開の防止)。**記事本文 (article.md) は編集しない**。
   ```markdown
   ---
   slug: {slug}
   reviewer: blog-critic
   mode: expert
   verdict: PASS | REVISE
   date: 2026-MM-DD
   ---
   ## 評価サマリ
   <読者価値の総括>
   ## 指摘
   - [BLOCK|MAJOR|MINOR] <具体的指摘 + 修正案>
   ## 判定理由
   <根拠>
   ```
   BLOCK が1つでも残れば `verdict: REVISE`。呼び元 (article-writer) が修正 → 再 review で PASS に更新。
6. `review.md` のパス、更新したTODO ID（該当時）と総評を報告する

### 保存先 (expert モード)

公開ゲート用 `docs/21_ブログ記事原稿/{slug}/review.md` のみ。レビュー全文はセッション出力に留める。

## --mode proofread: 公開前校正

記事作成後の公開前チェックを 4 領域で実施する。 問題を検出したら修正案を提示し、 承認を得てから article.md に直接適用する。

### チェック項目

#### 1. フロントマター

- `publishedAt` が `(未定)` のままでないか
- `description` が 120〜160 字であるか
- `tags` が 1 件以上設定されているか
- `category` が設定されているか
- `subtitle` が設定されているか (OGP 画像のサブテキストに使用)
- `title` に `──` や `｜` が含まれていないか (title / subtitle に分離すべき)
- `rankingKeys` が残っていないか (廃止済み・削除対象)
- `seoKeywords` が残っていないか (廃止済み・削除対象)
- **`title` が「○○ランキング」形式でないか** (ランキングページとの検索カニバリ回避)
  - 検出パターン: `title` が「ランキング」を含む
  - ランキングページ `/ranking/` がデータ参照意図を押さえるため、 ブログ記事は洞察・発見・対比をタイトルにすべき
  - 修正方針: 既存の `subtitle` を参考に、 記事の切り口を反映したタイトルに変更を提案する
  - 例: `製造品出荷額ランキング` → `愛知58兆円一強の製造業地図`
- **`title` が「○○格差」「○○の地域差」パターンに偏っていないか**
  - 検出パターン: `title` が「格差」「地域差」で終わる
  - 多くの記事が同じパターンだと一覧で単調に見える。意外性・疑問・逆説・自分ごと化など多様なパターンを使う
  - 例 (NG): `失業率2倍差の労働市場格差` → 例 (OK): `失業率が高い県、低い県の構造`
- **slug が `-ranking` で終わっていないか** (`/ranking/` の URL パスと混同される)
  - 検出: ディレクトリ名 (slug) の末尾が `-ranking`
  - ⚠️ として報告する (slug 変更はリダイレクト設計が必要なため自動修正しない)
- **`title` に記事の主要指標キーワードが含まれているか** (SEO 検索流入チェック)
  - 記事の `tags` や本文の見出しから主要な統計指標名 (例: 「貯蓄率」「日照時間」「出生率」「失業率」) を特定する
  - `title` にその指標名が含まれていない場合、 ターゲットクエリ (「○○ 都道府県」「○○ ランキング」等) での検索流入が見込めない
  - 検出: `tags` の第 1 タグのキーワードが `title` に含まれていない
  - 修正方針: 指標名を自然に組み込んだタイトルを提案する (ランキング形式は避けつつ、 検索意図と記事内容が一致するように)
  - 例 (NG): `手取りの何割を貯められるか` (「貯蓄率」がない → 個人向け家計相談記事に見える)
  - 例 (OK): `貯蓄率が高い県、低い県──手取りの何割を貯めているか` (指標名 ＋ 地理比較 ＋ 自分ごと化)

#### 2. 本文・チャート

- **文体が ですます調 に統一されているか** (★2026-06-08、正典 `.claude/rules/blog-quality-standards.md`「文体」)。本文の地の文に である調 (である。/だ。/だった。/ではない。/だろう。/のだ。/動詞終止形 〜する。〜なる。) が混在していないか。`quality-gate.mjs` が copula である調を blocker 検出するが、動詞終止形の常体は目視/critic で確認。callout・引用・データ出典の体言止めは対象外。混在は ですます へ修正
- フロントマター直後に `# タイトル` (h1) が残っていないか (ページ側で `<h1>` を表示するため二重になる)
- チャートプレースホルダー `<!-- chart:... -->` が残っていないか (SVG 画像に置換済みか)
- `![alt](data/file.svg)` の画像ファイルが `data/` ディレクトリに実在するか
- `[チャート: ...]` 形式のプレースホルダーテキストが残っていないか
- 見出し・alt テキスト・本文に「ベスト」「ワースト」が使われていないか
  - Stats47 は統計情報サイトとして中立的なトーンを保つため「上位」「下位」を使う
  - 例外: 記事タイトル・description・URL slug・他記事へのリンクテキストは変更不要
  - 修正例: `ワースト10──死者が多い県` → `死者数が多い上位10県`
- 本文中に未リンクの指標キー記法が残っていないか
  - 対象パターン: `` e-Stat: `ranking-key` `` / `` (`ranking-key`) `` / `` 使用指標: `ranking-key` (日本語名) ``
  - 修正: 指標キーを削除し、 日本語名を `/ranking/{key}` へのリンクに置き換える
- ボールド記法の中に全角カッコ (`「」`・`（）`) が含まれていないか
  - 検出パターン: `**「` / `**（` / `」**` / `）**`
  - 修正例: `**「規模の不経済」**` → `「**規模の不経済**」`
- ボールド終端 `**` の直前が記号 (`%`・`円`・数字以外の半角記号など) でスペースなしの場合
  - 修正: `**` の後にスペースを入れる
- ボールド開始 `**` の直後に特殊記号 (`△` `▲` `▽` `▼` `※` 等) がある場合
  - 修正: 記号を変更するか前後にスペースを入れる。 減少を示す `△` は `−` (マイナス記号 U+2212) に統一する
- 数値の括弧列挙が冗長でないか
  - 検出パターン: 1 文中に `都道府県名 (数値)` の括弧付き列挙が **3 つ以上**
  - 修正方針: 括弧内の数値を削除し都道府県名のみの列挙にする / 1 位の数値だけ地の文に組み込む
- まとめセクションの構成が正しいか (正しい順序: ①導入文 → ②SVG → ③考察文)
  - NG: マークダウンテーブルとSVGが両方ある / 導入文なしでいきなりSVG
  - マークダウンテーブルのみで SVG がない場合は ❌ として報告し、 SVG を作成して差し替える
- **記事全体のマークダウンテーブル監査** (まとめセクション以外も対象)
  - ❌ 削除対象: Top/Bottom ランキング羅列、 本文と数値が重複、 4 行以下の少量データ
  - ✅ 許可: 採点方法・多次元スコア (8 列以上)・相関係数テーブルなど
- `data/*.svg` の `<svg>` タグに `width`/`height` 属性が明示されているか
  - 修正ルール: 横長は `width="780" height="{round(780*H/W)}"`、 縦長は元寸法維持、 正方形は `width="700" height="700"`
- `data/*.svg` のサブタイトル行に出典・データソース名・年度が埋め込まれていないか
  - 出典情報は SVG に含めず、 md 側の `<data-source>` で記載する

#### 3. データ注記・出典

- 年次ズレ (主要指標と比べて 2 年以上古い) があるデータの散布図・チャート直下に `> [!NOTE]` コールアウトが付いているか
- 各チャート (`![...](data/...)` の画像) の直下に `<data-source>` コンポーネントがあるか
  - 形式: `<data-source url="..." label="..." note="..."></data-source>`
  - `url` と `label` は必須、 `note` は任意、 `year` 属性は **使用しない**
  - **`url` 属性の欠落チェック**: `<data-source label="..."` のみで `url=` がない場合は ❌ として報告し、 DB から `statsDataId` を取得して `https://www.e-stat.go.jp/dbview?sid={statsDataId}` を設定
  - `label` は `e-Stat {source.name}` の形式に統一 (例: `e-Stat 社会・人口統計体系`)
  - 旧形式 (`> 出典：[...](URL)` / `**データ出典:**` 等) は `<data-source>` に変換
- 記事末尾に冗長な全体出典 `<data-source>` が残っていないか
  - 各チャート直下に個別出典がある場合、 末尾の汎用出典は **不要** (削除)

#### 4. サイト内リンク

- ランキングページ・相関ページへのサイト内リンクが `<source-link>` コンポーネントを使っているか
  - 形式: `<source-link href="/ranking/xxx">リンクテキスト</source-link>`
  - 旧形式 (`[○○ランキングを Stats47 で見る →](/ranking/xxx)` 等) は変換
- `### 関連記事` の見出しレベルが `###` (h3) になっているか
- 本文・末尾に空リンク `()` が残っていないか
- **ランキングチャートに対応する `<source-link>` があるか** (ランキング → リンク対応チェック)
- **`<source-link>` が末尾に集約されていないか** (インライン分散チェック)
  - 各 `<source-link>` は、 そのランキングデータを言及・分析しているセクションの末尾に配置すべき
  - 配置の正典: `.claude/rules/blog-quality-standards.md`「source-link の配置」。決定的検査: `node .claude/scripts/blog/audit-article-structure.mjs` (`/ranking/` の末尾集約 2 個以上を検出)
- **リンク先の存在確認** (完全DBレス。旧 D1 indicators は廃止): `<source-link>` や `### 関連記事` のリンク先が実在・公開済みか R2 で確認
  - ランキングは `curl -s -o /dev/null -w '%{http_code}' https://storage.stats47.jp/app/ranking/<key>/item.json` が 200 か
  - 存在しないキーが見つかった場合の **類似キー検索** (必須):
    1. リンクテキストからキーワードを抽出
    2. `curl -s https://storage.stats47.jp/app/ranking-items/all.json | jq '.items[] | select(.title | test("キーワード")) | {ranking_key: .rankingKey, title}' | head`
    3. キーの一部でも部分一致検索
    4. 候補があれば修正案を提示、 なければ TS-config 追加 + `/page-data-batch --metric <key>` でデータ登録を提案
  - 登録・修正するかどうかはユーザーの判断に委ねる (自動修正しない)

### 手順 (proofread モード)

1. 引数で指定された記事ファイルを読み込む
2. slug (ディレクトリ名) を特定し、 `data/` ディレクトリの内容を確認する
3. 各チェック項目を実行する
4. 結果を下記フォーマットで出力する
5. ❌ 項目がある場合、 修正内容を提示してユーザーの承認を得てから article.md を更新する
6. 修正適用後、 校正日時を **article.md の frontmatter** に記録する (完全DBレス。記事 SSOT は article.md。旧 D1 `articles` テーブルは廃止):
   - frontmatter に `proofreadAt: <ISO日時>` を追記/更新する (例: `proofreadAt: 2026-07-04T12:00:00Z`)
   - 公開記事の article.md は R2 `app/blog/<slug>/article.md` が SSOT (作業は `/brushup-blog` の取得フロー経由)

### 未校正記事の一覧取得 (proofread モード)

完全DBレス (旧 D1 `articles` テーブルは廃止。判定は article.md frontmatter):

```bash
# 未校正の公開記事 (proofreadAt 未設定、古い順)。proofreadAt は article.md frontmatter → snapshot に export 済
curl -s "https://storage.stats47.jp/app/blog/all.json" \
  | jq -r '.articles | map(select(.published and (.proofreadAt == null))) | sort_by(.publishedAt) | .[] | [.slug, .title] | @tsv'

# 校正後に本文更新された記事 (再校正要): proofreadAt < updatedAt
curl -s "https://storage.stats47.jp/app/blog/all.json" \
  | jq -r '.articles | map(select(.proofreadAt != null and .proofreadAt < .updatedAt)) | sort_by(.updatedAt) | reverse | .[] | [.slug, .proofreadAt, .updatedAt] | @tsv'

# 作業中ドラフト (docs/21 outbox) は frontmatter を直接見る: grep -L "proofreadAt:" docs/21_ブログ記事原稿/*/article.md
```

### サイト内リンクの追加方針 (proofread モード)

記事末尾には `### 関連記事` セクションを配置し、**他のブログ記事 (`/blog/...`) へのリンクのみ** を掲載する。

```markdown
### 関連記事

- [記事タイトル](/blog/slug)
```

- リンク数は 2〜4 件を目安とする
- リンク先は `/blog/...` のみ。 ランキングページ (`/ranking/...`) は本文中に `<source-link>` でインライン配置する
- 記事の `tags`・テーマから関連性の高い既存ブログ記事を選ぶ。 該当記事がない場合はセクション自体を省略してよい
- 旧形式チェック: 末尾に `<source-link>` や `/ranking/...` リンクが並んでいたら、 ランキングリンクは本文中に移動し、 関連ブログ記事のリンクに差し替える
