**コメントは実行されない。** 同じ情報を 2 箇所に書き、「追加時は両方を更新」と注意書きで
同期を担保する設計は、注意書きを読まないまま片方だけ更新されて必ずドリフトする。

## 実測した被害 (2026-08-20)

`app/sitemap.xml/route.ts` が `const SEGMENT_COUNT = 8` とハードコードし、
「app/sitemap.ts の SEGMENTS と一致（追加時は両方を更新）」とコメントしていた。実際には:

| segment | 追加 | URL 数 | 結果 |
|---|---|---|---|
| cities | 2026-06 | **1,080** | **2 か月以上** Google 未提出 |
| japan | 2026-08-20 | 19 | 新設直後から未提出 |

**Why 発見が遅れたか:** shard 自体 (`/sitemap/8.xml`) は 200 で正しい内容を返す。
ページを直接叩く監視・スモークテストでは**原理的に発見できない**。
index を経由して初めて分かる欠落だった。

**Why 誤診しかけたか:** 最初は ISR キャッシュの stale を疑い purge まで実行した (効果なし)。
決め手は **「cities は 6 月からあるのに index に無い = 以降の複数回のデプロイでも直っていない」**。
キャッシュ説では説明がつかない、という消去法でコード側に辿り着いた。

**How to apply:**

1. **同じ情報を 2 箇所に書かない。** 定義を 1 ファイルへ切り出し、両方が import する。
   件数は `X.length`、id は `X.indexOf(name)` で**導出**する。
2. **テストにも数値を書かない。** 書くと 3 つ目の同期先になる。
   `expect(count).toBe(SEGMENTS.length)` のように単一ソースとの一致で検査する。
3. **「〜と一致させる」「両方を更新」というコメントを見たら疑う。**
   それは「まだ壊れていない二重管理」の宣言であって、担保ではない。
   横断検索: `grep -rnE "両方を更新|と一致させ|と完全一致|同期させ"`
4. **配信物の"入口"を監視対象にする。** 個々のページが 200 でも、
   index・一覧・sitemap から漏れていれば到達されない。
