**事象 (2026-10-07)**: テーマ系 PR (#1084→#1085→#1090) の取り込みを一時 worktree で検証したとき、
`node_modules` を本体の `/home/user/stats47/node_modules` へ丸ごと symlink していた。root の
`node_modules/@stats47/<pkg>` は `../../packages/<pkg>` への相対 symlink なので、解決先が **本体の
packages (develop)** になり、worktree のブランチにだけある export (`@stats47/data-configs/theme-selection-viewpoints`)
が「見つからない」と出た。そこから派生した implicit any などの型エラー 10 件以上は、すべて見かけの誤りだった。
逆に、本体にあって worktree に無いものは見逃す。

**同じ型 (2026-10-28)**: アプリが作る worktree (`.claude/worktrees/<名前>`) には node_modules が無く、Node は親を辿って
本体の `node_modules/@stats47/*` (本体の develop) を読む。pre-commit の `content:sync --check` と `metrics:check` が本体の指標で
判定し、「ID索引が古い状態です」で worktree のコミットを止めた。`content:sync` を走らせると本体の指標で索引を書き換えてしまう
(書いたら `git checkout -- data/content` で戻す)。worktree に `node_modules/@stats47/<名前>` だけを作り worktree の
`packages/*`・`apps/*` へ symlink すると、両検査とも通った。

**How to apply**:
- worktree で型検査・テストを回すときは、root `node_modules` を丸ごと symlink しない。実ディレクトリを作り、
  `@stats47` 以外の各エントリだけを本体へ symlink し、`node_modules/@stats47/<pkg>` は worktree の
  `packages/<pkg>` を指す symlink にする (`readlink -f node_modules/@stats47/data-configs` が worktree を指すことを確かめる)。
- worktree の型エラーが「モジュールが見つからない」から始まるときは、コードを直す前にまず解決先を疑う。
- Linux の `rm -rf` / `git worktree remove` は symlink を辿らないが、Windows の junction は辿って本体を消す
  (`feedback_worktree_junction_deletes_target.md`)。

**同じ型 (2026-11-05)**: root の `node_modules` だけ張った worktree では、pre-commit の `type-check:image-pipeline` が `@opennextjs/cloudflare` 不在と `tailwind-merge` の `radius` で落ちた。どちらも `packages/*/node_modules` にだけある依存 (r2-storage の optional / components の 3.x。root の tailwind-merge は 2.6.1) で、変更とは無関係。workspace ごとの `node_modules` にも junction を張ると通る。bash から junction を張るときは `fs.symlinkSync(path.resolve("C:/…"), path.resolve(p), "junction")` のようにスラッシュ区切りで書き、`fs.readlinkSync` で張り先を確かめる (バックスラッシュが落ちると、壊れたリンクが黙ってできる)。外すときは全 junction を `fs.unlinkSync` してから `git worktree remove`。

**worktree で `npm ci` を走らせると本体の依存が消える (2026-11-14)**: PR の CI の落ちる段をまとめて洗い出そうと、`pr-quality-check.yml` の job の `run:` 段を手元で全部流すスクリプトを書き、`npm ci` の段まで実行した。worktree の `packages/*/node_modules`・`apps/*/node_modules` は本体の同名フォルダへの symlink だったので、`npm ci` が symlink を辿って**本体の 25 個の workspace の node_modules を空にした** (root の node_modules は worktree 側が実ディレクトリで無事)。本体で動く別のセッションの型検査とビルドも落ちる。復旧はオーナー承認のうえ本体で `npm install --prefix <本体>`。**CI の段を手元で流すときは、依存を入れる段 (`npm ci`・`npm install`・`npx playwright install` など) を必ず除く。** worktree で依存の入れ直しが要るときも、symlink の先が本体なら本体を壊すので実行しない。

**worktree で管理画面を動かす (2026-11-05)**: preview_start は本体の `.claude/launch.json` を読むので worktree の設定は効かない。junction の worktree では Turbopack が root の外をコンパイルしないため、一時的に `apps/admin/next.config.ts` へ `turbopack: { root: "C:/" }` を足し、PATH に本体の `node_modules/.bin` を入れて `PORT=4748 node scripts/run-next.mjs dev` で起動した (確認後に戻す)。`npm exec -- node` は npx キャッシュの別の node を起動し、全ページが `rawHeaders.hasOwnProperty is not a function` で 500 になる。

**Mac の worktree で管理画面を動かす (2026-11-13)**: `.claude/worktrees/<名前>` で依存を symlink にした worktree では、Turbopack が「Could not find the Next.js package」で全ページ 500 になる。一時的に `apps/admin/next.config.ts` へ `turbopack: { root: "<本体の絶対パス>" }` を足すと通る。preview_start は worktree の `.claude/launch.json` を読むので、4747 を本体が使っているときは `bash -c "PORT=4748 npm run admin"` の設定を一時的に足す。ブラウザは `localhost:4748` で開く (`127.0.0.1` は拒否された)。`npm run admin` の前処理が `.claude/state/metrics/model-usage/` を書き換えるので、確認後に `git checkout --` で設定 2 つと一緒に戻す。

**Mac の worktree で公開サイト (apps/web) を動かす (2026-11-14)**: 管理画面と違い、`turbopack.root` を足すだけでは「Could not find the Next.js package」のまま全ページ 500 になる。`apps/web/next.config.ts` は `outputFileTracingRoot` も持っていて、2 つの基準フォルダが食い違うと Turbopack が worktree 側を採るため。一時的に `outputFileTracingRoot` と `turbopack.root` の両方を本体の絶対パスにし、`apps/web/.next/dev` を消してから `npm run dev:web` で起動する (確認後に `git checkout -- apps/web/next.config.ts` で戻す)。`WEB_DEV_BUNDLER=webpack` でも起動はするが、8GB の Mac では 1 ページ 75 秒かかり計測に使えなかった。preview_start の `web` は本体ツリーのコードで起動するので、worktree の変更を見るときは Bash のバックグラウンド実行で起動する。
