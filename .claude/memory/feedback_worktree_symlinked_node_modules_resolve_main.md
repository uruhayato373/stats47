**事象 (2026-10-07)**: テーマ系 PR (#1084→#1085→#1090) の取り込みを一時 worktree で検証したとき、
`node_modules` を本体の `/home/user/stats47/node_modules` へ丸ごと symlink していた。root の
`node_modules/@stats47/<pkg>` は `../../packages/<pkg>` への相対 symlink なので、解決先が **本体の
packages (develop)** になり、worktree のブランチにだけある export (`@stats47/data-configs/theme-selection-viewpoints`)
が「見つからない」と出た。そこから派生した implicit any などの型エラー 10 件以上は、すべて見かけの誤りだった。
逆に、本体にあって worktree に無いものは見逃す。

**同じ型 (2026-10-28)**: アプリが作る worktree (`.claude/worktrees/<名前>`) には node_modules が無く、Node は親を辿って
本体の `node_modules/@stats47/*` (本体の develop) を読む。pre-commit の `content:sync --check` と `metrics:check` が本体の指標で
判定し、「ID索引が古い状態です」で worktree のコミットを止めた。`content:sync` を走らせると本体の指標で索引を書き換えてしまう
(書いたら `git checkout -- data/content` で戻す)。worktree に `node_modules/@stats47/<名前>` だけを作り worktree の
`packages/*`・`apps/*` へ symlink すると、両検査とも通った。

**How to apply**:
- worktree で型検査・テストを回すときは、root `node_modules` を丸ごと symlink しない。実ディレクトリを作り、
  `@stats47` 以外の各エントリだけを本体へ symlink し、`node_modules/@stats47/<pkg>` は worktree の
  `packages/<pkg>` を指す symlink にする (`readlink -f node_modules/@stats47/data-configs` が worktree を指すことを確かめる)。
- worktree の型エラーが「モジュールが見つからない」から始まるときは、コードを直す前にまず解決先を疑う。
- Linux の `rm -rf` / `git worktree remove` は symlink を辿らないが、Windows の junction は辿って本体を消す
  (`feedback_worktree_junction_deletes_target.md`)。
