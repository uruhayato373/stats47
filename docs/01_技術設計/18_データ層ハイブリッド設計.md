# データ層ハイブリッド設計（旧・却下案）

> （以下は採択時の原文。歴史的記録）
> 「全部 DB レス（R2 直接）」でも「全部リモート D1」でもなく、**データの“形”で SSOT を使い分ける**。

## 0. 結論（一行）

**本番アプリは R2 snapshot のみ読む（不変）。** オーサリング SSOT は「形」で使い分ける —
**低volume・人手・型/レビューが効く設定 = git TS** / **横断クエリ・関係・集計入力 = リモート D1** /
**配信 = R2 JSON** / **集計(Derived) = D1 で JOIN → R2**。

## 1. なぜハイブリッドか（2026-05-29 決定）

両極端はどちらも最適でない:

- **全部 DB レス（R2 直接 JSON）**: simple だが、横断クエリ・参照整合性・トランザクション・集計 JOIN が弱い。
  page_components のような関係を持つ設定や area_profile/相関の集計には不向き（使い捨て DB を毎回建てる新規実装が要る）。
- **全部リモート D1**: クエリ・関係・集計は強いが、人手オーサリングの設定まで DB に入れると
  **version control（diff/PR review/型安全）の利点を失う**。設定は「コードとして」持つ方が事故が少ない。

→ **データの形で SSOT を選ぶ**のが最適。**配信層は常に R2**（app は R2 しか読まない）で固定し、上流だけ使い分ける。

## 2. 3 層モデル

```
オーサリング層(SSOT)  : 形で選ぶ ── git TS(型/review)  または  リモートD1(クエリ/関係)
配信層(app が読む)    : 常に R2 JSON snapshot                      ← ここは不変
集計(Derived)        : リモートD1 で JOIN → R2 へ書き出し（or エフェメラル計算）
```

## 3. データ分類と置き場（決定表）

| 種別 | サブ判定 | SSOT 置き場 | 該当 |
|---|---|---|---|
| **Authored / 設定** | 低volume・人手・型/review が効く | **git TS**（→ seed で D1 / R2 反映） | テーマのチャート定義（`theme-page-component-additions.ts`）、各種カタログ定義 |
| **Authored / 関係・運用** | 横断クエリ・参照整合性・高頻度 CRUD | **リモート D1**（→ exporter で R2） | page_components・theme_metrics・sns_posts・affiliate_ads・categories/themes |
| **Reference** | 外部に真実源あり | **再生成** | metrics(TS registry)・articles(article.md)・estat_catalog(e-Stat API)・prefectures/cities(JSON) |
| **Derived** | 計算で作れる | **D1 で JOIN → R2**（永続しない） | area_profiles・correlations |

> **page_components の位置づけ**: 関係を持つ運用設定なので SSOT は **リモート D1**。
> ただし**再現可能性のため、量産・追加分は git TS 定義 → seed スクリプトで D1 投入**する
> （手編集 JSON の散逸を防ぐ）。§5 参照。

判定フロー:

```
このデータの真実源は？
  ├─ 外部に元がある(git TS/article.md/API)         → Reference（再生成）
  ├─ 観測値等から計算できる                          → Derived（D1 JOIN → R2、永続しない）
  └─ 人/エージェントが作る(元ネタ無し)
        ├─ 低volume・人手・型/review が効く設定        → git TS（SSOT）→ seed → D1/R2
        └─ 横断クエリ・関係・運用 CRUD                → リモート D1（SSOT）→ exporter → R2
```

## 4. リモート D1 の扱い（セットアップ＝ローカル）

- **D1 のセットアップ・編集・集計はローカル（Mac）で行う**。`account_id` / wrangler 認証 /
  インスタンス再作成（解約済 database_id の作り直し）が必要なため。手順は `17_リモートD1ハイブリッド設計.md` §5 と
  `packages/database/seed/README.md`。
- **クラウドの Claude Code** は当面 **R2(S3) と git TS のみ**で作業する（D1 認証が無い）:
  - できる: git TS 設定の編集、R2 serving snapshot の生成・反映（S3 creds あり）、R2 からの読み取り。
  - できない（ローカルに委譲）: D1 への直接 CRUD、D1-backed の exporter 実行、D1 を使う集計。
- 本番ランタイムは **R2 snapshot 配信を維持**（D1 = オーサリング/ビルド DB）。動的化は後段で検討。

### クラウド ↔ ローカル 作業分担

| 作業 | クラウド agent | ローカル(Mac) |
|---|---|---|
| git TS 設定の編集・review | ✅ | ✅ |
| R2 serving snapshot 反映（S3 直接） | ✅ | ✅ |
| D1 への CRUD / seed 投入 | ❌（R2 直接 fallback で代替可） | ✅ |
| D1-backed exporter（sync-snapshots） | ❌ | ✅ |
| 集計（area_profile/相関の JOIN） | △（エフェメラルなら可） | ✅ |

## 5. page_components の標準フロー（実例）

```
① git TS 定義        apps/web/scripts/theme-page-component-additions.ts   ← 単一ソース（review/型）
② seed → D1          apps/web/scripts/seed-theme-page-components.ts        ← ローカルで D1 投入（冪等）
③ D1 → R2 export     apps/web/scripts/export-page-components-snapshot.ts   ← serving snapshot 生成
─────────────────────────────────────────────────────────────────────────
（クラウド fallback）  apps/web/scripts/sync-theme-additions-to-r2.ts        ← D1 不在時に R2 直接反映（即時）
```

- 平常は ①→②→③（ローカル、D1 が SSOT）。
- クラウドで急ぎ反映したい時だけ fallback（①の定義から R2 を直接更新）。**次回ローカルで②③を流せば D1 と一致**
  （①が単一ソースなので drift しない）。

## 6. 集計（Derived）

- **リモート D1 で指標横断 JOIN → R2 に書き出す**のが基本（compute ロジックは
  `packages/area-profile/.../run-batch-area-profile.ts` / `packages/correlation/.../calculate-pearson.ts` 既存）。
- D1 を使わない選択肢として、**エフェメラル計算**（`:memory:` SQLite or DuckDB で R2 観測値を読む使い捨て）も可。
  クラウド完結が必要な集計だけこちらにする。
- **観測値は二度と永続 DB に入れない**（R2 のまま。Phase 6 の肥大=解約の原因を再発させない）。

## 7. 移行フェーズ

| Phase | 内容 | 状態 |
|---|---|---|
| ① | docs/rules/CLAUDE.md/hook を本ハイブリッド設計に更新 | ✅ 2026-05-29 |
| ② | 設定の量産を git TS 定義化（theme charts で実証） | ✅ |
| ③ | リモート D1 インスタンス再作成 + migration + seed 投入（ローカル） | ⬜ |
| ④ | area_profile/相関を D1 JOIN（or エフェメラル）→ R2 に整理 | ⬜ |
| ⑤ | `db:pull` 持ち回り（R2 blob を SSOT 扱い）を廃止し、D1 共有 + git TS に一本化 | ⬜ |

> ③まで未完の間は、現行の R2 blob 持ち回り（`db:pull`/`db:push`）も併存して構わない（壊さない）。
> ただし**手調整データを書くのはローカル 1 箇所に固定**し、クラウドは読む/R2 直接 fallback に留める（上書き消失防止）。

## 8. 禁止事項

| NG | OK |
|---|---|
| 観測値・派生を永続 DB に入れる | R2（観測値）/ D1 JOIN or エフェメラル（派生）→ R2 |
| 設定を手編集 JSON で散逸させる | git TS を単一ソースにし seed/export で反映 |
| 本番アプリから DB を query する | R2 snapshot 経由（`fetchFromR2AsJson`） |
| クラウド agent が D1 を前提に詰まる | D1 作業はローカルに委譲、クラウドは git TS / R2 直接 |
