# リモート D1 ハイブリッド設計（ブログ管理・運用エンティティの cloud 完結）

> **目的**: クラウドの Claude Code で**すべての作業を完結**できるようにする。
> 現状ネックの「git 管理外・R2 持ち回りの SQLite 1 ファイル」を、
> **リモート Cloudflare D1（共有 DB）**に置き換え、`db:pull` 持ち回りを無くす。

> **採用案 (status: adopted)**。検討した代替案（純 file-SSOT / 現状の持ち回り）は [§6](#6-検討した代替案と却下理由) に記録。

## 0. 背景（なぜ見直すか）

2026-05-29 のセッションで、クラウド環境から `npm run db:pull` が失敗（R2 に `database/stats47.sqlite` が未 seed）し、
次フェーズ（metric 量産・snapshot 生成）がブロックされた。根本原因を実測調査した結果:

- **本番 `apps/web` は DB を一切クエリしない**（R2 snapshot のみ。grep ヒットは型 import だけ）
- DB を import する 142 ファイルは**すべてビルド時 exporter / batch**
- DB の唯一の仕事 = `sync-snapshots` の 13 exporter＋相関計算の**入力**になること
- **真のネックは「集計」ではない**。area_profiles / correlations は compute script が実在し再生成可能。
  本当に救出が要るのは **Authored 系（sns_posts / affiliate_ads / theme_metrics 等）で、
  真実源が DB 内だけにあり git/R2 にバックアップが無い**こと。これが「初回 seed は実環境から」を必須化し、
  持ち回りを不可避にしている。

関連: `.claude/rules/data-sqlite-ssot.md`（Phase 6 で観測値を R2 移行済の経緯）

## 1. 全テーブルを3種類に仕分ける

設計の鍵は、各テーブルを**真実源の所在**で分類すること。

| 種別 | 定義 | 置き場 | 該当（2026-05-29 実測） |
|---|---|---|---|
| **Authored** | 人/エージェントが作る。外部に真実源が無い | **リモート D1** | sns_posts(549)・affiliate_ads(24)・theme_metrics(284)・page_components(411)・categories/themes master |
| **Reference** | 外部に真実源がある | **再生成**（import / API） | metrics(TS registry)・prefectures/cities(JSON)・estat_metainfo/estat_catalog(e-Stat API)・**articles(article.md)** |
| **Derived** | 他データから計算できる | **batch 計算 → R2**（保存しない） | area_profiles・correlations（compute script 実在、入力を DB→R2 に繋ぎ替え） |

実測根拠:
- `packages/area-profile/src/services/run-batch-area-profile.ts`（compute 実在）/ `packages/correlation/src/utils/calculate-pearson.ts`（compute 実在）
- **articles は Derived**: `packages/database/scripts/sync-articles-from-r2.ts` の `buildArticleData()` が示すとおり
  `article.md` frontmatter から全列再構成可能。D1 の SSOT にする必要は無く **R2 が真実源**。
- theme_metrics: compute / populate script が見つからない → **Authored（手調整）**と判断

## 2. 目標の最終形（ハイブリッド）

```
本文          = article.md (git/R2)        ← 履歴・review が効く
運用メタ/索引  = リモート Cloudflare D1      ← 共有・CRUD 快適・cloud 完結
観測値        = R2 (app/stats/*)            ← 不変
集計(相関等)   = R2 からエフェメラル計算       ← §4
```

- クラウド・ローカル・本番が**1 つの共有 D1** を叩く → `db:pull` 持ち回りが消える（今回詰まった原因の根絶）
- 本番ランタイムは当面 **R2 snapshot 配信を維持**（D1 = オーサリング/ビルド DB）。動的化は後段で検討。

## 3. なぜ D1 ハイブリッドが妥当か（2026-05-29 実測）

- 解約理由（観測値 5.5M 行で 15GB 肥大）は R2 移行で解消済。残る運用データは**数百行＝D1 無料枠に余裕で収まる**
- drizzle schema は全テーブル `sqliteTable`＝**D1（SQLite）で無改修動作**。migration `0000`〜`0008` も流用可
- `wrangler.toml` に binding `STATS47_STATIC_DB` が残存（database_id は解約済のため**再作成が必要**）

## 4. 集計の「工夫」＝エフェメラル計算パターン

指標横断の SQL JOIN が要る処理（area_profile / 相関）だけ、実行時に一時 DB を建てる（D1 にも持ち回り SQLite にも依存しない）:

```ts
// build-aggregates.ts （cloud で実行、何も永続しない）
const db = new Database(":memory:");          // or /tmp/xxx.sqlite（使い捨て）
for (const m of registry)                     // metrics/*.ts を import
  insert(db, await readStatsValues(m.key));   // R2 から観測値を流し込む
const profiles = computeStrengthWeakness(db); // 既存ロジックを再利用
const corr     = computePearson(db);
await writeR2("app/areas/.../profile.json", profiles);
await writeR2("app/correlation/top-pairs.json", corr);
db.close();                                   // 破棄
```

- 「何度も実行しない」前提なので、毎回 ~2,000 本の JSON を読んでも問題なし（バッチであってリクエストではない）
- DuckDB なら R2 の JSON を直接 SQL で JOIN 可能（既存 better-sqlite3 ロジックを残すなら in-memory SQLite でも可）

## 5. 実装と runbook

### 用意済みツール（2026-05-29、クラウドで検証済）

| ツール | 役割 | 実行環境 |
|---|---|---|
| `packages/database/scripts/extract-articles-seed-from-r2.ts` | R2 article.md → `seed/articles.json`（196 件） | **クラウド可** |
| `packages/database/scripts/dump-tables-to-seed.ts` | Authored 系を Mac SQLite → `seed/<table>.json`（Phase 0 凍結兼用） | **Mac 必須** |
| `packages/database/scripts/seed-to-d1-sql.ts` | seed → `seed/d1-seed.sql`（D1 投入 SQL） | クラウド可 |

**検証済（クラウド）**: 抽出 196 件 → SQL 生成 → in-memory SQLite ロード（196 行・published=117・tags 有効 JSON）。

### 残作業（要 Mac / Cloudflare 認証）

1. Authored 系ダンプ（Mac、Phase 0 凍結兼用）
2. D1 インスタンス再作成（`wrangler d1 create`）
3. migration 適用（`wrangler d1 migrations apply`）
4. seed 投入（`wrangler d1 execute --file`）

**全手順の runbook**: `packages/database/seed/README.md`

### 運用ルール（再肥大の防止）

- **観測値は二度と D1 に入れない**（R2 のまま）。D1 = 運用/メタ専用。
- 編集後は従来どおり `/sync-snapshots` で R2 snapshot を再生成。

## 6. 検討した代替案と却下理由

| 案 | 概要 | 却下理由 |
|---|---|---|
| **案1: 純 file-SSOT（DB レス）** | 全 Authored を git ファイル化し、SQLite を完全廃止。集計のみ :memory: で一時計算 | 13 exporter の全書換＋ page_components 等の per-file 化が大工事。D1 ハイブリッドと同じ cloud 完結効果を、遥かに大きい移行コストで得るだけ |
| **案2: 現状維持（持ち回り SQLite）** | `db:push`/`db:pull` で R2 経由の SQLite blob を持ち回る | クラウドで `db:pull` 必須＝今回詰まった原因そのもの。blob は diff/merge 不可で上書き消失リスク |

案3（D1 ハイブリッド）を採用：移行コストが最小（schema 無改修・migration 流用）で、cloud 完結＋ multi-writer 安全＋ CRUD 快適を同時に満たす。articles 本文は git/R2 に残すため、D1 の弱点（行に履歴が無い）も補える。

## 7. 暫定運用（D1 立ち上げ前まで）

D1 を立ち上げるまでは、現行の R2 持ち回りで量産は回る:
- **判断ルール**: DB 内の手調整データ（page_components / sns_posts 等）を**書くのはローカル 1 箇所に固定**。
  クラウドは読むだけ。これを守る限り blob 持ち回りでも上書き消失は起きない。
- 手順: ローカル（Mac）で `npm run db:push --workspace=packages/r2-storage` → 以降クラウドで `npm run db:pull`
