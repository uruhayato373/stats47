# 完全DBレス設計（正典）

> **本ファイルが stats47 のデータ層アーキテクチャの単一正典。**
> 永続 DB（リモート/ローカルの常駐 D1・SQLite）を **SSOT として持たない**。
> SSOT は **git TS（コード）** と **R2（観測値・配信）** の二つだけ。集計（Derived）は
> **エフェメラル計算**（使い捨て `:memory:` SQLite / DuckDB が R2 を読む）→ R2 へ書き出す。
> 旧記述（データ層ハイブリッド設計 / リモートD1ハイブリッド設計 / `.claude/rules/data-sqlite-ssot.md` 等）と食い違う場合は**本ファイルが優先**。

## 0. 結論（一行）

**永続 DB を一切持たない。** SSOT は **git TS（設定・定義・運用エンティティ）** と **R2 JSON（観測値・配信 snapshot）**。
本番アプリは **R2 snapshot のみ読む**（不変）。集計（area_profiles / correlations）は
**ビルド時のエフェメラル計算 → R2**。リモート D1 は廃止する。

## 1. なぜ完全DBレスか（2026-05-29 決定）

同日に一度「ハイブリッド（運用エンティティはリモート D1 が SSOT）」を採択（doc 18）したが、
**owner 判断で完全 DB レスに変更**した（改訂履歴 §10）。理由:

- **本番ランタイムは既に R2 only**。Phase 8（2026-04-29）で本番 D1 binding を削除済み、CI gate で再発防止済。
  app 実行時の D1 query は 0 件。配信層を変えずに「上流の永続 DB」だけ無くせる。
- **リモート D1 は運用コストと単一障害点**。Phase 6 で観測値肥大により一度解約した経緯があり、再導入は
  「account_id / wrangler 認証 / インスタンス再作成 / ローカル専用 CRUD」という**クラウド完結を妨げる制約**を持ち込む。
- **設定・運用エンティティはコード（git TS）で持つ方が事故が少ない**。diff / PR review / 型安全 / 再現性が効き、
  「手編集 JSON の散逸」も「DB 行のドリフト」も起きない。
- **横断クエリ・参照整合性は「ビルド時」に解決すればよい**。実行時の動的 JOIN は不要（本番は静的 snapshot 配信）。
  必要な集計は git TS / R2 を入力にビルド時計算して R2 JSON を出す。

→ **永続 DB を SSOT にしない。** 配信は常に R2、上流は git TS、集計は使い捨て計算。

## 2. 2 層モデル

```
オーサリング層(SSOT)  : git TS（設定・定義・運用エンティティ）  +  R2（観測値）
配信層(app が読む)    : 常に R2 JSON snapshot                      ← ここは不変
集計(Derived)        : エフェメラル計算（:memory: SQLite / DuckDB が R2 を読む使い捨て）→ R2 へ書き出し
```

**永続 DB は登場しない。** ビルド/集計時に一時的な in-memory / 使い捨て SQLite を建てるのは可
（schema 定義 `packages/database/src/schema/*.ts` を型ソースとして再利用）。**プロセス終了で消える**ことが条件。

## 3. データ分類と置き場（決定表）

| 種別 | サブ判定 | SSOT 置き場 | 該当 |
|---|---|---|---|
| **Authored / 設定** | 低volume・人手・型/review が効く | **git TS** → R2 へ反映 | page_components 定義（`apps/web/scripts/data/page-components/`）、各種カタログ定義 |
| **Authored / 運用** | 関係・横断参照を持つ運用エンティティ | **git TS（定義が SSOT）** → 生成スクリプトで R2 JSON | page_components・theme_metrics・sns_posts・affiliate_ads・categories/themes |
| **Reference** | 外部に真実源あり | **再生成** | metrics(TS registry)・articles(article.md)・estat_catalog(e-Stat API)・prefectures/cities(JSON) |
| **Derived** | 計算で作れる | **エフェメラル計算 → R2**（永続しない） | area_profiles・correlations |

> **「運用エンティティ」が D1 から git TS に変わった点が doc 18 からの最大の差分**。
> 横断クエリ・参照整合性は **ビルド時に git TS（+必要なら R2 観測値）を入力に検証・生成**して担保する
> （実行時の動的クエリは不要）。手編集 JSON を SSOT にはしない（必ず git TS 定義 → 生成）。

判定フロー:

```
このデータの真実源は？
  ├─ 外部に元がある(git TS / article.md / API)        → Reference（再生成）
  ├─ 観測値等から計算できる                            → Derived（エフェメラル計算 → R2、永続しない）
  └─ 人/エージェントが作る(元ネタ無し)                  → git TS（SSOT）→ 生成スクリプトで R2
```

## 4. クラウド ↔ ローカル 作業分担（完全DBレスの利点）

永続 D1 を無くすことで **クラウド agent / ローカル Mac の作業差がほぼ消える**（D1 認証が不要になる）。

| 作業 | クラウド agent | ローカル(Mac) |
|---|---|---|
| git TS 設定・定義の編集・review | ✅ | ✅ |
| R2 serving snapshot 生成・反映（S3 直接） | ✅ | ✅ |
| Derived のエフェメラル計算（`:memory:`/DuckDB が R2 読み）→ R2 | ✅ | ✅ |
| 永続 D1 への CRUD | — (廃止) | — (廃止) |

- S3 creds（`.env.local` / CI secrets）さえあれば **集計もクラウドで完結**する（doc 18 の「集計はローカル限定」制約が外れる）。
- 本番ランタイムは **R2 snapshot 配信を維持**。動的化は後段で検討。

## 5. 運用エンティティ（page_components 等）の標準フロー（Phase E 実装済 2026-05-30）

```
① git TS 定義   apps/web/scripts/data/page-components/<pageType>/<key>.json  ← 単一 SSOT (git tracked)
                  pageType = area / area-category / city-category / theme
                  ranking page-cards = .../ranking-page-cards/<key>.json
② git TS → R2   apps/web/scripts/export-page-components-snapshot.ts          ← R2 serving snapshot を直接生成
                  ranking page-cards = export-ranking-page-cards-snapshot.ts
③ 検証          apps/web/scripts/verify-page-components-snapshot.ts          ← 生成物 == cloud 配信を byte 一致確認
```

- **永続 D1 への seed と D1→R2 export は廃止**。git TS JSON から R2 を直接生成する 1 経路に一本化。
  旧 `theme-page-component-additions.ts` / `sync-theme-additions-to-r2.ts` / `seed-*-page-components.ts` は
  Phase E で全削除（内容は data/page-components/ に取り込み済）。
- 初期 git TS 化は `extract-page-components-from-r2.ts`（cloud R2 を git TS から列挙した key で probe → verbatim 保存）で実施。
- 横断検証（参照整合性・キー重複・孤立参照）は **生成スクリプト内でビルド時に行う**（in-memory で十分）。
- affiliate_ads も同型: `apps/web/scripts/affiliate-ads-data.ts`（git TS）→ `export-affiliate-ads-snapshot.ts`。
- themes/theme_metrics は `packages/types/src/indicator-sets/*.ts` が SSOT（app が直読、R2 config は不要）。
- これにより「定義が単一ソース → 生成で R2」がクラウド/ローカル両対応になり drift しない。

## 6. 集計（Derived）

- **使い捨て計算で R2 → R2**。`:memory:` SQLite（schema 定義を再利用）または DuckDB で R2 観測値を読み、JOIN/集計して R2 に書き出す。
  プロセス終了で計算 DB は消える。compute ロジックは既存（`packages/area-profile/.../run-batch-area-profile.ts` /
  `packages/correlation/.../calculate-pearson.ts`）を **入力=R2・出力=R2** に付け替える。
- **観測値は二度と永続 DB に入れない**（R2 のまま。Phase 6 の肥大=解約の原因を再発させない）。
- **派生も永続しない**（毎回 R2 観測値から再計算可能）。

## 7. リモート/永続 D1 の扱い（廃止）

- **リモート D1 インスタンスは作らない / 残っていれば解約する**（Time Travel 30 日窓の経過後）。
- **ローカル常駐 SQLite を SSOT にしない**。`.local/d1/...` のビルドキャッシュは「再生成可能な使い捨て」に限る。
- schema 定義（`packages/database/src/schema/*.ts`）と integration テスト用 miniflare 設定は **型ソース / テスト基盤として残す**
  （配信 R2 に影響しない。エフェメラル計算の temp table 型にも使う）。

## 8. 禁止事項

| NG | OK |
|---|---|
| 観測値・派生を永続 DB に入れる | R2（観測値）/ エフェメラル計算（派生）→ R2 |
| 設定・運用エンティティを手編集 JSON で散逸させる | git TS を単一ソースにし生成スクリプトで R2 反映 |
| リモート/常駐 D1 を SSOT として再導入する | git TS + R2 + 使い捨て計算 |
| 本番アプリから DB を query する | R2 snapshot 経由（`fetchFromR2AsJson`） |
