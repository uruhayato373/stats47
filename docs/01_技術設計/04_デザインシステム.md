# デザインシステム

stats47 の UI は、統計を迷わず探し、比較し、長時間読める道具として設計する。装飾より情報階層、派手な差別化より一貫性を優先する。

この文書は UI 判断の正典である。実際の class、props、token はコードを正典とし、数値を本書へ二重管理しない。

## 原則

1. **データファースト** — 主要な値、比較、出典へ短い距離で到達できる。
2. **テンプレートを正とする (2026-10-27 オーナー決定)** — 部品・色・角丸・余白はテンプレートに寄せ、独自の部品や値をできるだけ持たない。白基調・角丸なしのカード・細い線・影なし・詰めた余白。チャートは D3 のまま、見た目だけをテンプレートのチャートに合わせる (Recharts は gzip 約 119KB の上乗せになるため使わない)。
3. **一つの意味に一つの表現** — 同じ種類の header、card、rail を feature ごとに作り直さない。既存UIで目的を満たせる場合は、新しいUIを追加せず共通部品を使う。
4. **日本語の可読性** — system font、過度な letter spacing を避け、本文幅と行間を守る。
5. **responsive は情報優先度で決める** — desktop を縮小するだけでなく、mobile の読む順序を設計する。
6. **accessibility は見た目と同格** — heading、focus、contrast、keyboard、reduced motion を後付けにしない。
7. **目的地までの操作を減らす** — 探索用リンクは可能な限り常時表示し、表示領域に収まる一覧へ不要な折りたたみや中間操作を加えない。

### 見た目の 5 原則 (melta-ui 由来)

ブランドパーソナリティは「静謐・精緻・温もり」。melta-ui の 5 原則を stats47 に適応して引き継ぐ。値は現行のトークンとコードを正典とし、旧資料の生パレット色の class 名は引き継がない。

| 原則 | 内容 | stats47 での適用 |
|---|---|---|
| Layered (レイヤー構造) | UI は 3 層で構成する。最下層の地色 (Background)、その上の表層 (Surface)、Surface 上の文字・アイコン (Text/Object) | shadcn の CSS 変数 `--background` / `--card` / `--foreground` がこの 3 層に対応する。light/dark の値は `globals.css` だけが持つ |
| Contrast (コントラスト) | WCAG 2.1 AA に準拠する。通常テキスト (16px 未満) は 4.5:1 以上、大きなテキスト (18px bold または 24px 以上) と UI 要素 (アイコン・ボーダー) は 3:1 以上 | light / dark の両方で確かめる |
| Semantic (セマンティック) | 色は見た目でなく用途で命名する。メインテキスト・本文・補助・ボーダー・成功・警告・エラー | `text-foreground` / `text-body` / `text-muted-foreground` / `border-border` / `positive` / `warning` / `negative` を優先し、生の Tailwind カラーはアクセントや状態表現に限る (「色」節の `no-raw-palette-color`) |
| Minimal (ミニマル) | 1 画面に使う色は最大 3 色 (背景・アクセント・文字)。シャドウは 4 段階だけ (`none` / `shadow-xs` / `shadow-md` / overlay 専用の `shadow-xl`)。カードの hover は影の段を 1 つ上げる遷移に限る | 影の禁止パターンは「禁止パターン」の節 |
| Grid (グリッド) | スペーシングは 4px の倍数、8px を推奨する | ページの余白・列の gap は「レイアウト」の節が正典 |

stats47 固有の判断:

- h1 は `PageHeader` の scale (`text-xl font-semibold`) に統一する。melta-ui の `text-3xl` は採用せず、情報密度を優先する。
- ダッシュボードのカードグリッドはビューポートの `md:` ではなく、コンテナクエリ `@sm` / `@md` / `@lg` を使う (「Responsive」の節)。
- 素の HTML 要素より `@stats47/components` の shadcn ベース部品を優先する (「Component の三層」の節)。
- 色は melta-ui の直接の Tailwind クラスではなく、shadcn の HSL CSS 変数 (`--primary`・`--border` 等) の semantic token を使う。

旧資料の次の値は、現行の正典と食い違うため引き継がない: Layered / Semantic の `bg-gray-50` / `bg-slate-900` / `text-slate-*` / `border-slate-*` / `text-emerald-*` 等の生パレット色の class (意味トークンに置き換えた)、Grid の「カード内 `p-5` 以上・セクション間隔 `mt-10` 以上・ページコンテンツ `px-6 py-8` 以上」(ページの外側の余白は持たず、列の gap・縦の間隔は 16px。「PageShell」の節)、h1 の `text-2xl font-bold` (`PageHeader` へ)。

## ブランドの視覚方針：地域のデータアトラス

stats47 の発行元としての印象は「地域を見つけ、データで確かめ、比較できる」に統一する。地理的な視点と統計の根拠を同時に伝える。都道府県ランキングに加え、テーマ、調査、地域、ブログ、実務向け資料にも通用する方針とし、「47」はサービス名の一部として扱い、対象地域数の上限を示す記号にはしない。

- 識別の核は `stats47` の文字と、**折りたたんだ地図に一地点の注目を示す**簡潔な記号とする。記号は小サイズ用に省略しても同じ輪郭を保つ。正式なベクターと 16/32px の視認性を確かめるまでは、生成画像中のロゴを正式資産として使わない。
- 色の軸は既存の藍・インク色・白に置く。UI の実値は `globals.css` の semantic token、OGP の実値は `apps/web/src/features/ogp/brand.ts` を正典とする。砂色などの暖色は地域を描く補助に限り、順位・増減・危険度などのデータ上の意味をブランド色で上書きしない。
- サイトの通常面は既存の白基調・フラットな設計を守る。地図の折り目や地域風景は、発行元の識別や内容理解を助ける場面に置き、ランキング表・チャート・出典を覆わない。全ページに同じ大きな地図画像を敷かない。
- 実際の地域形状、値、順位を示す図は根拠データから描画する。装飾用の地図風図案は精密な行政界や数値に見せず、統計図として読まれる位置に置かない。
- キャラクターはこの方針の必須要素にしない。発行元名、問い、図、出典の反復で識別を作る。

### 画像への展開

画像種別の寸法・保存先・配信は既存の画像規約を正典とし、見た目は以下の共通原則を適用する。

| 接点 | 共通原則 |
| --- | --- |
| favicon・サイトヘッダー・SNSプロフィール | 同じ記号の骨格を使う。サイトヘッダーと横長画像では `stats47` の文字を併記し、円形トリミングと 16/32px で判読できる省略版を用意する。 |
| サイト内カード・ページ hero | 地域や記事ごとに内容に即した図案を選ぶ。見出し・数値・出典は DOM テキストまたは決定的 renderer で描き、装飾画像に焼き込まない。 |
| OGP・note 表紙・X・Instagram | 一つの問いまたは発見を主題にし、記号・発行元名・藍系の色・文字階層を反復する。媒体ごとの比率と安全域に合わせて再構成し、同一画像の無理な切り抜きで済ませない。 |
| データ地図・チャート | データ、地域名、凡例、単位、期間、出典を保つ。強弱・カテゴリの色は意味を優先し、装飾の地図風図案と明確に区別する。 |

公開資産の切替は、正式記号、favicon、サイトヘッダー、代表的な OGP・note・X・Instagram の実寸試作を一組として見比べた後に行う。現行の favicon（47文字）、ヘッダーの棒グラフ、SNS の円形アイコンは形が異なるため、切替時に同じ版で揃える。画像の詳細な制作・検査契約は `.claude/rules/ogp-image-standards.md` を参照する。

統合用の画像試作 v1 とファイル一覧は `apps/web/public/brand/atlas-v1/manifest.json` に置く。公開 UI への参照変更と SNS プロフィール画像の更新は、この素材群を確認してから媒体ごとに行う。

## レイアウト

### 骨組み (サイドバー型)

骨組みはテンプレートのサイドバー型 (2026-10-27 オーナー決定)。寸法と DOM はコードが正典 (`apps/web/src/app/layout.tsx`・`components/organisms/{AppSidebar,SiteHeader,Footer}`)。

- ルートの `SidebarProvider` の中に `AppSidebar` (variant="inset") と `SidebarInset` を兄弟で置き、`SidebarInset` に `SiteHeader`・ページで唯一の `main#main-content` (余白なし)・`Footer`・Cookie 同意の帯を並べる。lg (1024px) 未満のサイドバーは Sheet。サイドバー部品は Server Component から `AppSidebar/sidebar-shell.tsx` (1 つの client モジュール) 経由で import する。
- サイドバーのヘッダーはテンプレートの full-logo と同じ 2 段 (ロゴ + 名前 + 副題)。主要ナビはサイトの内容の種類 (ランキング・テーマ・地域・地域分析・統計ブログ) だけで常に展開する。テーマのグループを主要ナビの直後に置き、navigation-only SSOT `THEME_NAV_GROUPS` の 5 系統を開閉できる項目 (テンプレートの nav-collapse) として既定で開く。カテゴリのグループはその後に置いて既定で閉じ、件数の札は出さない。調査・地域間比較はサイドバーに置かずフッターから入れる (2026-10-28 オーナー合意・[03_情報設計.md](./03_情報設計.md)「地理スコープ」)。項目はすべてアイコン付き、行の高さはテンプレートと同じ 1 行 40px。下端 (SidebarFooter) は置かない。
- ヘッダーは開閉ボタン・検索欄 (テンプレートと同じ text-sm)・右端のアイコンボタン群 (一覧への出口・配色の切り替え)。フッターは主要な入口数個・サイトの案内・著作表記の 1 段で、導線の一覧を持たない。
- Cookie 同意は `SidebarInset` の最後に置く `sticky bottom-0` の 1 行の帯。浮きカードにしない (本文・地図とテーブルのタブを覆うため)。トースト (sonner) は使わない。
- 部品の lyra スタイルは CSS として読まない。正本 `style-lyra.css` の `cn-*` 規則の中身を部品の className に書き込む (`npm run ui-theme:lyra`、`npm run ui-theme:lyra:test` が pre-commit と PR CI で書き込み漏れを検査。2026-10-28)。同じ見た目をユーティリティと lyra の規則の 2 通りで CSS に出さないため。lyra の値は呼び出し側の className より後ろで合成されて勝つ (CSS で読んでいたときと同じ。上書きは `!`)。

### LeftRailLayout (ページ内ナビ)

ページ内ナビ (旧 左レール) の置き場は `LeftRailLayout` を唯一の実装契約とし、`PageShell` と `ArticleShell` が共有する。

- ページ内ナビは列を作らず、どの幅でも本文の上の 1 か所に出す (2026-10-28。サイト全体のナビはサイドバーが持つので、サイドバーの右にもう 1 本の列を作らない)。幅で隠す分岐や、常に隠す代替 UI は持たない。
- パンくずとページ見出し (h1) は Shell の `header` (ArticleShell は `breadcrumb` と `header`) に渡し、ページ内ナビより先に出す (`check-design-system.mjs` の `left-rail-requires-header-first`)。
- 本文の列は `div[data-slot=shell-main]` で描く。ページで唯一の `<main>` はルートレイアウトの `main#main-content` が持ち、Shell や page は `<main>` を入れ子にしない（`check-design-system.mjs` の `no-nested-main-landmark`）。
- feature はナビの内容だけを所有し、grid、breakpoint、sticky を再定義しない。
- 機械監査は `check-design-system.mjs`、振る舞いは layout contract tests が固定する。

### PageShell

通常の一覧、検索、ダッシュボードは `PageShell` を使う。

- 横幅とレール境界のコンテナは `SHELL_CONTAINER_CLASS`（`@container/shell` + 1280px）が正典。外側の余白は持たない。ルートレイアウトの `main#main-content` も Shell も余白を持たず、本文の格子は外枠 (`SidebarInset`) の線に接する（2026-11-23 オーナー決定。それまでは main の `p-4` で 16px 空けていた）。main の外にある chrome（Footer）は `SHELL_WIDTH_CLASS`（1280px。横の余白は持たない）に自分で `px-4` を足して同じ幅と余白に揃える。
- 右レールは `globals.css` の `rail:`（shell 幅 988px = 本文 672px + 316px。間は余白を空けず 1px の線。2026-11-25 までは gap 16px で本文 656px）で右列に出す。表示境界はこの variant、列幅は `PageShell.tsx` の `RIGHT_RAIL_GRID_CLASS` が単一所有し、`ArticleShell` も共有する。ナビ・広告の出し分けにも `rail:` を使い、画面幅の `lg:` / `xl:` や個別の shell 閾値を書かない。
- `rightRail` は関連情報を主役にし、広告はその後に置く。広告・販促だけの rail で本文を狭めない。
- `leftRail` はそのページの探索・切替に限る。site 全体 nav を複製しない。Theme はグループ別テーマリンク・地域・全指標・出典調査、home / ranking / category はカテゴリ探索に使う。テーマグループは navigation-only SSOT とし、ranking category / ThemeCatalog taxonomy とは分離する。
- `leftRail` と `rightRail` は併用できない。両方渡した場合は右だけを描画する。
- `leftRail` は共有 `LeftRailLayout` を使い、`header` (パンくず + h1) の後・本文の上にどの幅でも出す。
- 右 rail は狭い画面で本文下へ積み、内容を消さない。
- `variant="reading"` は単純な読み物に限る。記事系の標準は `ArticleShell`。
- page 内で独自の `container mx-auto` や別の全体 `max-width` を作らない。

### ArticleShell

blog、ranking detail、survey、規約等の読むページは `ArticleShell` を使う。

- 本文と rail を同じ reading zone に置く。
- rail はページと一緒に流れる。追従する領域や独立した縦 scroll (`max-height` / `overflow-y`) を作らず、ページ本体の scroll だけで全 widget に到達できる自然フローとする。
- 本文と右列は `PageShell` と同じグリッド。レール内も常にグリッドで、狭幅は 1 列、shell 640px 以上は 2 列、`rail:` では 1 列にする。Flex への切り替えを持たず、カード幅を個別指定しない (上揃えの `items-start` が横方向の縮みに変わる事故を防ぐ)。
- 右 rail は 1 回だけ描く。shell コンテナ 988px 未満は本文の後に積み、988px 以上は同じ要素を本文の右の列に置く (2 か所に描いて広告の計測画像・リンクを HTML に二重に出さない)。
- 見出し (h1 と操作の行) を `header` に渡すと、右 rail の先頭が本文の最初のカードと上端を揃える。
- ページ探索用の `leftRail` は `LeftRailLayout` の契約どおり本文の上に置く。左右を同時指定した場合は右 rail を優先する。
- survey の左 rail は「調査一覧・このページ・代表ランキング・関連する分類」に限定する。
  site 全体 nav や全ランキングを常時展開せず、調査の出典ハブとして読む順序を補助する。
- survey の狭幅のナビにも `/survey` の「調査一覧へ」を残し、上位ハブへの出口を失わない。

### PageHeader

標準ページ見出しは `PageHeader` を使う。

- `h1` はページに一つ置き、DOM 上でも主要コンテンツより先にする。
- `description`、`meta`、`stats` は役割を混ぜない。
- `description` はタイトルから推測できない対象範囲・定義・使い方だけを書く。画面を見れば分かる操作説明や、直下の chart と同じ説明は省略する。
- 題名の右に添える操作・短い補助情報は `actions`、操作行は `controls`、補助カラムは `aside` slot を使う。`actions` はモバイルでは題名の下に並ぶ。
- ランキング詳細の h1 は `buildRankingPageTitle` が表示中の指標名と地域粒度から生成する（例: 都道府県別 年間日照時間ランキング）。図表は短い指標名を保つ。最終更新は表示中の `RankingItem.updatedAt` を `RankingHeaderPanel` の `<time>` で一度だけ表示し、欠損・不正な日付は省略する。データの対象年は可視化の年度選択に置く。配線・重複は `ranking-header-density-contract.test.ts`、画面幅ごとの配置は `ranking-controls.spec.ts` で検査する。
- header 本体を暗色 gradient や巨大 KPI 面にしない。
- feature 固有 header が必要な場合も、既存 header component を拡張または合成し、新しい hero 系統を増やさない。

## レール UI 契約

左右レールは配置・幅・sticky・responsive 非表示が異なっても、Surface・見出し・リンク行の視覚契約は共通とする。部品は `apps/web/src/components/surface/SurfaceCard.tsx` の `RailCard` / `RailNavRow` / `RailNavRowButton` と `apps/web/src/components/rail/{RailStack,RailCategoryList,RailLinksCard}.tsx` に集約する。

### 左右共通

- レール内の独立したまとまりは `RailCard` 1 枚 = 通常カードと同じ `CARD_SURFACE_CLASS`（角丸・線色はトークン）。見出し `h3` は `text-sm font-medium text-muted-foreground`（`border-b px-4 py-3`）、本文は `px-4 pb-4 pt-3`。折りたたみは `RailCard collapsible`（details/summary、summary `min-h-12`）。
- カード間の縦積みは `RailStack`（`flex flex-col gap-3`）だけを使う。`page.tsx` で `<aside>` を自前で描かない。landmark は `PageShell` / `ArticleShell` / `LeftRailLayout` が持つ。

### リンク行

- リンク行は `RailNavRow`（Link）/ `RailNavRowButton`（`aria-pressed`）。透明背景、寸法は `LINK_ROW_SIZE_CLASS` の 1 種類（`text-sm p-2 min-h-11 sm:min-h-10`。左右の余白 8px は `-mx-2` で外へ出し、文字の左端をカード本文の端にそろえる。密度の切り替えは持たない）、`hover:bg-accent/50`、`focus-visible:ring-2 ring-inset`、右矢印、件数は `tabular-nums`。
- active は `aria-current="page"` + `bg-accent font-semibold text-primary`。カラーバー（inset shadow / `border-l`）で示さない。
- 末尾リンクは `text-xs font-medium text-primary hover:underline`（モバイル `min-h-11`）。

### 左右で異なってよいもの

- **基本の文字:** 見本は Geist 16px。stats47 は日本語の可読性を優先して system の和文書体のまま (Typography の節)。
- **進め方:** 部品の種類ごとに 1 つずつ作り直し、見本と stats47 を同じ方法で測り直して差を確かめる。作り直した部品には、ページの側で上書きできないよう `design-system:check` の規則を同時に足す (例: パネルの題名の大きさ・余白の上書き、補足のパネル外への配置、パネルを並べる格子の `gap-4`)。

## Surface

共有 surface は `SurfaceCard`、`SurfaceSection`、`SurfaceLinkCard` と primitive `Card` を基底にする。

共通の節見出し `SectionHeader` は h2 を `text-base`、小見出し h3 を `text-sm` にし、太さはともに `font-semibold` とする。HTML の階層と見た目を同じ部品で決め、ページ側の文字サイズ上書きは加えない。

- Surface は 3 段階で管理する: ページ `bg-background` / カード `bg-card` / hover・選択中・補助要素（タグピル・バッジ・サムネ地）だけ `bg-muted` または `bg-accent`。
- 通常の行・リンク群に理由なく `bg-muted` を使わない（詳細は「レール UI 契約」）。
- カード外枠の単一定義は `CARD_SURFACE_CLASS`（`packages/components/src/atoms/ui/card.tsx`）。primitive `Card` と `SurfaceCard` / `SurfaceSection` / `SurfaceLinkCard` / `RailCard` / `ArticleCard` はすべてこれを合成し、外枠クラスを別に書かない。
- 外枠の見た目はアプリごとのトークンで決める: 角丸 `--card-radius`（`rounded-card`）、線色 `--card-outline`（`border-card-outline`）。Web は角丸 0・線 `--border` (テンプレートの lyra カードと同じ白地・細い線・影なし。2026-10-27 に 2026-09-25 の「線なし・薄グレー地」から変更)。ページ地 (`--background`) もテンプレートの白で、記事ゾーンを含めサイト全体で 1 値。管理画面は `--card-outline: hsl(var(--border))` で線ありの角丸カード。border 幅は残るので、レイアウトと interactive card の hover 枠色 (`hover:border-primary/40`) が保たれる。表・グリッド・入力欄・ボタンの線は残す。
- 角丸はクラスを役割で選び、値はトークンで決める: カード外枠・その仮表示・地図/チャート枠は `rounded-card`、ボタン・ドロップダウンは `rounded-md`、カード内の小タイル・バッジ・サムネは `rounded-sm`（`--radius`。値はテンプレートの 0.625rem。部品自体の角は lyra スタイルがほぼ `rounded-none` で決める）。形として四角であるべきもの（凡例の色見本、タイル地図のマス、下線タブ、一覧行）だけ `rounded-none`、円形 icon・avatar・pill だけ `rounded-full`。`cn` は `rounded-card` / `rounded-content` を角丸として解決する（`packages/components/src/lib/cn.ts`）。
- **本文の中に置く部品は `rounded-content`（`--content-radius`、Web は 6px。2026-09-25 採択）**。ページを区切るカード外枠（レイアウト）と、記事本文の中に置くまとまり（callout・本文内のランキングカード・コードブロック）は役割が別なので、別トークンにする。レイアウトはフラットのまま、本文内の部品だけ少し丸めて「本文の一部」と分かるようにする。本文内の部品は白いカードを重ねず（カード内カード禁止）、地の色で区切る。
  - `--content-radius` は `:root` に 1 か所だけ定義する（ページ種別ごとに上書きしない）。
  - `rounded-content` を使えるのは本文を描く部品のファイルだけで、そのファイルでは `rounded-card` / `rounded-lg` を使わない。対象ファイルの一覧は `check-design-system.mjs` の `ARTICLE_BODY_COMPONENT_FILES`。本文内に部品を足したらこの一覧へ足す。
  - callout（`> [!NOTE]` 等）はアイコン + 日本語ラベル（補足 / 読み解きのポイント / 注意 / 重要 / 要注意）の 1 行と本文で組み、左の色バーは使わない。種類ごとのラベル・色・優先度の単一定義は `apps/web/src/features/blog/components/callout-config.ts`、表示は `Callout.tsx`。
- clickable card は card 全体の click target、focus-visible、hover を一致させる。
- 色付きの順位チップ（「N位」）は `RankBadge`（`apps/web/src/components/atoms/RankBadge.tsx`）で描く。幅は固定せず最小幅 4em で揃え、折り返さない。色は意味の `tone`（`positive` / `negative`、向きのない順位は `rankToneByPosition`）。表のセル・補足の文字・文章中の「N位」は文字のまま書く。機械ゲートは `design-system:check` の `rank-chip-must-use-rank-badge`。
- portal card の縦横比は `PORTAL_CARD_ASPECT_CLASS` を使う。
- feature 内で border / shadow / padding をまとめた独自 card shell を複製しない。
- card / section surface の内側に別の card surface を置かない。まとまりが必要なら外側を通常の `section`、内側を区切り線付き list / table にする。
- 商品詳細 LP は本文全体を 1 つの `SurfaceSection` にまとめ、内容・用途・作例・ファイル見本は見出しと余白で区切る。説明文だけのパネルや節ごとの枠は増やさない。用途は項目名と説明を続けた箇条書き、図は「作成例」の h2 と用途別の h3 でまとめ、見出しを言い換えただけの導入文は置かない。上下の購入案内は `ProductPurchase` を共用し、末尾のみ台帳の表紙を添える。図／ファイル見本の種別・訴求文・作成方法は商品台帳に持つ。3商品種別 × 4画面幅で `responsive-layout.spec.ts` が枠数・余白・末尾導線を検査する。
- 作成例とファイル見本の掲載幅は共通 `ProductShowcase` がコンテナ幅に応じて1列／2列に決め、画像が1枚の節でも複数枚の節と同じ幅にする。1枚の作成例は説明ごと横に並べ、複数枚の節は両列を使って同じ幅の画像を並べる。元画像の縦横比を維持し、商品別・枚数別の画像拡大分岐を設けない。`responsive-layout.spec.ts` が単画像／複数画像の商品間で掲載幅・列間隔・縦横比を比較する。

### 色

- `background` / `foreground` / `muted` / `border` / `primary` 等の semantic token を使う。
- データの状態は状態トークンで表す: `positive`（上位・良い値）/ `negative`（下位・悪い値）/ `warning`（注意）/ `info`（補足）。各 `DEFAULT` は文字・線、`-soft` は淡い地。light/dark の値は `globals.css` だけが持つ。
- category や chart series の色は意味の識別に使い、装飾的なカラーバーを増やさない。カテゴリ・地域・性別・メダル・SNS ブランドなど識別のための配色は `*.palette.ts` モジュールに集め、そこだけで Tailwind の生パレット色を使う。
- 生パレット色（`slate-500` / `emerald-600` 等）を UI に直書きしない。`npm run design-system:check -w apps/web` の `no-raw-palette-color` が apps/web と packages/components・packages/visualization を検査する。`black` も使わない。
- positive / negative の色だけで意味を伝えず、label、symbol、値を併用する。

### カラーモード（light / dark）

- 既定は light。dark は利用者が明示的に選ぶ opt-in とし、OS 設定へ自動追従しない。
- 選択状態は `next-themes` が保持する。実装の正典は `apps/web/src/providers/theme-provider.tsx`。
- component は両 mode の semantic token と contrast を確認する。
- mode 別画像が必要な場合は `ThemeAwareImage` 等の既存 component を使い、同じ画像を二重表示しない。

### Typography

- 本文は system font stack を使い、Web font を表示の必須依存にしない。
- 通常ページの `h1` は既存 `PageHeader` の scale に合わせる。
- `h2` / `h3` は見た目ではなく文書構造で選ぶ。
- 数値表では桁、単位、小数点の比較しやすさを優先する。
- `tracking-tight` 等、日本語の可読性を落とす指定を避ける。

## Component の三層

| tier              | 配置                                          | 例                                | ルール                                        |
| ----------------- | --------------------------------------------- | --------------------------------- | --------------------------------------------- |
| Primitive         | `packages/components/src/`                    | Button、Card、Select、Table       | 先に既存 primitive を探す                     |
| Shared composite  | `apps/web/src/components/`                    | PageShell、SurfaceCard、StatTile | 複数 feature で使う UI                        |
| Feature component | `apps/web/src/features/<feature>/components/` | ranking header、theme section     | feature 固有。別 feature から直 import しない |

同じ UI が二つ以上の feature で必要になったら shared composite への昇格を検討する。将来使うかもしれないという理由だけで抽象化しない。

### 本文コンテンツの開閉 UI

- FAQ は共有 `FaqSection`、統計の定義・AI考察など単一本文は共有 `ContentDisclosure`（`apps/web/src/components/content/`）を使う。feature ごとに Accordion や三角文字を再実装しない。
- 操作は native `details/summary` を基底とし、閉じた本文も SSR DOM に保持する。見出し・質問・本文は 14px（見出し・質問は 500、本文は normal。2026-10-28 に見本の accordion に合わせた）、上下の余白 10px、操作高 44px 以上、状態表示は 12px の細線 + / − に統一する。
- hover / tooltip は補助説明に限り、開閉や主要導線を hover のみに依存させない。ナビゲーション用の `details` は本文開閉と責務が異なるため、この部品へ無理に統合しない。

## ページ別の契約

### Home

- 白基調のポータルとして、主要な探索入口を短く提示する。
- 暗色の巨大 hero を既定へ戻さない。
- category、ranking、area、blog の優先順位は `apps/web/src/features/home-portal/README.md` に従う。

### Ranking

- ranking detail は既存の `RankingHeader/` 系を使う。
- `h1`、操作、統計、地図、table の順序は mobile / desktop の利用目的を踏まえて既存 feature contract に揃える。
- mobile では主要可視化へ早く到達できるようにする一方、`h1` は DOM 先頭を維持する。
- 一位だけを巨大な暗色 KPI 面で特別扱いせず、上位、最下位、全国値を通常 surface で比較できるようにする。

### Theme / Area

- 商品への案内は、商品台帳の作成例が参照するテーマの章の末尾に、共通 `ThemeProductLinks` で表示する。同一商品は章内で1件にまとめる。LPは各作成例から同じテーマの章へ戻れるリンクを持つ。見出しと関係は台帳から生成し、販売版・改訂案の選択を両ページで揃える。

- Theme は複数指標の意味的な順序、Area は一地域の特徴を主語にする。
- chart の配置は [`03_情報設計.md`](./03_情報設計.md) と ThemeCatalog / page_components の定義に従う。
- Theme の左 rail はグループ別テーマリンク、地域、全指標、出典調査をこの順で整理する。テーマと出典調査には `/themes`・`/survey` の上位ハブリンクを1件ずつ置く。現在テーマのグループだけ初期展開し、現在リンクを明示する。
- 地域では「比較単位（47都道府県 / 市区町村 / 日本）」と「表示する都道府県」を別の操作として示す。比較単位は共有 `StatisticsScopeNav` の rail variant、都道府県は `PrefectureSelect` を使い、リンクや状態定義を複製しない。
- 狭幅では左 rail を隠し、共有 `StatisticsScopeNav` の横タブ・テーマ Select・地域・ページ内クイックリンク・全指標・出典調査を本文上部へ置く。同じ操作を同時表示しない。
- Theme / Japan / Municipality の地理スコープ切替には共有 `StatisticsScopeNav` を使う。
- 関連情報が無い dashboard / hub は全幅とし、広告だけの right rail を作らない。

#### 選択 UI と集合レイアウトの件数規則

- 選択 UI（checkbox・tab・選択タイル・横に並ぶ選択の列）は、フィルタ後に有効な選択肢が 2 件以上あるときだけ表示する。0 件はセクションごと非表示、1 件は選択 UI を出さず指標名・値・単位・年次・順位・ランキング導線を直接並べる。外せない checked 状態や、カード見出しと唯一の選択肢ラベルの重複を作らない。
- 集合レイアウト（指標カードの grid）は 0 件で wrapper を描かず、1 件でも複数列 grid wrapper を作らない。2 件以上のときだけ container query の grid（`grid grid-cols-1 gap-4 @md:grid-cols-2`）で包む。desktop の compact card は複数あるときだけ 2 列、mobile は常に 1 列。詳細チャート・複数指標切替パネル・固定年比較は全幅を維持する。
- 単一指標の推移は、都道府県選択時に異なる年が 2 件以上あるときだけ小さな折れ線（`MiniLineChart`、84px）を描く。単年は自然高の 1 行テキストにし、空の折れ線枠・ローディング風の大面積・「時系列データがありません」だけの固定高領域を置かない。
- 時系列データの取得は指標 1 件分の遅延取得（自地域 + 全国）を再利用し、47 都道府県一覧表示のための一括取得へ戻さない。

### Blog / Survey / 規約

- `ArticleShell` と reading zone を使う。
- 本文、出典、図表、CTA、rail の優先度を分ける。
- 記事 card 内へ別の大きな card shell を重ねない。

## Chart と table

- 新規 chart の前に既存 catalog を確認する。
- title、unit、period、source、legend を chart 単体でも理解できるようにする。
- title・凡例・軸から自明な reader description (「線の傾きを確認できます」等の componentType 由来の定型文) を自動生成せず、title の下へ出さない。Theme chart header は短い title に絞る。
- 系列断絶、母集団差、比較不能条件など chart 固有の誤読防止条件だけを近接 footer の `annotation` に置く。
- 指標の定義・算出方法・一般注釈は `/ranking/[key]` の指標ハブへ集約し、chart からリンクする。
- 指標の選定理由や内部 provenance (ThemeCatalog の内部 selection rationale) は reader UI へそのまま露出せず、SSOT に保持する。指標一般の定義・算出方法を chart ごとの annotation へ複製しない。
- loading、empty、partial、error を同じ表示にしない。
- color scale と axis は指標間で意味が変わる場合に使い回さない。
- table は header scope、数値 alignment、mobile overflow、sort state を確認する。
- visualization を decoration として置かず、ページの問いへ答えるものだけを置く。

## page_components の設計契約

永続 DB は使わない。ページコンポーネントの正典と配信経路は次のとおり。ThemeCatalog の編集手順・チャート選定文法は `.claude/rules/theme-catalog-standards.md`、データの置き場は `.claude/rules/data-storage.md` が正典である。

| 対象 | SSOT | 生成物 / 配信 |
|---|---|---|
| Theme | `data/themes/catalogs/<key>.json` (ThemeCatalog) | `apps/web/scripts/data/page-components/theme/<key>.json` → R2 |
| Area / Area category / City category | `apps/web/scripts/data/page-components/<pageType>/<key>.json` | 同一 byte を R2 へ配信 |
| Area databook | `packages/data-configs/src/area-databook/` | area page-components JSON → R2 |

Theme の生成済み JSON は手編集しない。編集後は `npm run generate:catalog --workspace=@stats47/data-configs` と `npm run validate:catalog --workspace=@stats47/data-configs` を実行する。R2 反映は `apps/web/scripts/export-page-components-snapshot.ts` が担当する。

### PageComponent contract

各行は少なくとも次を持つ。

| field | 用途 |
|---|---|
| `componentKey` / `componentType` | 一意な識別子と描画型 |
| `title` | 可視化の短い見出し |
| `description` | 互換用の任意補足。Theme chart header では表示しない |
| `componentProps` | statsDataId、系列、ラベル、色 role、任意 `annotation` 等 |
| `sourceName` / `sourceLink` | 出典 |
| `rankingLink` | 対応する単一指標ランキング |
| `gridColumnSpan*` | レスポンシブ配置 |
| `section` / `sortOrder` | グループと表示順 |

ThemeCatalog は `charts.description` / `charts.rankingLink` を持たない。component type 由来の定型文は生成せず、生成済み Theme PageComponent の `description` は互換用に `null` とする。誤読防止に不可欠なチャート固有条件だけを `charts.annotation` に書き、generator が `componentProps.annotation` へ出力する。指標の定義・算出方法・一般注釈は `/ranking/[key]` の指標ハブを正典とし、`relatedRankingKeys` で接続する。generator は先頭 key を `rankingLink`、残りを `rankingLinks` へ変換する。`metrics.selection.rationale` は内部 provenance であり、読者 UI に表示しない。

### pageType の責務

配置判断の正典は [03_情報設計.md](./03_情報設計.md)。

| pageType | 置く情報 | 置かない情報 |
|---|---|---|
| `theme` | 47都道府県横断でテーマを説明する指標・関係 | 一県だけの事情、公式全国値だけの chart |
| `area` | 一地域のプロフィール、他地域との差 | 全国テーマの一般説明だけの chart |
| `area-category` | 地域 × 統計分類として意味がある比較 | 全国値の無条件な複製 |
| `city-category` | 市区町村の統計主体・定義で成立する比較 | 都道府県用 statsDataId の流用 |

市区町村と都道府県は entity と statsDataId が異なる。サービス層で暗黙変換せず、各カタログ / pageType が正しい参照を持つ。日本の公式全国値は `/japan/*` の別契約で扱い、47県平均を page-components から全国値として作らない。

### 1データ1コンポーネント

同じ統計・同じ entity・同じ表現は既存 component を再利用する。ページごとに chart key、chart type、色、ラベルを複製しない。ただし地理粒度や統計主体が異なる場合は別定義にする。

### 読者向け表示契約

各 `ChartPanel` は次を近接して表示する。

1. title
2. chart / legend / axis
3. 年度・単位・出典
4. 存在する場合だけ chart 固有 annotation
5. 対応する指標ハブへの link

ページ header に全 chart の説明をまとめたり、ページ末尾だけに出典を集約したりしない。同じ事実を KPI card と chart で二度強調せず、値・比較・推移・構成の役割を分ける。reader description の自動生成の禁止と、指標の定義・内部 provenance の置き場は「Chart と table」の節にまとめている。

### 色

ThemeCatalog は `chart-color-role.ts` の role を持ち、generator が配信用の色へ解決する。ThemeCatalog の色 field に生の hex / rgb / hsl を書かない。性別等の意味色と可読性は `.claude/rules/chart-component-standards.md` に従う。

- `generate:catalog --check`: ThemeCatalog と生成物の drift
- `validate:catalog`: key、props、全 data-bound component の link coverage、annotation、旧定型 description、evidence の整合
- `apps/web/scripts/check-design-system.mjs`: layout / focus / surface の禁止パターン
- `npm run type-check --workspace apps/web`: reader 型と renderer の整合

### page_components の禁止事項

- 永続 D1 / table を page-components の SSOT とする。
- Theme の生成済み JSON を手編集する。
- page / component 内へ chart 定義をハードコードする。
- ThemeCatalog に `description` / `rankingLink` を二重管理する。
- 47県 chart を市区町村・日本へ無条件に複製する。

## データ出典

出典の表示は3層に分け、層ごとに部品を1つに固定する (2026-09-25)。

| 層 | 部品 | 役割 |
|---|---|---|
| ページ全体の出典 | `DataSourceList` (`apps/web/src/components/molecules/DataSourceList.tsx`) | ページ末尾の「データ出典」。ブログ記事・ランキング・市区町村ランキング・Geo レイヤー |
| 図ごとの出典 | `ChartFooter` + `SourcesSheet` | テーマのダッシュボードは図の周りに文章を置かず、パネルの見出しの右端のアイコン (`ChartFooter placement="header"`) から開く Sheet の先頭に誤読を防ぐ注記を入れる (注記があればアイコンに点の印。2026-11-01 オーナー決定)。それ以外の図は、図の直下は誤読を防ぐ注記と「出典・指標の定義」のボタン 1 つ。出典・指標の定義・ランキングへのリンクはボタンから開く右の Sheet にまとめる (2026-10-30 オーナー決定。旧: 短い出典リンクと件数付きのメニュー)。テーマの数値タイルは右上の本のアイコンから同じ Sheet を開く。ランキングのページの出典の節とブログ本文の出典は本文なので Sheet にしない。テーマ・エリア・stat-charts |
| 調査ハブへの回遊 | `SurveyTaxonomyCard` | 右レール等の「この記事の出典調査」。出典の表記ではなく導線 |

- 1 行は「調査名 (サイト内の `/survey/<id>` へ)・(機関)・[統計表 ↗] (e-Stat 等の実データ表)」。
  調査ではないデータセットは名前を外部ページへリンクし、ライセンスがあれば行末に出す。
  地図の行政区域データのような補助データは `note` (例: 「地図データ:」) を付けて同じ一覧に並べる。
- 行はデータ (`DataSourceEntry`) から派生させる。ブログは図の `source.json`、ランキングは `item.json` の
  `sourceConfig` と `attribution` が入力で、解決は `@stats47/ranking` の `resolve*DataSources` だけが行う。
  画面側で出典の文字列や e-Stat の URL を組み立てない (`buildEstatTableUrl` だけが URL を作る)。
- 原典調査の名前・機関・URL は JSON 台帳 `surveys.master`、指標との対応は既存の出典辞書が持つ。
  調査ではない編成統計・地図の共通出典は `provenance.reference-sources` が持ち、
  `getReferenceDataSource(id)` で読む。調査マスタへ擬似調査を追加したり、画面へ名前・URL を直書きしない。
- ランキングの地図・表の下には集計条件だけを置き、最終更新はページ見出し、出典はページの一覧に集約する。集計条件がなければ補足の線と余白も描かない。
  `DataSourceList` 自身は上側の線・余白を持たず、区画の間隔は親レイアウトに任せる (2026-11-11)。
- ブログ本文に手書きの「データ出典」節を書かない。計算方法や定義の説明は「データについて」節に書く。
- 機械ゲート: `apps/web/src/__tests__/data-source-contract.test.ts` (「データ出典」見出しは `DataSourceList` だけ・
  e-Stat URL・共通出典の直書き禁止・可視化直下での重複出典禁止・旧 `item.source` 参照禁止)、
  `ranking-controls.spec.ts` (画面幅ごとの出典一意性・余白・横はみ出し)、`quality-gate.mjs` (記事の手書き節を blocker)、
  週次のタクソノミー監査 (手書き節・出典 0 件・未焼き込みの件数)、ページ品質監査
  (`duplicate_data_source_sections`)。

## 禁止パターン

上の「禁止事項」がページ構造の禁止、本節が class・部品の水準の禁止パターンの正規版 (SSOT) である。他の文書・agent・skill・検査の文言はここを参照する。出典は melta-ui の `foundations/prohibited.md` を stats47 に合わせたもの。機械検査は `npm run design-system:check -w apps/web` (`apps/web/scripts/check-design-system.mjs`)。

### カラー

| 禁止 | 理由 | 代替 |
|---|---|---|
| `text-black` | 純黒はコントラストが強すぎて長時間の利用で目が疲れる | `text-foreground` |
| 生パレット色の直書き (`text-slate-500` / `bg-emerald-50` 等) | light/dark と配色変更に追従しない。`no-raw-palette-color` が拒否する | 意味トークン (`foreground` / `muted-foreground` / `border` / `positive` / `negative` / `warning` / `info` と各 `-soft`)。カテゴリ・性別・メダル等の識別配色だけ `*.palette.ts` に集める |
| `bg-gray-300` 以上の暗い背景 | テキストのコントラスト確保が困難になる | semantic token `bg-muted` / `bg-accent` (hover・選択中・補助要素のみ。「レール UI 契約」) |
| `bg-primary-400` (薄いアクセント) | CTA として弱く、目立たない | `bg-primary` |
| 本文への `text-gray-400` | WCAG 不適合 (コントラスト比不足) | `text-muted-foreground` |
| `border-gray-100` | 薄すぎて境界が見えない | `border-border` |
| 状態を生の緑・黄・赤で表す | 配色変更と dark に追従しない | `positive` / `warning` / `negative` (`-soft` は淡い地) |
| リンクへの `text-blue-*` | primary で統一する | `text-primary` |
| 色だけで情報を伝える | 色覚多様性への非対応。アクセシビリティ違反 | アイコン・テキストを必ず併用する |

### モーション

| 禁止 | 理由 | 代替 |
|---|---|---|
| 過剰なアニメーション (常時ループ等) | 操作の邪魔になり、認知コストを増やす | 150〜300ms の状態変化フィードバックに限る |
| `duration-500` 以上 | 操作が鈍く感じる (Progress のフィルバーは例外) | `duration-300` 以下 |
| `prefers-reduced-motion` の無視 | アクセシビリティ違反 | メディアクエリで対応する |
| 装飾的なアニメーションの多用 | 動きに敏感な利用者への配慮不足 | 状態変化のフィードバックだけ |

### タイポグラフィ

| 禁止 | 理由 | 代替 |
|---|---|---|
| `tracking-tight` | 日本語の可読性が低下する | `tracking-normal` 以上 |
| 本文への `text-xs` | 小さすぎて読みづらい | `text-base` (16px) |
| `font-light` (300) | 細すぎて可読性が低い | `font-normal` (400) 以上 |
| プレースホルダーだけでラベルを省略 | 入力開始で消え、目的がわからなくなる | `<label>` を必ず使う |

### スペーシング・レイアウト

| 禁止 | 理由 | 代替 |
|---|---|---|
| カードへの個別角丸 (`rounded-xl` / `rounded-2xl` 等)、ナビ・ボタンへの手動角丸 | フラット (`--radius: 0`) の統一を崩す | `rounded-card` (= 0)。本文内の部品は `rounded-content`。円形だけ `rounded-full` |
| callout・注記の左の色バー (`border-l-4`) | 4px のアクセントバーは禁止。種類を色だけに頼らない | 地の色 + アイコン + 日本語ラベル (`Callout.tsx`)。例外は下の「AI 生成パターンの排除」 |
| `shadow-lg` / `shadow-2xl` | 影が強すぎてノイズになる | `shadow-xs` 〜 `shadow-md` (オーバーレイは `shadow-xl`) |
| ボタンの `py-0.5` | タップターゲットが小さすぎる | `h-8` 以上 (S: `h-8` / M: `h-10` / L: `h-12`) |
| カードの `p-0` | コンテンツが窮屈になる | `RailCard` 既定の padding (`px-4 pb-4 pt-3`)。「レール UI 契約」 |
| セクション間の `gap-0` | セクションの区切りが不明瞭 | `gap-6` 以上 |
| ページコンテンツの `m-0` | ページ端にコンテンツが張り付く | Shell の余白契約に従う |
| ナビアイコンの `w-7 h-7` 以上 | DS 標準のアイコンサイズからの逸脱 | `w-5 h-5` |
| Drawer のフォーカストラップ省略 | キーボード利用者が背面要素を操作してしまう | フォーカストラップを実装する |
| `aria-current="page"` の省略 | スクリーンリーダーが現在ページを識別できない | Active のナビ項目に必ず付ける |
| ページ幅・レール幅のページ内直書き、独自グリッドでの多カラム直書き | ページ間で幅がばらつく温床 | `PageShell` / `ArticleShell` の共有契約を使う |
| `AppSidebar` の右にページ内ナビの 2 本目の列を作る | サイト全体のナビ (サイドバー) と列が二重になる | ページ内ナビは `leftRail` に渡し本文の上に置く (「LeftRailLayout」の条件) |

ページ内ナビ (旧 左レール) の例外の条件は、(1) 中身はそのページを操作するナビだけでグローバルナビを複製しない、(2) 列を作らずどの幅でも本文の上に置く (`no-retired-left-rail-narrow-api`)、(3) パンくずと h1 を先に出す (`left-rail-requires-header-first`)、(4) 現在地に `aria-current="page"` を付ける。survey の「このページ」と関連分類、`/areas` の地方の切替が該当する。

### AI 生成パターンの排除

AI (LLM) が UI を生成するときに頻出する「それっぽい」装飾パターンを禁止する。

| 禁止 | 理由 | 代替 |
|---|---|---|
| カード上部・左部のカラーバー (`border-t-4` や色付き `div`) | AI 生成 UI の典型パターン。装飾過剰で汎用性が低い | 共通カード (`SurfaceCard` 系 / `CARD_SURFACE_CLASS`) で構成し、装飾バーを足さない |
| 左端・上端のカラーストライプ (`border-l-4 border-*-500`) | Alert を含む全部品で禁止 | 全周ボーダー |

正式な例外 (2026-07-11・機械検査 `no-thick-accent-border` の allowlist と同期): Markdown 散文中の blockquote の引用バー (`md-content.tsx`) と callout admonition の左バー (`md-preprocessor.ts`) だけ `border-l-4` を許容する。引用・注記の一般的な typography であり、減衰色 (`border-primary/30` 等) で使う。カード・パネル・Alert への適用は引き続き禁止。

### Card

| 禁止 | 理由 | 代替 |
|---|---|---|
| `CardContent className="...pt-0"` | `CardHeader` の `border-b` 直下に内容が貼り付き窮屈に見える | `pt-3` を維持する (Card の既定。`p-4 pt-3` 相当) |
| `CardContent` の上 padding の独自値での上書き | サイト全体でカードの余白が不揃いになる | 既定の `pt-3` を尊重する。変えるなら `pt-2` (8px) か `pt-4` (16px) を意図とともにコメントで明示する |
| カード・section surface の内側の別カード | 境界線・影・padding が二重になり情報密度が落ちる | 外側を通常の `section`、または内側を区切り線付きの list / table / link row にする |

経緯: 2026-05-27 に apps/web 内 29 箇所の `CardContent ... pt-0` を一括で `pt-3` に修正した (`CardHeader` の下線直下の余白が 0px になる問題)。違反の検知は `grep -rn 'CardContent[^>]*pt-0' apps/web/src --include='*.tsx'` が 0 件であること。

### ボタン

| 禁止 | 理由 | 代替 |
|---|---|---|
| 同一スタイルのボタンの並列配置 | 重要度の区別がつかない (Neutral のみ例外) | 階層の異なるボタンを組み合わせる |
| `aria-label` のないアイコンボタン | 操作内容がスクリーンリーダーに伝わらない | `aria-label="閉じる"` 等を付ける |
| 44px 未満のタップ領域 | 操作が難しい (インラインのテキストリンクを除く) | パディングでタップ領域を確保する |
| ボタンへのシャドウ | ボタンにシャドウは不要 | シャドウなし |

### フォーム

| 禁止 | 理由 | 代替 |
|---|---|---|
| `<select>` の `appearance-none` 省略 | ネイティブ矢印はブラウザ間で不安定 | `appearance-none` + カスタム SVG シェブロン |
| ラベルなしのフォーム入力 | スクリーンリーダーが目的を読み上げられない | `<label>` を `for` 属性で関連付ける |
| ラベルの横配置 | モバイルで破綻し、視線移動が増える | ラベルは入力欄の上 |
| エラーメッセージの自動非表示 | 利用者が読む前に消える | 修正されるまで表示する |
| 色だけでのエラー状態の伝達 | 色覚多様性への非対応 | ボーダー色 + エラーアイコン + テキスト |
| カード直下の `<fieldset>` + `<legend>` | `<legend>` のブラウザ既定の描画がカードの `border` と干渉する | `<div>` + `<h2>` を使う |
| チェックだけで確定する設計 | 意図しない確定が起きる | 確認ボタンを必ず置く |
| 入力途中の自動フォーカス移動 | 利用者を混乱させる | 利用者の操作に任せる |
| 離れた位置のエラー表示 | フィールドとの対応がわからない | フィールド直下に表示する |

### モーダル

| 禁止 | 理由 | 代替 |
|---|---|---|
| フォーカストラップなしのモーダル | キーボード利用者がモーダルの外へ出てしまう | Tab / Shift+Tab がモーダル内を循環する |
| Esc キーで閉じられないモーダル | 利用者が脱出できない | Esc キーで閉じる |
| `role="dialog"` の省略 | スクリーンリーダーがモーダルを認識できない | 必ず付ける |
| オーバーレイなしのモーダル | 背景との分離が不明確 | `bg-black/50` のオーバーレイ |
| 2 階層以上のモーダルのネスト | UX が複雑になりすぎる | 設計を見直す |

### テーブル

| 禁止 | 理由 | 代替 |
|---|---|---|
| レイアウト目的の `<table>` | セマンティクス違反 | `flex` / `grid` を使う |
| `<th>` の `scope` 省略 | ヘッダーとデータの関係が不明確 | `scope="col"` を付ける |

### ディバイダー

| 禁止 | 理由 | 代替 |
|---|---|---|
| `<div>` + `border-b` での水平区切り | セマンティクス違反 | `<hr>` または `role="separator"` |
| `border-slate-400` 以上の区切り線 | 線が強すぎてノイズになる | `border-border` (標準)。薄すぎる `border-gray-100` も使わない (「カラー」の表) |

### スケルトン・ローディング

| 禁止 | 理由 | 代替 |
|---|---|---|
| スケルトンに `bg-muted` 以外の色 (旧資料の記述は `bg-slate-200`) | DS の統一から外れる | `bg-muted` (`Skeleton` 部品) |
| `aria-busy="true"` の省略 | スクリーンリーダーがローディング状態を認識できない | コンテナに `aria-busy="true"` + `role="status"` |

### アクセシビリティ (全般)

| 禁止 | 理由 | 代替 |
|---|---|---|
| ring なしの `outline: none` | フォーカスインジケーターが消える | `focus:ring-2 focus:ring-primary/50` |
| `tabindex` > 0 | フォーカス順序が混乱する | DOM 順に従い、`tabindex="0"` または `-1` だけを使う |
| 時間制限のある操作 | 利用者が操作を完了できない可能性 | 時間制限を設けない |

### stats47 固有の注記

- shadcn/ui ベースの部品 (`packages/components/src/`) 内の `tracking-tight` / `shadow-lg` はライブラリの既定として許容する。
- アプリケーションコード (`apps/web/src/`) では上記の禁止パターンを厳守する。
- `text-muted-foreground` / `border-border` 等の shadcn CSS 変数は semantic color として許容する。

## UI 変更時の確認

1. 既存 primitive / shared component で実現できないか。
2. PageShell / ArticleShell / PageHeader のどれに従うか。
3. mobile の DOM 順、keyboard、focus、contrast が成立するか。
4. loading、empty、error、long text、最大値で崩れないか。
5. chart と page_components の既存契約を再利用したか。
6. 変更前後を同じ viewport で目視し、意図しない UI 差分がないか。
7. UI 変更でない作業では class、DOM、asset を変更しない。

### ランキングの相関一覧

- 選定は `data/correlation/selection-policy.json` が所有し、正負それぞれ最大10件を生成時に確定する。画面は `groups.positive/negative` をそのまま共通 `ValueTable` の「指標・順位相関」2列で表示する。解説記事の列・リンク・取得は持たない。
- 部品の幅が共通 `@md` (768px) 以上なら正負を左右、それ未満は上下に並べる。片方だけなら1列、両方空なら節ごと省略する。件数をそろえるために空行や追加指標を作らない。
- 件数・符号・順序・重複・自己参照は相関パッケージの parser/生成時検査、全指標の参照と生成漏れは `verify-correlation-by-key.ts`、レスポンシブ配置は `correlation-layout.spec.ts` が検査する。
