# デザインシステム

stats47 の UI は、統計を迷わず探し、比較し、長時間読める道具として設計する。装飾より情報階層、派手な差別化より一貫性を優先する。

この文書は UI 判断の正典である。実際の class、props、token はコードを正典とし、数値を本書へ二重管理しない。

## 正典の階層

| 対象                           | 正典                                            |
| ------------------------------ | ----------------------------------------------- |
| デザイン原則・ページ横断の判断 | 本文書                                          |
| layout の props と寸法         | `apps/web/src/components/layout/`               |
| surface の variant             | `apps/web/src/components/surface/`              |
| color・font・radius の実値     | `apps/web/src/app/globals.css`、Tailwind config |
| primitive component            | `packages/components/`                          |
| Claude Code 向け実装規約       | `.claude/rules/ui-components.md`                |
| chart component                | `.claude/rules/chart-component-standards.md`    |
| page_components                | `.claude/design-system/page-components.md`      |

`.claude/design-system/` の quick reference や旧資料と食い違う場合は、本書と現在のコードを優先する。

## 原則

1. **データファースト** — 主要な値、比較、出典へ短い距離で到達できる。
2. **白基調・フラット** — 通常面は semantic color、薄い境界、控えめな影を使う。
3. **一つの意味に一つの表現** — 同じ種類の header、card、rail を feature ごとに作り直さない。既存UIで目的を満たせる場合は、新しいUIを追加せず共通部品を使う。
4. **日本語の可読性** — system font、過度な letter spacing を避け、本文幅と行間を守る。
5. **responsive は情報優先度で決める** — desktop を縮小するだけでなく、mobile の読む順序を設計する。
6. **accessibility は見た目と同格** — heading、focus、contrast、keyboard、reduced motion を後付けにしない。
7. **目的地までの操作を減らす** — 探索用リンクは可能な限り常時表示し、表示領域に収まる一覧へ不要な折りたたみや中間操作を加えない。

## レイアウト

### LeftRailLayout

ページ内ナビの左レールは `LeftRailLayout` を唯一の実装契約とし、`PageShell` と `ArticleShell` が共有する。

- 列幅、gap、992px の表示境界、`aside` と本文の DOM 構造は `LeftRailLayout.tsx` が正典。
- feature はレールの内容だけを所有し、grid、breakpoint、sticky を再定義しない。
- データ中心の概況ダッシュボードは `PageShell.leftRailDensity="compact"` を選べる。狭いレールの寸法も `LeftRailLayout` が所有し、既定表示・表示境界・自然スクロールは維持する。
- 左レールはページ本体と同じ自然スクロールに置く。Theme と survey で追従挙動を分岐させない。
- 狭幅代替 UI は `LEFT_RAIL_NARROW_ONLY_CLASS` を使い、desktop rail との二重表示・空白区間を作らない。
- 機械監査は `check-design-system.mjs`、振る舞いは layout contract tests が固定する。

### PageShell

通常の一覧、検索、ダッシュボードは `PageShell` を使う。

- 横幅と外側 padding は `SHELL_WIDTH_CLASS` が正典。
- `rightRail` は関連情報を主役にし、広告はその後に置く。広告・販促だけの rail で本文を狭めない。
- `leftRail` はそのページの探索・切替に限る。site 全体 nav を複製しない。Theme はグループ別テーマリンク・地域・全指標・出典調査、home / ranking / category はカテゴリ探索に使う。テーマグループは navigation-only SSOT とし、ranking category / ThemeCatalog taxonomy とは分離する。
- `leftRail` と `rightRail` は併用できない。両方渡した場合は右だけを描画する。
- `leftRail` は共有 `LeftRailLayout` を使う。本文最小幅 656px を維持できる 992px から表示する。
- rail は狭い画面で本文下へ積み、内容を消さない。ただし**ページ内容を切り替える nav** は本文下に積むと操作対象より後ろへ回るため、`leftRailNarrowBehavior="hide"` で隠し、同等の操作を**本文上部**に置く。この時に代替 UI を用意せず隠すことはしない。
- `variant="reading"` は単純な読み物に限る。記事系の標準は `ArticleShell`。
- page 内で独自の `container mx-auto` や別の全体 `max-width` を作らない。

### ArticleShell

blog、ranking detail、survey、規約等の読むページは `ArticleShell` を使う。

- 本文と rail を同じ reading zone に置く。
- rail は初期表示用の通常領域と、目次等の sticky 領域を分ける。
- rail 内に独立した縦 scroll を作らず、ページ本体の scroll だけで全 widget に到達できる自然フローとする。
- rail の sticky 領域にも `max-height` / `overflow-y` container を作らない。
- 右 rail は mobile で本文後へ積む。ページ内探索用の `leftRail` は共有契約の 992px 未満で隠し、同じ操作を
  `PageHeader` 直後の折りたたみナビとしてページ側が `LEFT_RAIL_NARROW_ONLY_CLASS` 付きで出す。左右を同時指定した場合は右 rail を優先する。
- survey の左 rail は「調査一覧・このページ・代表ランキング・関連する分類」に限定する。
  site 全体 nav や全ランキングを常時展開せず、調査の出典ハブとして読む順序を補助する。
- survey の狭幅代替ナビにも `/survey` の「調査一覧へ」を残し、左 rail 非表示時に上位ハブへの出口を失わない。

### PageHeader

標準ページ見出しは `PageHeader` を使う。

- `h1` はページに一つ置き、DOM 上でも主要コンテンツより先にする。
- `description`、`meta`、`stats` は役割を混ぜない。
- `description` はタイトルから推測できない対象範囲・定義・使い方だけを書く。画面を見れば分かる操作説明や、直下の chart と同じ説明は省略する。
- 操作は `actions` / `controls`、補助表示は `aside` slot を使う。
- header 本体を暗色 gradient や巨大 KPI 面にしない。
- feature 固有 header が必要な場合も、既存 header component を拡張または合成し、新しい hero 系統を増やさない。

## レール UI 契約

左右レールは配置・幅・sticky・responsive 非表示が異なっても、Surface・見出し・リンク行の視覚契約は共通とする。部品は `apps/web/src/components/surface/SurfaceCard.tsx` の `RailCard` / `RailNavRow` / `RailNavRowButton` と `apps/web/src/components/rail/{RailStack,RailCategoryList,RailLinksCard}.tsx` に集約する。

### 左右共通

- レール内の独立したまとまりは `RailCard` 1 枚 = `bg-card` + 全周 border + `shadow-sm` + `rounded-none`。見出し `h3` は `text-sm font-medium text-muted-foreground`（`border-b px-4 py-3`）、本文は `px-4 pb-4 pt-3`。折りたたみは `RailCard collapsible`（details/summary、summary `min-h-12`）。
- カード間の縦積みは `RailStack`（`flex flex-col gap-3`）だけを使う。`page.tsx` で `<aside>` を自前で描かない。landmark は `PageShell` / `ArticleShell` / `LeftRailLayout` が持つ。

### リンク行

- リンク行は `RailNavRow`（Link）/ `RailNavRowButton`（`aria-pressed`）。透明背景、`min-h-11 sm:min-h-9`（compact）/ `min-h-11 sm:min-h-10`（default）、`hover:bg-accent/50`、`focus-visible:ring-2 ring-inset`、右矢印、件数は `tabular-nums`。
- active は `aria-current="page"` + `bg-accent font-semibold text-primary`。カラーバー（inset shadow / `border-l`）で示さない。
- 末尾リンクは `text-xs font-medium text-primary hover:underline`（モバイル `min-h-11`）。

### 左右で異なってよいもの

配置、幅（左 264〜280px / 右 316px）、sticky、responsive の非表示・移動、中身（操作ナビ vs 補助情報）は左右で別契約のままでよい。992px / `lg` / `xl` の境界が別契約であることと、視覚言語が共通であることは別の話。

### カテゴリ導線

- カテゴリ導線の正は `RailCategoryList`（`@/components/rail`）。単列・区切り線付き、件数は「ランキング数」で固定（sr-only「のランキング」）。枠は持たず `<RailCard title="カテゴリから探す">` で包む。
- props は意味ベース（`items` 必須 / `showCount` / `activeCategoryKey` / `density` / `trackingSurface` 必須 / `moreLink`）。`variant="home"` 等のページ名 variant は禁止。
- `/` `/ranking` `/category/*` `/areas/*` `/blog` `/blog/*` `/survey/*` が同じ部品を使う。旧 `PortalCategoryGrid` と `RailLinksCard layout="grid"` は廃止。

### タグ

`RailLinksCard layout="chips"` はピル 1 種（`rounded-full`、`min-h-11 sm:min-h-7`、`border-muted-foreground/40 bg-muted`）。タグ専用でカテゴリ一覧へ流用しない。`rounded-full` はタグ・バッジ・ピルのみ。`RailLinksCard.trackingSurface` は必須。

## Surface

共有 surface は `SurfaceCard`、`SurfaceSection`、`SurfaceLinkCard` と primitive `Card` を基底にする。

- Surface は 3 段階で管理する: ページ `bg-background` / カード `bg-card` / hover・選択中・補助要素（タグピル・バッジ・サムネ地）だけ `bg-muted` または `bg-accent`。
- 通常の行・リンク群に理由なく `bg-muted` を使わない（詳細は「レール UI 契約」）。
- 通常 card は semantic background、全周 border、控えめな shadow。
- 外枠の radius は global token に従う。円形 icon、avatar、pill だけ `rounded-full` を使う。
- clickable card は card 全体の click target、focus-visible、hover を一致させる。
- portal card の縦横比は `PORTAL_CARD_ASPECT_CLASS` を使う。
- feature 内で border / shadow / padding をまとめた独自 card shell を複製しない。
- card / section surface の内側に別の card surface を置かない。まとまりが必要なら外側を通常の `section`、内側を区切り線付き list / table にする。

### 色

- `background` / `foreground` / `muted` / `border` / `primary` 等の semantic token を使う。
- category や chart series の色は意味の識別に使い、装飾的なカラーバーを増やさない。
- 本文へ raw `gray-*` / `black` を直接使わず、contrast を semantic token で保つ。
- positive / negative の色だけで意味を伝えず、label、symbol、値を併用する。

### カラーモード（light / dark）

- 既定は light。dark は利用者が明示的に選ぶ opt-in とし、OS 設定へ自動追従しない。
- 選択状態は `next-themes` が保持する。実装の正典は `apps/web/src/providers/theme-provider.tsx`。
- component は両 mode の semantic token と contrast を確認する。
- mode 別画像が必要な場合は `ThemeAwareImage` 等の既存 component を使い、同じ画像を二重表示しない。

### Typography

- 本文は system font stack を使い、Web font を表示の必須依存にしない。
- 通常ページの `h1` は既存 `PageHeader` の scale に合わせる。
- `h2` / `h3` は見た目ではなく文書構造で選ぶ。
- 数値表では桁、単位、小数点の比較しやすさを優先する。
- `tracking-tight` 等、日本語の可読性を落とす指定を避ける。

## Component の三層

| tier              | 配置                                          | 例                                | ルール                                        |
| ----------------- | --------------------------------------------- | --------------------------------- | --------------------------------------------- |
| Primitive         | `packages/components/src/`                    | Button、Card、Select、Table       | 先に既存 primitive を探す                     |
| Shared composite  | `apps/web/src/components/`                    | PageShell、SurfaceCard、ChartCard | 複数 feature で使う UI                        |
| Feature component | `apps/web/src/features/<feature>/components/` | ranking header、theme section     | feature 固有。別 feature から直 import しない |

同じ UI が二つ以上の feature で必要になったら shared composite への昇格を検討する。将来使うかもしれないという理由だけで抽象化しない。

### 本文コンテンツの開閉 UI

- FAQ は共有 `FaqSection`、統計の定義・AI考察など単一本文は共有 `ContentDisclosure`（`apps/web/src/components/content/`）を使う。feature ごとに Accordion や三角文字を再実装しない。
- 操作は native `details/summary` を基底とし、閉じた本文も SSR DOM に保持する。見出し・質問・本文は 14px（見出しは semibold、質問・本文は normal）、操作高 44px 以上、状態表示は 12px の細線 + / − に統一する。
- hover / tooltip は補助説明に限り、開閉や主要導線を hover のみに依存させない。ナビゲーション用の `details` は本文開閉と責務が異なるため、この部品へ無理に統合しない。

## Responsive

| 対象                | 判断基準                                            |
| ------------------- | --------------------------------------------------- |
| page と rail の切替 | `PageShell` / `ArticleShell` の breakpoint          |
| typography・button  | viewport breakpoint                                 |
| dashboard card grid | container query                                     |
| 指標カード集合      | 0 件=wrapper なし / 1 件=単列・grid なし / 2 件以上=container query grid (`@md:grid-cols-2`) |
| table               | 横 scroll、列優先度、別表現のいずれかを意図的に選ぶ |
| chart               | container width と touch target                     |

- mobile の DOM 順は読み上げ順、SEO、視覚順で矛盾させない。
- hover だけで表示される情報を作らない。
- 横長 table をカードへ変換する場合、比較可能性を失わない。
- safe area と固定 header を考慮し、anchor / sticky content を隠さない。

## ページ別の契約

### Home

- 白基調のポータルとして、主要な探索入口を短く提示する。
- 暗色の巨大 hero を既定へ戻さない。
- category、ranking、area、blog の優先順位は `apps/web/src/features/home-portal/README.md` に従う。

### Ranking

- ranking detail は既存の `RankingHeader/` 系を使う。
- `h1`、操作、統計、地図、table の順序は mobile / desktop の利用目的を踏まえて既存 feature contract に揃える。
- mobile では主要可視化へ早く到達できるようにする一方、`h1` は DOM 先頭を維持する。
- 一位だけを巨大な暗色 KPI 面で特別扱いせず、上位、最下位、全国値を通常 surface で比較できるようにする。

### Theme / Area

- Theme は複数指標の意味的な順序、Area は一地域の特徴を主語にする。
- chart の配置は [`03_情報設計.md`](./03_情報設計.md) と ThemeCatalog / page_components の定義に従う。
- Theme の左 rail はグループ別テーマリンク、地域、全指標、出典調査をこの順で整理する。テーマと出典調査には `/themes`・`/survey` の上位ハブリンクを1件ずつ置く。現在テーマのグループだけ初期展開し、現在リンクを明示する。
- 地域では「比較単位（47都道府県 / 市区町村 / 日本）」と「表示する都道府県」を別の操作として示す。比較単位は共有 `StatisticsScopeNav` の rail variant、都道府県は `PrefectureSelect` を使い、リンクや状態定義を複製しない。
- 狭幅では左 rail を隠し、共有 `StatisticsScopeNav` の横タブ・テーマ Select・地域・ページ内クイックリンク・全指標・出典調査を本文上部へ置く。同じ操作を同時表示しない。
- Theme / Japan / Municipality の地理スコープ切替には共有 `StatisticsScopeNav` を使う。
- 関連情報が無い dashboard / hub は全幅とし、広告だけの right rail を作らない。

#### 選択 UI と集合レイアウトの件数規則

- 選択 UI（checkbox・tab・選択タイル・`ScrollableRow`）は、フィルタ後に有効な選択肢が 2 件以上あるときだけ表示する。0 件はセクションごと非表示、1 件は選択 UI を出さず指標名・値・単位・年次・順位・ランキング導線を直接並べる。外せない checked 状態や、カード見出しと唯一の選択肢ラベルの重複を作らない。
- 集合レイアウト（指標カードの grid）は 0 件で wrapper を描かず、1 件でも複数列 grid wrapper を作らない。2 件以上のときだけ container query の grid（`grid grid-cols-1 gap-4 @md:grid-cols-2`）で包む。desktop の compact card は複数あるときだけ 2 列、mobile は常に 1 列。詳細チャート・複数指標切替パネル・固定年比較は全幅を維持する。
- 単一指標の推移は、都道府県選択時に異なる年が 2 件以上あるときだけ小さな折れ線（`MiniLineChart`、84px）を描く。単年は自然高の 1 行テキストにし、空の折れ線枠・ローディング風の大面積・「時系列データがありません」だけの固定高領域を置かない。
- 時系列データの取得は指標 1 件分の遅延取得（自地域 + 全国）を再利用し、47 都道府県一覧表示のための一括取得へ戻さない。

### Blog / Survey / 規約

- `ArticleShell` と reading zone を使う。
- 本文、出典、図表、CTA、rail の優先度を分ける。
- 記事 card 内へ別の大きな card shell を重ねない。

## Chart と table

- 新規 chart の前に既存 catalog を確認する。
- title、unit、period、source、legend を chart 単体でも理解できるようにする。
- title・凡例・軸から自明な reader description を自動生成しない。Theme chart header は短い title に絞る。
- 系列断絶、母集団差、比較不能条件など chart 固有の誤読防止条件だけを近接 footer の `annotation` に置く。
- 指標の定義・算出方法・一般注釈は `/ranking/[key]` の指標ハブへ集約し、chart からリンクする。
- 指標の選定理由や内部 provenance は reader UI と混ぜず、SSOT に保持する。
- loading、empty、partial、error を同じ表示にしない。
- color scale と axis は指標間で意味が変わる場合に使い回さない。
- table は header scope、数値 alignment、mobile overflow、sort state を確認する。
- visualization を decoration として置かず、ページの問いへ答えるものだけを置く。

## データ出典

出典の表示は3層に分け、層ごとに部品を1つに固定する (2026-09-25)。

| 層 | 部品 | 役割 |
|---|---|---|
| ページ全体の出典 | `DataSourceList` (`apps/web/src/components/molecules/DataSourceList.tsx`) | ページ末尾の「データ出典」。ブログ記事・ランキング・市区町村ランキング・Geo レイヤー |
| 図ごとの出典 | `ChartFooter` | 図の直下の短い出典リンク。テーマ・エリア・stat-charts |
| 調査ハブへの回遊 | `SurveyTaxonomyCard` | 右レール等の「この記事の出典調査」。出典の表記ではなく導線 |

- 1 行は「調査名 (サイト内の `/survey/<id>` へ)・(機関)・[統計表 ↗] (e-Stat 等の実データ表)」。
  調査ではないデータセットは名前を外部ページへリンクし、ライセンスがあれば行末に出す。
  地図の行政区域データのような補助データは `note` (例: 「地図データ:」) を付けて同じ一覧に並べる。
- 行はデータ (`DataSourceEntry`) から派生させる。ブログは図の `source.json`、ランキングは `item.json` の
  `sourceConfig` と `attribution` が入力で、解決は `@stats47/ranking` の `resolve*DataSources` だけが行う。
  画面側で出典の文字列や e-Stat の URL を組み立てない (`buildEstatTableUrl` だけが URL を作る)。
- ブログ本文に手書きの「データ出典」節を書かない。計算方法や定義の説明は「データについて」節に書く。
- 機械ゲート: `apps/web/src/__tests__/data-source-contract.test.ts` (「データ出典」見出しは `DataSourceList` だけ・
  e-Stat URL の直書き禁止・旧 `item.source` 参照禁止)、`quality-gate.mjs` (記事の手書き節を blocker)、
  週次のタクソノミー監査 (手書き節・出典 0 件・未焼き込みの件数)、ページ品質監査
  (`duplicate_data_source_sections`)。

## 禁止事項

- ページごとの独自 outer container。
- page 内での rail 列幅の直書きと、広告だけの `RightRailWidgets`。
- feature ごとの独自 Card / Button / Table 基底。
- 通常ページへの巨大 gradient hero、暗色 KPI panel、過剰な shadow。
- 装飾だけの色帯、色だけに依存した状態表現。
- `h1` より前に主要コンテンツを DOM 配置する。
- rail の内容を狭い画面で無条件に非表示にする。
- component query が必要な grid を viewport 幅だけで決める。
- UI の件数、色、寸法を文書とコードの両方で個別管理する。
- 選択肢が 1 件しかないセレクタ（checkbox・tab・選択タイル）を置く。
- 時系列が 2 時点未満なのに空の固定高チャート枠・ローディング風の枠を置く。
- `page.tsx` で `<aside>` を自前で描く。
- 選択肢のカードに理由なく `bg-muted`。
- カテゴリ導線の独自 grid・独自行。
- ページ名依存の variant（`variant="home"` 等）。

## UI 変更時の確認

1. 既存 primitive / shared component で実現できないか。
2. PageShell / ArticleShell / PageHeader のどれに従うか。
3. mobile の DOM 順、keyboard、focus、contrast が成立するか。
4. loading、empty、error、long text、最大値で崩れないか。
5. chart と page_components の既存契約を再利用したか。
6. 変更前後を同じ viewport で目視し、意図しない UI 差分がないか。
7. UI 変更でない作業では class、DOM、asset を変更しない。
