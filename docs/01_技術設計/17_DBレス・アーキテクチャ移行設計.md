# DB レス・アーキテクチャ移行設計（ローカルビルド DB の使い捨て化）

> **目的**: クラウドの Claude Code で**すべての作業を完結**できるようにする。
> 現状ネックになっている「git 管理外・R2 持ち回りの SQLite 1 ファイル」を、
> いつでもソースから再生成できる**使い捨てビルド成果物**に格下げする（または完全廃止する）。

> **本ドキュメントは提案 (status: proposal)**。実装着手前に「SQLite 完全廃止 / 使い捨てツールとして残す」の
> 方針確定が必要（[§7 未決事項](#7-未決事項要判断)）。

## 0. 背景（なぜこの設計が必要か）

2026-05-29 のセッションで、クラウド環境から `npm run db:pull` が失敗（R2 に `database/stats47.sqlite` が未 seed）し、
次フェーズ（metric 量産・snapshot 生成）がブロックされた。根本原因を実測調査した結果、以下が判明:

- **本番 `apps/web` は DB を一切クエリしない**（R2 snapshot のみ。grep ヒットは型 import だけ）
- DB を import する 142 ファイルは**すべてビルド時 exporter / batch**
- DB の唯一の仕事 = `sync-snapshots` の 13 exporter＋相関計算の**入力**になること
- **真のネックは「集計」ではない**。area_profiles / correlations は compute script が実在し再生成可能。
  本当に救出が要るのは **Authored 系（page_components / sns_posts / affiliate_ads / theme_metrics 等）で、
  真実源が DB 内だけにあり git/R2 にバックアップが無い**こと。これが「初回 seed は実環境から」を必須化し、
  持ち回りを不可避にしている。

関連: `.claude/rules/data-sqlite-ssot.md`（Phase 6 で観測値を R2 移行済の経緯）

## 1. 大原則：全テーブルを3種類に仕分ける

「DB を持たない」を実現する鍵は、各テーブルを**真実源の所在**で分類し、別の置き場に逃がすこと。

| 種別 | 定義 | 逃がし先 | 該当（2026-05-29 実測） |
|---|---|---|---|
| **Authored** | 人/エージェントが作る。外部に真実源が無い | **git ファイル** | page_components(411)・sns_posts(549)・affiliate_ads(24)・theme_metrics(284, compute script 無し)・categories/themes master・articles メタ |
| **Reference** | 外部に真実源がある | **再生成**（import / API） | metrics(TS registry)・prefectures/cities(JSON)・estat_metainfo/estat_catalog(e-Stat API) |
| **Derived** | 他データから計算できる | **batch 計算 → R2**（保存しない） | area_profiles・correlations（どちらも compute script 実在、入力を DB→R2 に繋ぎ替えるだけ） |

実測根拠:
- `packages/area-profile/src/services/run-batch-area-profile.ts`（compute 実在、現状入力は DB `areaProfiles/metrics`）
- `packages/correlation/src/utils/calculate-pearson.ts`（compute 実在）
- theme_metrics: compute / populate script が見つからない → **Authored（手調整）**と判断

## 2. 目標の最終形（2つの SSOT だけ）

```
git    = Authored（定義・config・手調整・コンテンツ本文）
R2     = 観測値 (app/stats/*) ＋ 派生 snapshot (app/... 配信 JSON)
SQLite = もう "持たない"。集計時だけ :memory: で一時生成 → 破棄
```

永続 DB ファイルゼロ。`db:pull` の持ち回りゼロ。本番は従来どおり R2 のみ読む（変更なし）。

## 3. 集計の「工夫」＝エフェメラル計算パターン

指標横断の SQL JOIN が要る処理（area_profile / 相関）だけ、実行時に一時 DB を建てる:

```ts
// build-aggregates.ts （cloud で実行、何も永続しない）
const db = new Database(":memory:");          // or /tmp/xxx.sqlite（使い捨て）
for (const m of registry)                     // metrics/*.ts を import
  insert(db, await readStatsValues(m.key));   // R2 から観測値を流し込む
const profiles = computeStrengthWeakness(db); // 既存ロジックを再利用
const corr     = computePearson(db);
await writeR2("app/areas/.../profile.json", profiles);
await writeR2("app/correlation/top-pairs.json", corr);
db.close();                                   // 破棄。持ち回らない
```

- 「何度も実行しない」前提なので、毎回 ~2,000 本の JSON を読んでも問題なし（バッチであってリクエストではない）
- 高速化したいなら、R2 に**1 枚の指標マトリクス（parquet/JSON）**を事前生成すれば読み込み一発
- DuckDB なら R2 の JSON を直接 SQL で JOIN 可能（既存 better-sqlite3 ロジックを残すなら in-memory SQLite でも可）

これが「DB を持たずに JOIN の楽さだけ得る」具体策。

## 4. 移行フェーズ（具体手順）

### Phase 0 — 凍結（最優先・保険）
全テーブルを `db-dump/<table>.json` にダンプ → git＋R2 に確保。Authored 系の救出不能データを失う前に確保。
**以降の各 Phase の正解データ（golden）にもなる。**
※ DB 本体は現状 Mac 側にしか無いため、このダンプは**実データを持つ環境（Mac）で実行**が必要。

### Phase 1 — Authored を git SSOT に昇格
- categories/themes → `packages/data-configs/src/{categories,themes}/*.ts` registry を現 DB から生成
- page_components(411) → per-page config を TS/JSON で git に（`/populate-component-data` の出力先を DB→ファイルに）
- affiliate_ads(24) → `packages/data-configs/src/ads/*.ts` registry
- theme_metrics(284) → 手調整マッピングを TS に、自動選定分は判定ロジックをコード化
- sns_posts(549) → `.claude/state/sns/posts.json`（運用ログなので `.claude/` が適切）
- articles → DB 列のメタを `article.md` frontmatter に寄せる（本文は既に R2 にある）

### Phase 2 — 13 exporter を「DB 読み」→「SSOT 読み」に書換（1本ずつ）
対象 exporter（`.claude/skills/db/sync-snapshots/run.sh` の TASKS）:
`remotion-static / master / ai-content / area-profile / city-profile / blog / page-components /
themes / affiliate-ads / ranking-page-cards / fishing-ports / port-statistics / station-passengers`

書換方針:
- master / themes / page-components / ads / blog 系 → **git ファイル読み**
- area-profile / city-profile / correlation → **Phase 3 のエフェメラル計算**
- ai-content / ranking-page-cards → **R2 ＋ registry 読み**

**検証ゲート（必須）**: 書換後の R2 snapshot が Phase 0 の golden と**バイト一致**することを各本で確認（回帰防止）。

### Phase 3 — Derived をエフェメラル計算化
area_profile / correlation の compute 入力を DB → R2 (`readStatsValues`) に繋ぎ替え。§3 のパターンで :memory: 計算 → R2。

### Phase 4 — 永続 DB の廃止
- `db:pull` / `db:push` 持ち回りを削除
- どうしても SQLite ハンドルが要る処理だけ `db:build`（SSOT から一時生成）を残す
- SessionStart hook の「DB 不在警告」を撤去、CLAUDE.md / `.claude/rules/*` を更新

## 5. 完了後のクラウド完結ワークフロー

```
新規 metric : metrics/*.ts(git) → page-data-batch(R2) → build-aggregates(R2) → exporters(R2) → deploy
             ※ db:pull 不要。最初から最後までクラウドで完結
config 編集 : git のファイルを編集 → exporter → R2   ※ diff/レビュー/revert が効く
```

## 6. この設計の効きどころ

1. **クラウド完結**: 持ち回り blob が消え、`db:pull` の前提が無くなる（今回詰まった原因の根絶）
2. **事故耐性**: Authored が git に入る＝バイナリ上書き消失が起きない、履歴で戻せる、複数セッション同時編集も差分マージ可能
3. **過剰設計の回避**: 集計だけ局所的に SQL を使う（純 TS で 2,000 指標の JOIN を書く苦行を避ける）

## 7. 未決事項（要判断）

1. **SQLite の扱い**: 完全廃止 / 使い捨てツールとして残す（推奨: 後者。集計の JOIN だけ局所利用、持ち回りは廃止）
2. **theme_metrics の自動選定分**: ロジック化できるか、全部手調整として固定するか（中身を見て決める）
3. **Authored config の形式**: TS（型安全・metrics/*.ts と統一）か JSON（純データ）か

## 8. 暫定運用（移行完了まで）

移行が完了するまでは、**現行の R2 持ち回りで十分**に量産は回る:
- 量産フェーズは DB を実質「読み取り専用入力」として扱う（書込先は R2/git、`sync-metrics-cache` が触る
  `metrics` 表は TS から再生成可能なキャッシュ）
- **判断ルール**: DB 内の手調整データ（articles/page_components/sns_posts）を**書くのはローカル 1 箇所に固定**。
  クラウドは読むだけ。これを守る限り blob 持ち回りでも上書き消失は起きない。
- 手順: ローカル（Mac）で `npm run db:push --workspace=packages/r2-storage` → 以降クラウドで `npm run db:pull`
