# 情報設計 (ページ責務・タクソノミー・ファネル)

stats47 の「ページ系統・分類軸・ファネル役割」を 1 枚に統合した情報設計の正典。3 つのレンズで構成する:

- **Part 1 — ページ責務分離 (データ軸)**: `/areas` `/themes` `/category` `/ranking` の責務と `page_components` 配置ルール
- **Part 2 — 3 タクソノミー (ナビ軸)**: `category` / `theme` / `tag` の役割・選択基準・アンチパターン
- **Part 3 — ファネル役割マップ (KPI 軸)**: 各ページタイプを「集客面 / 回遊面」に分類し評価 KPI を確定

3 つは同じ「ページ/分類システム」を異なる軸で切ったもの。設計判断 (どの page_type に置くか / どの分類軸を足すか / どの KPI で測るか) はこのファイルに集約する。

# Part 1 — ページ責務分離 (データ軸)

4 つの「データ表示ページ系統」の責務を厳格に分離し、`page_components` の配置ルールを定義する。

## 背景

2026-05-27、`/areas/17000` (石川県) に「人口移動フロー」が表示されていたが、これは**主題**(人口動態)の深掘り可視化であって**県軸**の特徴ではなかった。`page_components` の `pageType="area"` に「全国横断視点が必要な可視化」が紛れ込み、area / theme の責務が曖昧化していた。本パートはその判定基準を定める。

## 4 ページ系統の責務マトリクス

| ページ | 軸 | ユーザー意図 | 主な要素 |
|---|---|---|---|
| `/areas/[code]` | **県軸 (行)** | 「この県の特徴を知りたい」 | 強み/弱み、県固有の時系列推移、カテゴリ別 top3、各種導線 |
| `/themes/[slug]` | **指標軸 (列) ×横断可視化** | 「この主題で 47 県を比べたい」 | indicator set (10〜15 指標) の地図/コロプレス、横並びダッシュボード、移動フロー・ピラミッド等の主題深掘り可視化 |
| `/category/[key]` | **カテゴリ内一覧** | 「このカテゴリにどんなランキングがあるか」 | ランキング一覧、簡易ナビ |
| `/ranking/[key]` | **個別指標深掘り** | 「この指標の詳細を知りたい」 | 47 県順位、地図、時系列、AI コンテンツ、関連指標 |

```
[県軸] /areas/[code]       ─┐
                            │  どちらも同じデータマトリクスを別軸で切る
[指標軸] /themes/[slug]    ─┘
        │↓ 深掘り
[個別指標] /ranking/[key]  ←  [カテゴリ一覧] /category/[key] (ハブ)
```

## page_components 配置の判定基準

`pageType` カラムに何を入れるかの判断軸。**1 つのチャートを複数 pageType に配置するのは可** (page_type + page_key + component_key で一意)。ただし**意味的に正しい pageType だけに配置すること**。

### pageType = "theme"
**判定軸**: 「47 県を横並びで見せる」「主題内の複数指標を関連付ける」「単一指標でも全国構造を可視化する」可視化。
- ✅ 地図/コロプレス (47 県塗り分け) / 移動フロー / 人口ピラミッド / 散布図 (2 指標相関) / 主題ダッシュボードのタブ別チャート群 / テーマ KPI タイル

### pageType = "area"
**判定軸**: 「**この県だけ**の時系列・構成・固有ストーリー」を語る可視化。県を変えれば中身が変わるが読み方は同じ。
- ✅ 県固有の時系列推移 / 県の年齢構成円グラフ / 県の産業構成 / 県内の市区町村ランキング
- ❌ 47 県比較地図 → theme へ / 主題全体の可視化 (移動フロー等) → theme へ / 全国平均対比だけ → ranking へ

### pageType = "area-category" / "city-category"
**判定軸**: その県/市区町村の「特定カテゴリ内」の指標を**複数まとめて見せる**ダッシュボード。
- ✅ カテゴリ内 KPI タイル群 / カテゴリ内チャート群 / 市区町村専用は `city-category` (statsDataId が異なる)

### pageType = "ranking"
**判定軸**: 個別ランキングページ内のサブチャート (主指標以外の補助可視化)。
- ✅ 関連指標の時系列 / 全国分布ヒストグラム / ランキング詳細ページ専用カード

## 設計原則

1. **重い横断可視化は theme へ** — `MigrationFlowPlayer`・地図コロプレス・47 県散布図のような全国を一度に処理する重いコンポーネントは theme に集約。area は 47 回 SSG されるため build 時間・bundle が 47 倍効き、SEO cannibalization リスクもある。
2. **area は県の自己紹介ハブ** — 本質は県固有のストーリー (強み/弱み・県固有時系列) と深掘り先への導線。「47 県横並び」は theme に委譲しリンクする。
3. **area の thin content 化を避ける** — 「導線だけ」まで削ると県名 SEO の着地が薄くなる。県固有の時系列推移は差別化要素として残す。
4. **重複は許容、ただし意味的に正しい pageType のみ** — 同じ component_key を theme と area-category の両方に登録するのは可。主題深掘り可視化を `area` に登録するのは禁止。

棚卸し: `.claude/scripts/audit/page-components-audit.cjs` で `pageType="area"` 配下に主題深掘り可視化が無いか全件確認 → `docs/04_レビュー/YYYY-MM-DD-area-theme-audit.md` に記録。

# Part 2 — 3 タクソノミー (ナビ軸)

分類概念として **category / theme / tag の 3 軸を意図的に並立**させる。それぞれの役割・選択基準・住み分けを定義する。

## なぜ 3 並立か

過去 (~2026-05) は「category は deprecated、tag に統合中」とされていたが、GSC 実測 (2026-W21) で 3 軸が異なる役割を果たしていることが確認された:

| 軸 | ページ数 | 週次 imp | 週次 clicks | 役割 |
|---|---|---|---|---|
| `/category/*` | 11 | 39 | 2 | サイドバー主要ナビ。e-Stat 機械分類のブラウズ動線 |
| `/themes/*` | 15 | 152 | 4 | curated ダッシュボード。SEO 上の主力ハブ |
| `/tag/[key]` | (blog のみ) | (blog 経路) | (blog 経路) | ブログ記事の横断分類 |

→ themes が curated コンテンツとして 4 倍の imp を稼ぎ、category とは別の SEO 価値を持つ。tag は blog に閉じて安定。3 軸統合は役割を曖昧化し SEO 上もマイナス。

## 3 タクソノミーの定義

### 1. `categories` — e-Stat 機械分類 (17 軸)
| 項目 | 内容 |
|---|---|
| 真実源 | git TS 定義 → 生成スクリプトで R2 snapshot (完全DBレス doc 12 Phase E。永続 D1 は廃止) |
| URL | `/category/[categoryKey]` |
| 例 | `population`, `economy`, `laborwage`, `agriculture`, `tourism`, `administrativefinancial` ほか 17 件 |
| 用途 | サイドバー主要ナビ。「同じ統計分野の他指標を見たい」用 |
| 実装 | `packages/category/`、ヘッダーのカテゴリメガメニュー |

### 2. `themes` — curated ダッシュボード (22 軸)
| 項目 | 内容 |
|---|---|
| 真実源 | TS-config `packages/types/src/indicator-sets/` + `apps/web/scripts/data/page-components/theme/` |
| URL | `/themes/[themeSlug]` (全国俯瞰)、`/areas/[code]/[themeSlug]` (県別・Type A のみ) |
| 例 | `healthcare`, `aging-society`, `tourism`, `population-dynamics`, `local-finance` ほか |
| 用途 | 「テーマで深掘り分析したい」。時系列・全国比較・地域構造の解説 |
| 実装 | `apps/web/src/features/theme-dashboard/` |
| Type 分類 | **Type A** (都道府県単位) 18 件 → `/areas/[code]/[themeSlug]` でも利用可。**Type B** (インフラ/ネットワーク) ports/railway/roads — 全国俯瞰専用 |

### 3. `tags` — ブログ記事の横断分類
| 項目 | 内容 |
|---|---|
| 真実源 | `article.md` frontmatter の `tags` (完全DBレス。R2 `app/blog/all.json` に再生成) |
| URL | `/tag/[tagKey]` (ブログ専用) |
| 例 | 日本語キー (例: `寿命`, `所得`, `教育`) |
| 用途 | 「このトピックの他の記事を読みたい」用 |
| 制約 | 記事 < 2 件のタグは `noindex` (thin content 回避) |

## 選択フロー (新規分類追加時)

```
新規分類を追加したい
  ├─ e-Stat 統計大分類か? → YES: categories に追加 (git TS 定義を PR → 生成で R2)
  ├─ 人間 curated の「テーマ別ダッシュボード」(chart 構成持ち) か?
  │     → YES: themes に追加 (packages/types/src/indicator-sets/ の TS config が SSOT)
  ├─ ブログ記事の横断分類か? → YES: article.md frontmatter の tags に追加
  └─ どれでもない → critical-review で要相談 (3 軸で固定が原則)
```

## アンチパターン

| ❌ NG | 理由 |
|---|---|
| category と theme で同じキー名を使う | 役割が違うため別キー空間にする |
| `/tag` をランキング横断対応にすぐ拡張 | tag メタ未整備、サイドバーが壊れる |
| `/category` を削除して `/themes` に統合 | サイドバー機能停止 + categoryKey 依存箇所多数 |
| 「subcategories」「topics」等で軸を追加 | 軸が増えるほど認知負荷が上がる、3 軸で固定 |
| themes のキーを `compare-*` で命名 | compare-* は IndicatorSet 用 (compare 機能と無関係)、混乱の元 |

> tag 統合を将来検討する場合の前提条件 (tag テーブル/curated リスト復活・17 categories→tag マッピング・301・参照箇所改修・サイドバー UI 検証) は現時点では未整備。実施しない。

# Part 3 — ファネル役割マップ (KPI 軸)

各ページタイプを**ファネル上の役割 =「集客面」か「回遊面」か**で分類し、**どの KPI で評価し / どのタクティクスを当てるか**を確定する。設計タクティクスの行き先を一意に決めるルーティング表。

## なぜ必要か

4 ページを横並びで扱うと**売上の 96% を稼ぐ面を議論から外したまま 1% の面に工数を注ぐ**誤りが起きる。GSC 実測では検索集客がほぼ `/ranking` と `/blog` に集中し、`/themes` `/areas` `/compare` は検索流入が実質ゼロ。この差を役割として固定する。

## GSC 実測 (2026-W22, 週次)

出典: `.claude/skills/analytics/gsc-improvement/reference/snapshots/2026-W22/pages.csv` (全体: clicks 1,319 / imp 50,101)

| ページ | clicks | imp | 平均順位 | clicks 構成比 |
|---|---:|---:|---:|---:|
| `/ranking/*` | **728** | 22,957 | 7.8 | **55%** |
| `/blog/*` | **544** | 24,337 | 7.9 | **41%** |
| `/survey/*` | 6 | 1,353 | 13.9 | 0.5% |
| `/areas/*` | 4 | 760 | 16.5 | 0.3% |
| `/themes/*` | 4 | 168 | 14.4 | 0.3% |
| `/category/*` | 3 | 65 | 9.5 | 0.2% |
| `/compare/*` | 1 | 44 | 8.1 | 0.1% |

**ranking + blog = clicks 96%。theme + area + compare = 合計 1%。** 検索需要は「テーマ」粒度では発生せず「単一指標・単一事実」粒度で発生する (例: `一般病床の病床利用率が最も高い都道府県は？`)。

## ファネル役割マップ (本体)

| ページ | データ軸 (Part 1) | 主な入口 | **ファネル役割** | **評価 KPI** |
|---|---|---|---|---|
| `/ranking/[key]` | 個別指標 | **検索** | **集客エンジン①** | clicks・impr・CTR・順位 |
| `/blog/[slug]` | 記事 | **検索** | **集客エンジン②** | clicks・impr・CTR・順位 |
| `/survey/[key]` | 調査束 | 検索(未開花) | **集客(潜在)** | CTR (現 0.4% が課題) |
| `/category/[key]` | カテゴリ一覧 | サイドバー/内部 | ナビ(内部) | 内部 CTR・回遊 |
| `/themes/[slug]` | 指標軸×横断 | **内部遷移** | **回遊・深掘り面** | 直帰率・pages/session・滞在 |
| `/areas/[code]` | 県軸 | **内部遷移** | **回遊・深掘り面** | 直帰率・pages/session・滞在 |
| `/compare/[key]` | カテゴリ比較 | **内部遷移** | **回遊・深掘り面** | 直帰率・回遊 |

```
[集客面] 検索需要が着地する単一事実粒度のページ
   /ranking ・ /blog ・ /survey(潜在)  → KPI: clicks / impr / CTR / 順位
   → 投資: コンテンツ・SEO・問い設計 (疑問形タイトル / FAQ / PAA 獲得)
[回遊面] 内部遷移の着地先。検索流入ほぼゼロ (天井は文体でなく "粒度" 由来)
   /themes ・ /areas ・ /compare ・ /category  → KPI: 直帰率 / pages-per-session / 滞在
   → 投資: UX (結論ファースト・問い化・内部リンク導線・回遊設計)
```

## 意思決定ルール (このマップが防ぐ誤り)

1. **回遊面 (theme/area/compare) を集客 KPI で評価しない。** `/themes` の 168 imp 天井は H1 の文体ではなく「テーマ」という検索需要のない粒度に起因 (誰も "人口動態" では検索せず "合計特殊出生率 都道府県" で検索する)。問い設計を当てても clicks は動かない。回遊・滞在 KPI で測る。
2. **集客投資は ranking/blog に寄せる。** 問い設計 (疑問形タイトル・FAQ・PAA) は imp 47,000 と疑問形クエリがある集客面でこそレバレッジが出る。
3. **survey は "潜在集客"。** imp 1,353 / clicks 6 (CTR 0.4%) = 需要はあるが未 converting。CTR/順位改善の対象に入れる。
4. **回遊面の問い化は別 KPI の独立施策として持つ。** 集客と切り離して直帰率・回遊で評価する。

## タクティクス・ルーティング表

| タクティクス | 行き先 | 根拠 |
|---|---|---|
| 疑問形タイトル / FAQ / PAA 獲得 | **ranking / blog / survey** | imp と疑問形クエリが既にある面 |
| CTR 改善 (タイトル curiosity gap) | **ranking / blog / survey** | imp あり clicks 少の面 |
| Hero 結論ファースト・問い化 UX | **theme / area / compare** | 内部遷移の着地、滞在・回遊を上げる |
| 内部リンク導線・関連回遊強化 | theme / area / compare / category | ハブとして ranking/blog へ送り返す |
| 新規指標・記事の面拡張 | ranking / blog | 集客の母数を増やす |

> **[仮説・未検証]** theme/area/compare の流入は大半が内部遷移で Organic Search は薄い。**検証**: `/fetch-ga4-data last28d pagePath,sessionDefaultChannelGroup` で Organic 比率を確認。**期日**: 次回週次レビュー。
