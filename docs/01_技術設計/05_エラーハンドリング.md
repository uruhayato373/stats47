# エラーハンドリング

stats47 では、利用者が対処できる期待内の失敗と、インフラ・実装上の期待外の失敗を分ける。`packages/types/src/result.ts` の `Result<T, E>` を共通表現として使い、空データと失敗を混同しない。

## 基本方針

| 状態                               | 表現                                            |
| ---------------------------------- | ----------------------------------------------- |
| 正常に取得でき、結果が 0 件        | `ok([])` / `ok(null)` 等、domain が定める成功値 |
| 入力不正・業務上の拒否・既知の不在 | 型付き error / `Result`                         |
| 外部 API・R2 の一時障害            | error を保持して上位へ伝播                      |
| 実装 invariant 違反                | throw                                           |
| URL resource の確定的な不在        | route 境界で `notFound()`                       |

`catch { return [] }` のように失敗を正常な空結果へ変換しない。build phase だけに必要な fallback は、runtime の挙動と分離し、コード上で条件を明示する。

## 層別の責務

```text
UI / Route / Server Action
          │ 利用者向け状態へ変換
          ▼
Service / Use case
          │ domain error を組み立てる
          ▼
Repository / Loader / Adapter
          │ I/O error と schema error を保持
          ▼
R2 / external API / filesystem
```

### Adapter / Repository / Loader

- HTTP status、R2 not-found、timeout、schema validation failure を区別する。
- domain が `Result` を採用している場合は `Result<T, DomainError>` を返す。
- throw を採用する低レベル API は、元の `cause` を失わない。
- I/O 失敗を `null`、`[]`、既定値へ変換しない。

### Service / Use case

- 下位の error を、呼び出し側が分岐できる domain error へ変換する。
- retry、status mapping、fallback のような決定的処理をモデル判断へ委ねない。
- catch する場合は、回復、文脈追加、型変換のいずれかを行う。何もせず握りつぶさない。

### Route / Server Action

- URL resource が存在しない場合だけ `notFound()` を使う。
- 一時障害を not-found に偽装しない。
- Server Action は serializable な `ActionResult` / `Result` へ変換し、利用者が修正できる入力エラーを返す。
- API route は `400`、`404`、`409`、`429`、`5xx` を意味に合わせ、常に `200` で error body を返さない。

### UI

- loading、empty、partial、error を別の状態として表示する。
- 利用者が回復できる場合は再試行または入力修正を案内する。
- 内部 stack、credential、bucket key、個人情報を画面へ出さない。
- error boundary は予期しない失敗の最終境界であり、通常の分岐に使わない。

## Result の使用例

```ts
import { err, ok, type Result } from '@stats47/types';

type LoadError =
  | { type: 'not-found'; key: string }
  | { type: 'upstream'; message: string; cause?: unknown }
  | { type: 'invalid-data'; message: string; cause?: unknown };

async function loadItems(key: string): Promise<Result<Item[], LoadError>> {
  try {
    const value = await readSnapshot(key);
    if (value === null) return err({ type: 'not-found', key });
    if (!isValid(value)) {
      return err({ type: 'invalid-data', message: 'snapshot schema mismatch' });
    }
    return ok(value.items);
  } catch (cause) {
    return err({ type: 'upstream', message: 'snapshot read failed', cause });
  }
}
```

`ok([])` は「取得に成功したが項目がない」。`err(...)` は「結果を信頼できない」。呼び出し側はこの差を維持する。

## ログ

- 同じ error を各層で繰り返し log せず、運用判断ができる境界で一度記録する。
- `logger` に operation、resource、error type、retryable、cause を構造化して渡す。
- credential、Cookie、authorization header、個人情報、本文全量を log しない。
- `console.log` を恒常運用の監視に使わない。

## Retry と fallback

- retry は timeout、rate limit、一時的な upstream failure のみに限定する。
- 回数、backoff、idempotency をコードで固定する。
- write の retry は重複実行を防げる場合だけ行う。
- stale snapshot を使う場合は、許容期限と観測可能な warning を持たせる。
- fallback が SEO 対象ページを薄い `200` にしないことを確認する。

## テスト

最低限、次を意図別に検証する。

1. 正常値と正常な空値。
2. 確定的な not-found。
3. upstream timeout / `5xx`。
4. schema 不一致。
5. error が空値へ変換されないこと。
6. route 境界の status / `notFound()`。
7. log や response に secret が含まれないこと。
