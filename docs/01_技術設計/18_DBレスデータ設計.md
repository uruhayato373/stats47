# DB レス データ設計（正典）

> **本ファイルが stats47 のデータ層アーキテクチャの単一正典**。
> 「ローカルビルド DB (SQLite)」「リモート D1 ハイブリッド」は本設計に**置き換えられた**。
> 旧記述（`.claude/rules/data-sqlite-ssot.md` / `17_リモートD1ハイブリッド設計.md` 等）と
> 食い違う場合は**本ファイルが優先**する。

## 0. 結論（一行）

**永続的な DB を持たない。** 本番アプリは R2 snapshot のみ読む。オーサリング/ビルドは
**R2 JSON / git の TS-config / article.md** を真実源とし、集計は**使い捨て（エフェメラル）計算**で行う。
`db:pull` による SQLite 持ち回りは**廃止**する。

## 1. なぜ DB レスか（2026-05-29 決定）

- 本番 `apps/web` は DB を一切クエリしない（R2 snapshot 配信のみ。実測: grep ヒットは型 import だけ）。
- 観測値は Phase 6 で R2 へ全面移行済（D1 肥大=解約の原因は解消済、二度と DB に戻さない）。
- 残る運用データ（数百行）のために常駐 DB を持つ費用対効果は低い。元ネタが無い Authored は
  どのみち git/R2 への JSON backup が必須 → **R2/git の JSON をそのまま SSOT にすれば DB は不要**。
- クラウドの Claude Code から R2(S3) 認証で**直接読み書きでき、db:pull 持ち回りが消える**
  （2026-05-29 に page_components の R2 直接反映で実証済）。

## 2. 全テーブルを3分類（真実源の所在で仕分ける）

| 種別 | 定義 | 真実源 / 置き場 | 該当 |
|---|---|---|---|
| **Authored** | 人/エージェントが手で作る。外部に元ネタ無し | **R2 JSON**（+ git ミラーで履歴・backup） | page_components・theme_metrics・sns_posts・affiliate_ads・categories/themes マスタ |
| **Reference** | 外部に真実源があり取り込んだだけ | **再生成**（git TS / article.md / e-Stat API / JSON） | metrics(TS registry)・articles(article.md)・estat_metainfo/estat_catalog(e-Stat)・prefectures/cities(JSON) |
| **Derived** | 他データから計算で作れる | **エフェメラル計算 → R2**（永続しない） | area_profiles・correlations |

判定フロー:

```
このデータの真実源は？
  ├─ 手作りで他に元が無い          → Authored → R2 JSON (app/... を SSOT、git にもミラー)
  ├─ git/article.md/API に元がある → Reference → 再生成 (取り込みは一時的)
  └─ 観測値等から計算できる         → Derived  → 使い捨て計算で R2 に書く
```

## 3. Authored の扱い（R2 直接 CRUD）

- **置き場 = 本番が読むのと同じ R2 キー**。例: page_components は
  `app/page-components/<pageType>/<pageKey>.json`（URL→キー対応は `r2-storage-design.md`）。
- **編集 = R2 を直接読み→マージ→書き戻す**スクリプト（S3 API、`@aws-sdk/client-s3` or `saveToR2`）。
  雛形: `apps/web/scripts/sync-theme-additions-to-r2.ts`（既存配列を取得し componentKey で冪等置換）。
- **定義の単一ソース**は git の TS（例: `apps/web/scripts/theme-page-component-additions.ts`）に置き、
  そこから R2 へ反映する。これで「手編集 JSON の散逸」を防ぎ、git で履歴・review が効く。
- **冪等**であること（同一 key は置換、再実行で壊れない）。
- 複数エージェントが同一 JSON を同時編集しないよう、**書き込みは 1 フローに直列化**する
  （トランザクションが無いため。read-modify-write の衝突回避）。

## 4. Derived の扱い（エフェメラル計算）

指標横断の SQL JOIN が要る処理（area_profile / 相関）は、**実行時に使い捨て DB を建てて捨てる**:

```ts
// build-aggregates.ts （cloud で実行、何も永続しない）
const db = new Database(":memory:");            // or /tmp/xxx.sqlite（使い捨て）
for (const m of registry) insert(db, await readStatsValues(m.key)); // R2 観測値を流し込む
const profiles = computeStrengthWeakness(db);   // 既存ロジック再利用
const corr     = computePearson(db);
await saveToR2("app/areas/.../profile.json", profiles);
await saveToR2("app/correlation/top-pairs.json", corr);
db.close();                                      // 破棄
```

- compute ロジックは既存（`packages/area-profile/.../run-batch-area-profile.ts`,
  `packages/correlation/.../calculate-pearson.ts`）。**入力を「DB select」→「R2 read」に繋ぎ替える**だけ。
- バッチ（リクエストではない）なので毎回数千 JSON を読んでも可。DuckDB なら R2 JSON を直接 JOIN 可。

## 5. Reference の扱い（再生成）

- metrics: `packages/data-configs/src/metrics/*.ts`（git）が SSOT。
- articles: `app/blog/<slug>/article.md`（R2）が SSOT。`buildArticleData()` が frontmatter から全列再構成。
- estat_catalog/metainfo: e-Stat API から取得（検索が要るなら §4 のエフェメラル DB に載せて検索）。
- prefectures/cities: `packages/area/src/data/*.json`（git）。

## 6. 移行フェーズ（段階移行・低リスク）

| Phase | 内容 | 状態 |
|---|---|---|
| ① | docs/rules/CLAUDE.md/SessionStart hook を DB レス正典に更新（本ファイル新設） | ✅ 2026-05-29 |
| ② | page_components 等 simple Authored を R2 直接化（定義 TS + sync スクリプト） | ✅ 着手済（theme charts で実証） |
| ③ | `sync-snapshots` の各 exporter の入力を DB select → R2/TS/article.md read へ繋ぎ替え | ⬜ |
| ④ | area_profile / 相関を §4 のエフェメラル計算へ（DB 永続を廃止） | ⬜ |
| ⑤ | ローカル SQLite・`db:pull`/`db:push`・`check-local-db` hook を撤去 | ⬜ |

> ③④ 完了までは旧 SQLite 経路も併存して構わない（壊さない）。ただし**新規スクリプトは DB レス経路で書く**。

## 7. 禁止事項

| NG | OK |
|---|---|
| 観測値・派生を「永続 DB」に入れる | R2（観測値）/ エフェメラル計算（派生） |
| `db:pull` の SQLite blob を SSOT として依存する新規実装 | R2 JSON / git TS を直接読む |
| Authored の手編集 JSON を散逸させる | 定義は git TS に置き、冪等スクリプトで R2 反映 |
| 本番アプリから DB を query する | R2 snapshot 経由（`fetchFromR2AsJson`） |
