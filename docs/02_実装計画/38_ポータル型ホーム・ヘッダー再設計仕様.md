## 1. 決定事項

### 1.1 採用

1. homeの暗色heroを完全撤去する。
2. homeは白基調の検索入口から開始する。
3. Headerは「ロゴ / 大きな検索 / 主要ナビ / theme toggle」に整理する。
4. homeに「カテゴリから探す」を主要セクションとして設置する。
5. 「知りたいことから探す」は既存Themeを人間向けの目的ラベルで見せる。
6. 「都道府県から探す」は `/areas` の入口として軽量に置く。
7. 注目ランキングは画像付きポータルカードにする。
8. ランキング画像は、内容一致するbuzz-map資産を第一候補、既存の決定的 `tileMapSvg` を第二候補、数値/TOP3 visualを第三候補とする。
9. 各セクションは少数の代表項目 + 「もっと見る」にし、homeへ全件を載せない。
10. URL、カテゴリ17軸、テーマSSOT、ランキングSSOTは変更しない。

### 1.2 不採用

- hero、背景写真、背景動画、大きなmarketing illustration
- ココナラの見た目・文言・商品UIの模倣
- 評価、価格、出品者、売れ筋バッジのようなmarketplace要素
- 17カテゴリ全件を同じ強さでhomeへ表示
- 2,000超のランキング全件へのAI画像生成
- SNS用画像の無条件流用
- 内容と一致しないbuzz-map画像の雰囲気利用
- 新しい分類軸の追加
- homeでの3種類以上の大規模A/B同時実験

## 2. サイト定義

Stats47を次のように定義する。

> 日本の地域データを、検索・カテゴリ・都道府県・テーマ・ランキングから探して楽しめる統計ポータル。

ページ責務:

| ページ | ユーザー向け役割 |
|---|---|
| `/` | 発見する |
| `/search` | 直接探す |
| `/ranking` / `/category/*` | 分野から探す |
| `/areas` | 地域から探す |
| `/themes` | 目的・関心から探す |
| `/ranking/[key]` | 答えと根拠を見る |
| `/blog/[slug]` | 背景・理由を読む |

内部の `category / theme / tag` 3軸は維持する。home上では次の平易なラベルへ翻訳する。

- category → `カテゴリから探す`
- theme → `知りたいことから探す`
- area → `都道府県から探す`
- ranking → `注目のランキング`
- blog → `統計を読み解く`

### 6.1 Desktop

```text
[stats47] [統計を検索........................] [ランキング] [都道府県] [テーマ⌄] [ブログ] [☀]
```

優先順位:

1. logo
2. search
3. ranking
4. areas
5. themes
6. blog
7. theme toggle

- Header高 `h-16` と1280px幅を維持。
- 検索はhome以外でも使える現行 `/search?q=` を維持。
- 検索欄はnavより視覚的に大きくするが、mobile headerへ無理に常設しない。
- categoryは新しい常設navにせず、ランキングdropdown/mega menuまたはhomeカテゴリセクションへ置く。
- theme dropdownは維持できるが、23件を平坦に見せる現状が過密なら「主要Theme + すべて見る」へ整理する。
- Headerに二段navを作らない。

### 6.2 Mobile

```text
[menu] [stats47] [search] [theme]
```

- 現行構成を基本維持。
- search iconで `/search` または検索overlayへ進む。
- drawer内は `ランキング / 都道府県 / テーマ / 統計ブログ`。
- drawerでカテゴリを展開する場合は17件をaccordion内に置く。
- 44px targetとfocusを維持。

### 6.3 Analytics

- Header link: 既存 `nav_click` / `nav_surface=desktop-header|mobile-drawer` を維持。
- Header search submit: GA4推奨 `search` eventを既存 `trackSearch` で送れるか確認。
- search event送信失敗でnavigationを止めない。
- Header再設計で既存 `nav_label` の連続性を変える場合、`.claude/rules/analytics-event-standards.md` に日付と変更内容を記録する。

### 6.4 Responsiveの設計原則

ココナラを参考に、狭い画面をdesktopの縮小版にしない。画面幅ごとに情報の優先順位を変える。

1. mobileでは「ロゴ、検索、メニュー」と最初の探索候補を最優先にする。
2. desktopの常設navはmobile drawerへ移し、headerを2段にしない。
3. カードの情報量は幅に合わせて減らすが、タイトル、主要値、遷移先は消さない。
4. 横方向carouselは「次の項目が少し見えることが発見に効く」セクションだけに限定する。
5. カテゴリのように全体を比較したい項目はcarouselにせず、mobileでも2列gridにする。
6. 横スクロールを採用する場合、scrollbar非表示だけに頼らず、次カードのpeek、`aria-label`、keyboard操作、scroll snapを備える。
7. viewport breakpointはページ構造、container queryはカードの実幅に使う。`.claude/rules/ui-components.md` の使い分けを守る。
8. JSの`window.innerWidth`でDOMを出し分けない。CSSを基本とし、SSRとhydrationを安定させる。

### 6.5 Breakpoint別の完成形

Tailwind既定のviewport breakpointと、リポジトリ固有container query（`@sm: 480px / @md: 768px / @lg: 1024px`）を混同しない。以下は受け入れ確認幅であり、新しい独自breakpointを増やす指示ではない。

| 確認幅 | Header | 冒頭検索 | Category | Ranking / Buzz | Theme | Area / Blog |
|---|---|---|---|---|---|---|
| 360〜479px | 1段、logo + search icon + menu + theme。高さを増やさない | full width、button 44px以上。人気語は横折返し | 2列、8件。iconと短いlabel中心 | 1.15枚程度見える横scrollまたは1列。画像比率固定 | 1列または1.15枚横scroll | Areaは単一CTA、Blogは1列 |
| 480〜767px | mobile構成を維持。無理にnavを出さない | full width | 2列、説明は最大2行 | 1.5〜2枚相当の横scrollまたは2列 | 2列可 | Blog 2列可 |
| 768〜1023px | logo + searchを優先し、収まる場合だけ限定nav。overflow時はmobile構成 | 最大幅を設けつつ十分広く | 4列 | 2列 | 2〜3列 | Areaはcompact、Blog 2列 |
| 1024〜1279px | desktop header。searchが可変幅、navは折返さない | 本文幅内 | 4列 | 3列 | 3列 | Blog 3列 |
| 1280px以上 | `PageShell` 1280px内。余白を広げてもcardを過剰に伸ばさない | 読みやすい最大幅 | 4列 | 4列を上限 | 3列 | Blog 4列を上限 |

実装時は既存componentの内容量を見て、表の「横scrollまたはgrid」のどちらか一方をセクションごとに決定し、同じセクション内で方式を混在させない。推奨は次の通り。

- Category: 全幅でgrid。mobile 2列、tablet/desktop 4列。
- Featured Ranking: mobile横scroll + snap、`md`以上grid。先頭カードだけ巨大化しない。
- Use Case / Theme: mobile 1列または横scrollの一方を、文章量の実測後に決定。`md`以上2〜3列。
- Buzz-map: mobile横scroll、`md`以上2列、`lg`以上3〜4列。在庫数より空columnを作らない。
- Blog: mobile 1列、`sm`以上2列、`lg`以上4列を上限。

### 6.6 Mobile header / drawerの詳細

- 360pxでlogo、検索、menu、theme toggleが重ならない。表示が厳しければtheme toggleをdrawerへ移す判断を優先する。
- search iconを押すと、専用検索ページへ即遷移するか、header直下に1行の検索panelを開く。全画面modalを新設する場合はfocus trap、Escape、閉じた後のfocus復帰を必須とする。
- drawerは開いた直後に現在地と主要4導線を理解できる順序にする。
- drawer内の17カテゴリは初期状態で全展開しない。「カテゴリから探す」のaccordionまたは一覧ページリンクに集約する。
- body scroll lock、Escape、overlay click、focus trap、route遷移後closeをtestする。
- sticky headerを維持する場合、mobile viewportの占有を抑え、Cookie bannerと重ならないことを確認する。

### 6.7 Cardのresponsive anatomy

- 画像は固定aspect-ratioで領域を予約し、幅ごとの高さ直書きを避ける。
- 360pxでもカードタイトルは最低2行まで表示し、主要値を省略しない。
- 補助説明、category、yearが過密なら、削除順は `description → secondary metadata → category`。title、主要値、リンク性は残す。
- hoverだけに情報や操作を置かない。touchでは同じ内容へ1tapで到達できる。
- card全体link内へ別button/linkをnestしない。
- horizontal listは両端のPageShell gutterと揃え、画面端へ不自然に切れないようにする。
- 画像内の文字をmobile表示の主要情報にしない。DOM textを正とする。

### 6.8 Responsive visual validation

実装前後に同じ条件でscreenshotを取り、次を比較する。画像は一時検証用なら `/tmp/` に置き、リポジトリへ残さない。

- widths: 360 / 390 / 480 / 768 / 1024 / 1280 / 1440px
- mobile portraitを必須、可能なら768px landscapeも確認
- light / dark
- 100% / 200% zoom
- menu closed / open、search focus、横scroll先頭 / 中間 / 末尾
- Cookie banner表示あり / なし
- loading、画像失敗、buzz在庫0、長い日本語title

各幅で以下を満たす。

- document幅がviewportを超えない。
- header、h1、search、最初のCategoryが初期スクロール量の中で把握できる。
- navやcard titleが意図せず1文字単位で折れない。
- section見出しと「もっと見る」の順序がscreen readerでも自然。
- 横scroll section以外に横方向overflowがない。
- 320pxは正式最適化対象外でも、破壊的な重なりや操作不能がないことをspot checkする。

## 12. Buzz-map画像の利用

### 12.1 原則

Buzz-mapはportalの視覚的差別化に使う。ただし「同じようなテーマ」ではなく、landing rankingとデータ・対象地域・年度・算式が一致するものだけを使う。

### 12.2 source優先順位

1. exact-match buzz-map card asset
2. existing `tileMapSvg`
3. deterministic top-three visual
4. deterministic comparison/number visual
5. neutral fallback（No Image文字は公開しない）

### 12.3 exact-match条件

- content ID / rankingKeyが一致
- target typeが一致（prefecture / cityを混同しない）
- data yearが一致またはカード上で明示
- normalized / rawの算式が一致
- landing URLが200かつ内容一致
- rights/provenanceが明確
- SNS投稿専用CTA、UTM、投稿日時、platform UIが画像へ焼き込まれていない

1つでも不明ならbuzz-map画像を使わず、決定的visualへfallbackする。

### 12.4 SNS画像の単純流用禁止

SNS creativeは文字量・safe area・縦横比がportal cardと異なる。元データとvisual grammarは共有し、portal card用派生を生成する。

```text
ranking/buzz data
  ├─ SNS creative
  ├─ OGP 1200x630
  └─ portal thumbnail（文字少・一覧向け）
```

別の自由promptや記事ごとの手作業画像を増やさない。既存renderer/catalogへportal surfaceを追加する。

### 12.5 データ設計

実装前に以下を監査する。

- buzz-map catalog / posts.json / asset manifest
- R2 asset key
- content_id / target_type / landing contract
- `FeaturedRankingItem` snapshot schema
- `HOME_FEATURED_RANKINGS`
- ranking thumbnail resolver
- gallery `/assets`

画像URLをruntimeで探索しない。採用assetはgit TS定義または生成時にfeatured snapshotへ焼き込む。home render時のN+1 R2 fetchを増やさない。

### 12.6 Performance

- above-the-foldの最大1〜2画像のみpriorityを検討。
- 残りはlazy。
- responsive `sizes` 必須。
- 固定aspectでCLSを防ぐ。
- SVG inlineが既存trusted generator由来の場合だけ `dangerouslySetInnerHTML`を許容。
- rasterはWebP/AVIF等の既存pipelineに合わせる。
- image 404時にcard全体を壊さずdeterministic fallback。

### 12.7 Codex MCPによるキャッチーな画像生成

注目ランキングの停止力を高めるため、Claude Codeから利用可能なCodex MCPまたは同等の画像生成connectorを使った専用visualを採用してよい。ただし、全ランキングの標準画像方式にはせず、homeでcurateする3〜8件を上限とする。実装開始時に利用可能なtool schemaと既存image pipelineを確認し、存在しないMCP名や引数を推測して呼ばない。

生成画像の責務は「感情的な入口となる背景・質感・象徴モチーフ」に限定する。統計の事実はコードで描画する。

```text
AI image layer
  背景 / 質感 / 抽象形状 / 統計テーマを連想させるモチーフ

deterministic data layer
  title / ranking / value / prefecture name / year / source / map
```

AI画像へ次を描かせない。

- 都道府県境を含む正確な日本地図
- 順位、数値、年度、出典
- 日本語タイトル、県名、細かなラベル
- ロゴ、CTA、UI部品
- 実在人物、政治家、公的機関を誤認させる表現

タイトル・数値・日本地図は既存Remotion / SVG / HTML rendererで合成する。AI画像内の文字や地理表現を正としてはならない。

### 12.8 生成対象の選定

AI visualの候補は次の条件をすべて満たすものから選ぶ。

1. home featuredまたはbuzz-mapとしてcurate済み。
2. 十分なlanding contractとprovenanceがある。
3. visual motifが統計内容と直接対応する。
4. 人口・所得・医療等のセンシティブな属性について、偏見や地域の優劣を煽らない。
5. 既存buzz-map rendererだけでは視覚的な差別化が弱い。

優先候補は、季節、観光、自然、交通、住環境、産業など象徴モチーフを安全に表現しやすいテーマとする。出生率、疾病、犯罪、所得、災害では人物や地域をステレオタイプ化せず、抽象表現を優先する。

### 12.9 Prompt contract

自由promptをpageやcomponentへ直書きしない。既存 `.claude/skills/image-prompt/` のカタログ・format規約を読み、portal thumbnail用prompt templateを1つの管理箇所へ置く。

promptには最低限次を含める。

- use case: `portal-ranking-thumbnail`
- ranking/content ID
- subject / symbolic motif
- mood / palette / brand compatibility
- aspect ratioと中央safe area
- `no text, no numbers, no labels, no logos, no UI`
- `no accurate map; leave map/data area visually quiet`
- 人物を使わない、または人物表現の条件

生成後に人が見るべき判断を自動passにしない。少なくとも文字混入、破綻した地図、意図しない人物、地域偏見、ブランド不一致を目視する。

### 12.10 Asset / provenance contract

採用した生成画像は、既存の画像資産管理方式に合わせ、次のmetadataを機械可読に関連付ける。

- asset ID
- ranking/content ID
- prompt template ID / version
- 実際のprompt
- generator / model
- generatedAt
- aspect ratio / pixel size
- review status
- rights / use restriction
- source asset key
- composite renderer version

秘密情報や一時URLをgitへ保存しない。生成物はruntime生成せず、事前生成・目視確認・圧縮後に配信する。production render中に画像生成MCPを呼ばない。

同一入力から完全再現できないgeneratorでも、prompt、model、設定、生成日時、採用結果は追跡可能にする。未承認画像、欠損画像、MCP利用不可の場合は `tileMapSvg → top3/comparison/number visual` へ戻す。

### 12.11 Portal composite

- AI背景の上に半透明overlayを無条件に重ねず、文字contrastを実測する。
- titleや数値を画像内へ焼き込む場合も、同じ情報をDOM textで保持する。
- mobile cropで主題が消えないよう、中央safe areaを定義する。
- portal用は16:9前後を基本とし、SNS 4:5や9:16からのcropを既定にしない。
- card一覧でAI visualとbuzz-map visualが混在しても、角丸、画像比率、metadata位置、data typographyを共通化する。
- 3〜8件を一度に生成した後、一覧表示で色・構図が単調または過度に派手になっていないか確認する。

## 13. 話題のデータ・バズマップsection
