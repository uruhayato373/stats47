# UI 統一・コンポーネント共通化ロードマップ

ページ間（テーマ / ランキング / カテゴリ / エリア / ブログ等）でばらついた UI を統一し、
コンポーネントを共通化・最適化するための監査結果と作業計画。Codex と並行で進めるため、
**対象範囲を Phase 単位で切り分け、同一ファイルの同時編集を避ける**（git 競合防止）。

正典: `docs/01_技術設計/15_デザインシステムSSOT.md` / `13_統一レイアウト設計.md`。
本書はそれを「いつ・どの順で・どこまで」適用するかの実行計画。

## 再発防止アーキテクチャ（拡張してもスパゲッティ化しない仕組み）

> 行動原則 5「モデルは判断時のみ。決定的なものはコードで処理する」。
> **再発防止をエージェントの"記憶"に依存しない**（agent は忘れ・drift する）。機械で検出できる逸脱は機械で弾き、
> agent は機械が判定できない意味的残余だけ担う。3 層の defense-in-depth で、誰が(人/Claude/Codex/将来 agent)書いても破綻させない。

| 層 | 仕組み | 捕まえるもの | 状態 |
|---|---|---|---|
| **① 決定的 lint（pre-commit + CI）** | ESLint `no-restricted-imports`（feature 横断結合・内部直 import 禁止）/ `check-design-system.mjs`（カード枠直書き・shadcn Card 直 import・shadow-lg・bg-white・rounded-xl・text-black・page.tsx 幅・色集約）/ `check-r2-route-ssg` / `svg-lint` 等 | 構文的逸脱（書いた主体に依存せず弾く＝最も durable な契約） | ✅ 稼働（本セッションで CI 配線 + ルール拡張） |
| **② エージェントゲート（意味判定）** | `ui-consistency-reviewer`（横断一貫性 + デザイン SSOT drift 番人）/ `ui-reviewer`（melta-ui パネル）/ `code-reviewer` | 「既存の共有部品と重複していないか」「tier ② か ③ か」等、lint で書けない意味的判断 | ✅ 稼働 |
| **③ SSOT 文書（共有の脳）** | `15_デザインシステムSSOT.md` / `ui-components.md`（配置 3 tier）/ `chart-component-standards.md` | ①②が参照する単一基準。人も agent も Codex もここを読む | ✅ |

**設計原則（なぜ機械が主・agent が従か）**: agent に「規約を覚えさせる」のは**主防御にしない**。agent が忘れても
**CI が PR を止める**＝lint が契約、agent 記憶は利便。`nextjs-ssg-preservation.md` と同じ思想（機械検知が主、
ESLint で書けない意味差だけ agent）。

**継続改善でやること（gap だけ）**:
- **lint カバレッジ拡大**: ①の検出対象を漏れなく広げる（app 全ルール化=0-6 / カード亜種 census / 配置 tier 違反）。
- **allowlist を増やさない**: 既存債務の grandfather は許すが**増殖を禁止**（allowlist 行数の上限ガード）。是正で減らす。
- **agent contract への配線**: UI 系 executor（`ranking-ui-manager`/`theme-ui-manager`/`chart-component-builder`）の
  「必読 rules」に `15` + 配置 tier を明記し、ハンドオフ前に `design-system:check` を自走させる（②の補助。主防御は①）。

## Phase 2: hero / header パターンの統合（③-A）✅ 完了 (2026-06-23)

3 つの「ページ見出し」実装を 1 系統に集約した。

- `PageHeader`（標準・ミニマル）/ `RankingHeroCard`（2列スタット+正規化ピル）/ `ThemeAreaHeader`（PageHeader+県セレクタ）
- → **`PageHeader` を基盤に、後方互換の任意 slot（`meta` / `controls` / `aside`）で拡張**して統合。
- 各ページは slot 注入で差分表現する。`PageHeader` 本体は白基調のまま（暗色グラデ/bg-white を足さない）。

**実装 (2026-06-23)**:
- `PageHeader` に optional slot 3 つを追加: `meta`（title 直下の出典/年度/更新行）/ `controls`（header ブロック下の操作行）/ `aside`（右カラム。指定時のみ lg で 2 カラム grid 化）。全 slot 未指定時は既存 19 利用と DOM 不変（後方互換）。
- `RankingHeroCard` を「PageHeader + slot 合成」へ作り替え。インライン `#f5f8ff` グラデと `bg-white` を除去。暗色 KPI 面は `RankingHeroStat.tsx`（presentational 子）へ抽出し `aside` slot へ注入（リッチさ維持＝意図的 `bg-slate-900` variant）。正規化ピル群+モバイル Select+メタ操作行は `controls` slot へ。既存 props/挙動・stats 算出ロジックは完全保持。
- `check-design-system.mjs` の allowlist から `RankingHeroCard.tsx`（37 行目 `bg-white` grandfather）を削除。年バッジの `bg-white/15` は `bg-slate-700/60` に置換（暗色面の白除去）。違反 0。

**学び**:
- **ThemeAreaHeader は既に正規パターン**だった（PageHeader を actions slot で合成済）。一切変更せず実証として残置。
- **真の逸脱は RankingHeroCard 1 件のみ**。PageHeader 非使用・独自 2 列グリッド・インライングラデ・暗色 KPI。
- **暗色 KPI 面は意図的 variant として維持**（minimalize しない）。`bg-slate-900` は bg-white ルール非該当で許容。slot 合成（actions=theme / aside+controls=ranking）が独自 hero を廃しつつリッチさを両立する正解。

**検証**: `npx tsc --noEmit -p apps/web/tsconfig.json` green / `node apps/web/scripts/check-design-system.mjs` 違反 0（allowlist 削除後）/ slot 未指定時の PageHeader DOM 不変。

**担当**: `chart-component-builder` + `ui-consistency-reviewer`。

各統合は **1 クラスタ = 1 PR** で小さく回す。`chart-component-standards.md` のカタログを都度更新。

> **Phase 3 の原則（3 クラスタ検証で実証・★最重要）**: 監査が挙げる「重複」は **まず実装を読んで「本当に同一用途か」を検証**する。
> 実測では **3 クラスタ中 1 つ(関連記事)だけが本物の重複** で、残り 2 つ(関連ランキング/空状態)は非重複だった。
> - 本物の重複は多くが「**データ層は重複・presentation は文脈ごとに正当に異なる**」→ 正しい統合は **共有コンポーネントでなく共有ロジック(fetcher/util)**。
> - **コードベースは監査(エージェント推定)が示唆したほどスパゲッティではない**。共有基盤(`SurfaceCard`/`ChartState`/`ChartPanel`/`RailCard`)は既に厚い。
> - よって Phase 3 は「クラスタを機械的に潰す」のでなく **検証して本物だけ直す**。無理な統合は leaky abstraction を生むため**やらないことも成果**。
>
> **4 クラスタ検証後の結論 (2026-06-23)**: 関連記事=本物(統合済)・関連ランキング/空状態/選択UI=非重複。
> **本物の重複は 4 中 1**。残り未検証(サイドバー/コロプレス節/パンくず)も「既に primitive 共有・presentation 正当差」の
> 公算が高い。→ **Phase 3 はほぼ完了扱い**。残りは個別に気づいた時点で 1 PR 是正。
> 機械的な全クラスタ消化より、Phase 2(hero の実在 divergence) / Phase 4(ブログ SVG 実在 backlog 209枚) が高 ROI。

## サイト全体の統一感をどう担保するか（最重要）

統一感はページ専任エージェントを増やすことでは保てない（基準が割れる）。
**単一 SSOT + 単一の横断ゲート + 決定的チェック**の 3 点に集約して担保する。

1. **単一の判断基準** — Claude / Codex / 全レビュアーが必ず `15_デザインシステムSSOT.md` を読む
   （`AGENTS.md`→`CLAUDE.md` symlink + `.claude/rules/` 共有）。判断が分岐しない。
2. **横断ゲートが 1 つ** — `ui-consistency-reviewer` がページ種を問わず**全 PR を同一基準で**review し、
   `15` との drift（パターン変更時の SSOT 更新漏れ）を BLOCK する。develop→main 前に必ず通す。
3. **決定的チェック** — トークン違反は grep で機械検出し 0 件を維持（下記 検証コマンド）。

> 一般ページ（home / category / areas / blog / survey / tag）には専任 UI manager を**新設しない**。
> ranking/theme 以外は `ui-consistency-reviewer` 主導の横断是正対象として扱う（CLAUDE.md「シンプル最優先」）。
> 専任 manager は「横断ゲートで回らない」と実証されたときに初めて検討する。

## エージェント分業（既存を再利用・新設しない）

executor↔critic の分業は既存 37 体構成に実装済み。新規エージェントは作らず、ドライバ（Claude / Codex）を
役割に割り当てる。両者とも同じ SSOT を読むため判断は揃う。

| 対象 | 実装（write）executor | Review / テスト（read-only）critic |
|---|---|---|
| ランキング UI | `ranking-ui-manager` | `ui-consistency-reviewer` + `code-reviewer` + `tdd-guide` |
| テーマ UI | `theme-ui-manager` | 同上 |
| 共有チャート部品 | `chart-component-builder` | `ui-reviewer`（melta-ui）+ `ui-consistency-reviewer` |
| page_components | `theme-component-builder` | `ui-reviewer` |
| ブログ SVG / 系譜 | `chart-author` | `blog-critic` |
| デザイン SSOT 文書 | 変更を入れた実装 agent が同一 PR で更新 | `ui-consistency-reviewer`（drift 番人） |

### Codex / Claude ドライバ割り当て（モデル A: 実装/レビュー分離）

- **Claude = 実装ドライバ**: 上記 executor で Phase を write。
- **Codex = Review ドライバ**: 同じ SSOT を根拠に差分 review + テスト（別 worktree）。
- PR ごとに役割交代も可。原則は **executor ≠ critic**（実装した側が単独で自分を採点しない）。
- `.claude/agents/*.md` は Claude のサブエージェント。Codex はこれを直接呼ばないが、`.claude/rules/` と
  `15` を読むため verdict 基準は一致する。

## 実行順とブランチ規律

1. **Phase 1 → 2 → 3** は依存順（骨格→hero→部品）。Phase 4 は独立に並行可。
2. Codex と同時に走る場合、**Phase（=対象ディレクトリ群）で担当を分割**し worktree を分ける
   （`CLAUDE.md` の git race 注意）。
3. デプロイは溜めて 1 回（`branch-workflow.md`）。各 Phase は localhost で確認し、まとまりで develop→main。
4. 各 Phase 完了時に `15_デザインシステムSSOT.md` のカタログ/例外を更新（drift 防止）。
