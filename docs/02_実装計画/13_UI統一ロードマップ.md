# UI 統一・コンポーネント共通化ロードマップ

ページ間（テーマ / ランキング / カテゴリ / エリア / ブログ等）でばらついた UI を統一し、
コンポーネントを共通化・最適化するための監査結果と作業計画。Codex と並行で進めるため、
**対象範囲を Phase 単位で切り分け、同一ファイルの同時編集を避ける**（git 競合防止）。

正典: `docs/01_技術設計/15_デザインシステムSSOT.md` / `13_統一レイアウト設計.md`。
本書はそれを「いつ・どの順で・どこまで」適用するかの実行計画。

## 監査サマリ (2026-06-23 実測)

| 層 | 状態 | 根拠 |
|---|---|---|
| **① デザイントークン層** | ✅ 良設計 | 全色 `hsl(var(--x))` セマンティック・`--radius:0` でフラット強制・dark/light 完備・system フォント。`rounded-xl/2xl`=0・`shadow-lg/2xl`=0・`text-black`=0 |
| **② shadcn プリミティブ層** | ✅ 単一ソース | new-york 30 個を `@stats47/components`(`packages/components/src/atoms/ui`) に集約・重複ゼロ |
| **③ レイアウト/シェル層** | ✅ 完了 (Phase 1) | `PageShell` を全主要ページで使用。ranking 詳細の独自グリッドも統一済 |
| **④ 中間層（app-local composite）** | 🔴 **未統制（最大ブロッカー）** | Card が 24 亜種・3 箇所に散在（`components/{surface,charts,stat-charts}`）。`@/components/{surface,charts}` が実質 180+ import の中核ハブだが「共有 tier」として未文書。atomic taxonomy(atoms/molecules/organisms) が形骸化し実態と不一致 |
| **⑤ feature 重複層** | 🔴 未着手 | hero/sidebar/related/選択UI 等 10 クラスタの並行実装。共有抽象なし（Phase 2-3 で対応） |
| **⑥ ブログ見栄え層** | 🔴 大きな負債 | SVG 612 枚中 34%(209) が元データ消失で再生成不可。是正キュー 140 記事（Phase 4） |
| **shadcn CLI 設定** | 🔴 footgun | `components.json` の `ui` alias が空 dir を指し `shadcn add` が誤 location（Phase 0 で是正） |

→ **トークン/プリミティブの土台は優秀**。だが**中間層（④）が未統制**で、これが Phase 2-3 の共通化を「もぐら叩き」にする根本原因。
**Phase 0（基盤ガバナンス）で構造を先に整えてから Phase 2-3 に進む**のが継続改善の前提。

## Phase 0: 基盤ガバナンス（横断・Phase 2-3 の前提）

中間層の構造的負債を先に解消し、共通化が持続的に効く状態を作る。症状（hero/sidebar 重複）でなく**根本原因**を直す。

| # | 課題 | 是正方針 | 状態 |
|---|---|---|---|
| 0-3 | `components.json` の `ui` alias が空の app-local を指す（`shadcn add` 誤 location footgun） | shadcn primitives の置き場を `packages/components` に確定。`packages/components/components.json` を新設し `cd packages/components && npx shadcn add` を README 化。app の `ui` alias を実体（`@stats47/components/atoms/ui`）に修正 | ✅ 完了 (2026-06-23) |
| 0-2 | `@/components/{surface,charts}` が実質共有ハブ（180+ import）なのに**配置 tier が未文書**。atomic taxonomy が形骸化 | 配置 tier を明文化: ① プリミティブ=`@stats47/components` / ② 共有 composite=`@/components/{surface,charts,stat-charts,layout}`（=正式な共有層）/ ③ feature 固有。`ui-components.md`「コンポーネント配置の 3 tier」に追加、doc 15 から相互リンク。**Card 再実装の禁止規約は doc 15 に既存だった**（=文書ギャップでなくコード追従ギャップと判明） | ✅ 完了 (2026-06-23) |
| 0-1 | Card が 24 亜種・3 tier に散在。**doc 15 が既に再実装を禁じているのにコードが未追従** | 既存 SSOT（doc 15 Surface/Card）に**コードを追従**させる。feature/各 tier の独自カード枠を基底（① `Card` / ② `SurfaceCard` / `ChartPanel`）経由に置換。新規抽象は作らず既存採用部品へ寄せる | ⬜ 次（中規模・Phase 2/3 の前提） |
| 0-4 | 非チャート UI のハードコード残（例 `RankingHeroCard` の `#f5f8ff` グラデ等 8 箇所） | トークン化（`hsl(var(--x))`）。チャート内の static SVG/D3 hex は規約上許容なので対象外 | ⬜ |
| 0-5 | 配置 tier・カード禁止が**人手レビュー頼み** | 0-2 の tier 定義を**決定的 lint 化**（feature 間 import 禁止・カード枠の直書き検出 等）。`ui-consistency-reviewer` の手動チェックを機械化 | ⬜ |

**実行順**: ✅ 0-3 / 0-2（設定・文書。低リスク・完了）→ **0-1（Card のコード追従。中規模）** → 0-4（トークン残）→ 0-5（lint 化）。
**担当**: `chart-component-builder`（Card 追従）+ `ui-consistency-reviewer`（tier・lint）。
**検証**: 各是正後に `@stats47/components`/`SurfaceCard` import 比率の上昇 / 独自 Card 定義箇所の減少を実測。

> **0-1 と Phase 2 の関係**: Phase 2(hero 統合)・Phase 3(sidebar/related 統合)は、0-1 で基底カードへ寄せておかないと各々が別の card 上に再構築され重複が残る。**0-1 → Phase 2/3 の順**を守る。
> **重要な発見**: 0-2 で「文書が足りない」のではなく「**文書（doc 15）はあるのにコードが追従していない**」と判明。よって残りは新規ルール作成でなく **既存 SSOT への是正 + lint 化** が本質。

## Phase 2: hero / header パターンの統合（③-A）

3 つの「ページ見出し」実装を 1 系統に集約する。

- `PageHeader`（標準・ミニマル）/ `RankingHeroCard`（2列スタット+正規化ピル）/ `ThemeAreaHeader`（PageHeader+県セレクタ）

**担当**: `chart-component-builder` + `ui-consistency-reviewer`。

## サイト全体の統一感をどう担保するか（最重要）

統一感はページ専任エージェントを増やすことでは保てない（基準が割れる）。
**単一 SSOT + 単一の横断ゲート + 決定的チェック**の 3 点に集約して担保する。

1. **単一の判断基準** — Claude / Codex / 全レビュアーが必ず `15_デザインシステムSSOT.md` を読む
   （`AGENTS.md`→`CLAUDE.md` symlink + `.claude/rules/` 共有）。判断が分岐しない。
2. **横断ゲートが 1 つ** — `ui-consistency-reviewer` がページ種を問わず**全 PR を同一基準で**review し、
   `15` との drift（パターン変更時の SSOT 更新漏れ）を BLOCK する。develop→main 前に必ず通す。
3. **決定的チェック** — トークン違反は grep で機械検出し 0 件を維持（下記 検証コマンド）。

> 一般ページ（home / category / areas / blog / survey / tag）には専任 UI manager を**新設しない**。
> ranking/theme 以外は `ui-consistency-reviewer` 主導の横断是正対象として扱う（CLAUDE.md「シンプル最優先」）。
> 専任 manager は「横断ゲートで回らない」と実証されたときに初めて検討する。

## エージェント分業（既存を再利用・新設しない）

executor↔critic の分業は既存 37 体構成に実装済み。新規エージェントは作らず、ドライバ（Claude / Codex）を
役割に割り当てる。両者とも同じ SSOT を読むため判断は揃う。

| 対象 | 実装（write）executor | Review / テスト（read-only）critic |
|---|---|---|
| ランキング UI | `ranking-ui-manager` | `ui-consistency-reviewer` + `code-reviewer` + `tdd-guide` |
| テーマ UI | `theme-ui-manager` | 同上 |
| 共有チャート部品 | `chart-component-builder` | `ui-reviewer`（melta-ui）+ `ui-consistency-reviewer` |
| page_components | `theme-component-builder` | `ui-reviewer` |
| ブログ SVG / 系譜 | `chart-author` | `blog-critic` |
| デザイン SSOT 文書 | 変更を入れた実装 agent が同一 PR で更新 | `ui-consistency-reviewer`（drift 番人） |

### Codex / Claude ドライバ割り当て（モデル A: 実装/レビュー分離）

- **Claude = 実装ドライバ**: 上記 executor で Phase を write。
- **Codex = Review ドライバ**: 同じ SSOT を根拠に差分 review + テスト（別 worktree）。
- PR ごとに役割交代も可。原則は **executor ≠ critic**（実装した側が単独で自分を採点しない）。
- `.claude/agents/*.md` は Claude のサブエージェント。Codex はこれを直接呼ばないが、`.claude/rules/` と
  `15` を読むため verdict 基準は一致する。

## 実行順とブランチ規律

1. **Phase 1 → 2 → 3** は依存順（骨格→hero→部品）。Phase 4 は独立に並行可。
2. Codex と同時に走る場合、**Phase（=対象ディレクトリ群）で担当を分割**し worktree を分ける
   （`CLAUDE.md` の git race 注意）。
3. デプロイは溜めて 1 回（`branch-workflow.md`）。各 Phase は localhost で確認し、まとまりで develop→main。
4. 各 Phase 完了時に `15_デザインシステムSSOT.md` のカタログ/例外を更新（drift 防止）。
