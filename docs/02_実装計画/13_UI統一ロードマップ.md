# UI 統一・コンポーネント共通化ロードマップ

ページ間（テーマ / ランキング / カテゴリ / エリア / ブログ等）でばらついた UI を統一し、
コンポーネントを共通化・最適化するための監査結果と作業計画。Codex と並行で進めるため、
**対象範囲を Phase 単位で切り分け、同一ファイルの同時編集を避ける**（git 競合防止）。

正典: `docs/01_技術設計/15_デザインシステムSSOT.md` / `13_統一レイアウト設計.md`。
本書はそれを「いつ・どの順で・どこまで」適用するかの実行計画。

## 監査サマリ (2026-06-23 実測)

| 層 | 状態 | 根拠 |
|---|---|---|
| **① デザイントークン層** | ✅ ほぼ完了 | features/components で `rounded-xl/2xl`=0・`shadow-lg/2xl`=0・`text-black`=0・ハードコード hex=0。`page.tsx` の `container mx-auto`/`max-w-[` 直書き=0 |
| **② レイアウト/シェル層** | 🟡 部分的 | `PageShell` 採用 22/24 page.tsx。未採用 2 件（ranking 詳細・areas themeSlug）は独自シェル/委譲 |
| **③ コンポーネント重複層** | 🔴 未着手 | hero/sidebar/related/card/選択UI 等で 10 クラスタの並行実装が併存 |
| **④ ブログ見栄え層** | 🔴 大きな負債 | SVG 612 枚中 34%(209) が元データ消失で再生成不可。是正キュー 140 記事 |

→ **低レベルのトークン是正は完了済み**。残作業は「構造の一貫性」と「コンポーネント統合」、そして「ブログの体系的な見栄え改善」の 3 本。

## Phase 1: レイアウト/シェルの完全統一（②）

最優先。ページの骨格が揃っていないと以降の共通化が効かない。

| # | 課題 | 対象 | 是正方針 |
|---|---|---|---|
| 1-1 | ranking 詳細が独自グリッドを再実装（`container`+`lg:flex` を `RankingKeyPageClient` 内に直書き、`RankingPageSidebarLayout` は幅 300px/lg breakpoint） | `features/ranking/components/RankingKeyPage/*` | `PageShell` + `rightRail` 経由に移行。独自グリッド廃止 |
| 1-2 | 右レールが 2 系統併存（`RankingPageSidebarLayout` lg/300px vs `RightRailWidgets` xl/360px/max-h） | ranking vs area/tag | `RightRailWidgets`（=`PageShell` rightRail）に一本化。幅/breakpoint/overflow を統一 |
| 1-3 | blog 詳細が `PageHeader` を使わず inline `<h1>`、`rightRailBreakpoint="lg"` を独自指定 | `app/blog/[slug]/page.tsx` | header パターンを共有化（記事タイトルは reading variant の規定 header に） |
| 1-4 | theme は leftRail+`ThemeAreaHeader`、areas は rightRail+`RightRailWidgets` で左右非対称 | theme-dashboard vs area-profile | レール位置のポリシーを SSOT に明文化し片側へ寄せる |

**検証**: `next build` で SSG/ƒ 区分が変わらないこと（ranking/areas は `ƒ` 維持、`nextjs-ssg-preservation.md`）。
**担当**: `ranking-ui-manager` / `theme-ui-manager` / `ui-consistency-reviewer`。

## Phase 2: hero / header パターンの統合（③-A）

3 つの「ページ見出し」実装を 1 系統に集約する。

- `PageHeader`（標準・ミニマル）/ `RankingHeroCard`（2列スタット+正規化ピル）/ `ThemeAreaHeader`（PageHeader+県セレクタ）
- → **`PageHeader` を基盤に、任意の KPI タイル slot・コントロール slot を持つ拡張**へ統合。
- 各ページは slot 注入で差分表現（独自 hero コンポーネントを廃止）。

**担当**: `chart-component-builder` + `ui-consistency-reviewer`。

## Phase 3: 反復コンポーネントの共通化（③-B）

Phase 1-2 で骨格が揃った後に実施。重複クラスタを基盤部品へ集約する。

| クラスタ | 併存実装 | 統合先 |
|---|---|---|
| 関連ランキング | ranking `RelatedRankingsGrid` / `RankingSidebarClient` / blog `RelatedRankingsSection` | 共有 `RelatedContentGrid` |
| 関連記事 | ranking `RelatedArticlesCard` / area `AreaRelatedBlogArticles` / theme `ThemeRelatedArticles` | slot ベース `RelatedArticles` |
| サイドバー | `RankingSidebarClient` / `AreaProfileSidebar` / `ThemeSidebar` | `FeatureSidebar` 基盤 |
| 選択 UI | `PrefectureSelect` / `RegionSelector` / `RankingYearSelector` | 汎用 `Selector` |
| チャートカード枠 | `StatsChartCard` / `ChartPanel` / `KpiCard` | `ChartPanel` バリアント |
| コロプレス節 | depopulation / region-comparison / theme-dashboard の各 Section | `MapSectionWrapper`（描画は共有 `DivergingChoroplethMap`） |
| パンくず | `CityBreadcrumbs` / `RankingPageBreadcrumbs` | `Breadcrumb` ユーティリティ |
| 空/notFound/loading | `ComparisonEmpty` / `ChartState` / `MapFallback` | `StateContainer` |

各統合は **1 クラスタ = 1 PR** で小さく回す。`chart-component-standards.md` のカタログを都度更新。

## Phase 4: ブログ記事の見栄え改善（④）

`blog-quality-standards.md` / `blog-data-schema.md` が正典。並行して進められる独立トラック。

- **4-1 SVG データ系譜の復元**（`.claude/state/blog/svg-lineage-queue.json`）
  - `source-backfill`(22) → `ssot-restore`(46) → `ssot-restore-new`(87) → `manual`(76) の軽い順。
  - 新規記事は generator が `source.json` をセット出力済（再発防止は実装済）。
- **4-2 カード型ランキング/タイルマップの統一再生成**（上位5+下位5・600×700 地図）
  - `regenerate-ranking-cards.mjs` / `regenerate-tile-maps.ts`。
- **4-3 是正キュー消化**（`remediation-queue.json` 140 記事）
  - GSC 流入 × 品質 blocker 順に `/brushup-blog --target queue` → blog-critic PASS。
- **4-4 blog 詳細ページの header/レール統一**（Phase 1-3 と整合）。

**担当**: `chart-author`（系譜復元）/ `article-writer` + `blog-critic`（記事是正）。

## 実行順とブランチ規律

1. **Phase 1 → 2 → 3** は依存順（骨格→hero→部品）。Phase 4 は独立に並行可。
2. Codex と同時に走る場合、**Phase（=対象ディレクトリ群）で担当を分割**し worktree を分ける
   （`CLAUDE.md` の git race 注意）。
3. デプロイは溜めて 1 回（`branch-workflow.md`）。各 Phase は localhost で確認し、まとまりで develop→main。
4. 各 Phase 完了時に `15_デザインシステムSSOT.md` のカタログ/例外を更新（drift 防止）。
