# UI 統一・コンポーネント共通化ロードマップ

ページ間（テーマ / ランキング / カテゴリ / エリア / ブログ等）でばらついた UI を統一し、
コンポーネントを共通化・最適化するための監査結果と作業計画。Codex と並行で進めるため、
**対象範囲を Phase 単位で切り分け、同一ファイルの同時編集を避ける**（git 競合防止）。

正典: `docs/01_技術設計/15_デザインシステムSSOT.md` / `13_統一レイアウト設計.md`。
本書はそれを「いつ・どの順で・どこまで」適用するかの実行計画。

## Phase 2: hero / header パターンの統合（③-A）

3 つの「ページ見出し」実装を 1 系統に集約する。

- `PageHeader`（標準・ミニマル）/ `RankingHeroCard`（2列スタット+正規化ピル）/ `ThemeAreaHeader`（PageHeader+県セレクタ）
- → **`PageHeader` を基盤に、任意の KPI タイル slot・コントロール slot を持つ拡張**へ統合。
- 各ページは slot 注入で差分表現（独自 hero コンポーネントを廃止）。

**担当**: `chart-component-builder` + `ui-consistency-reviewer`。

## サイト全体の統一感をどう担保するか（最重要）

統一感はページ専任エージェントを増やすことでは保てない（基準が割れる）。
**単一 SSOT + 単一の横断ゲート + 決定的チェック**の 3 点に集約して担保する。

1. **単一の判断基準** — Claude / Codex / 全レビュアーが必ず `15_デザインシステムSSOT.md` を読む
   （`AGENTS.md`→`CLAUDE.md` symlink + `.claude/rules/` 共有）。判断が分岐しない。
2. **横断ゲートが 1 つ** — `ui-consistency-reviewer` がページ種を問わず**全 PR を同一基準で**review し、
   `15` との drift（パターン変更時の SSOT 更新漏れ）を BLOCK する。develop→main 前に必ず通す。
3. **決定的チェック** — トークン違反は grep で機械検出し 0 件を維持（下記 検証コマンド）。

> 一般ページ（home / category / areas / blog / survey / tag）には専任 UI manager を**新設しない**。
> ranking/theme 以外は `ui-consistency-reviewer` 主導の横断是正対象として扱う（CLAUDE.md「シンプル最優先」）。
> 専任 manager は「横断ゲートで回らない」と実証されたときに初めて検討する。

## エージェント分業（既存を再利用・新設しない）

executor↔critic の分業は既存 37 体構成に実装済み。新規エージェントは作らず、ドライバ（Claude / Codex）を
役割に割り当てる。両者とも同じ SSOT を読むため判断は揃う。

| 対象 | 実装（write）executor | Review / テスト（read-only）critic |
|---|---|---|
| ランキング UI | `ranking-ui-manager` | `ui-consistency-reviewer` + `code-reviewer` + `tdd-guide` |
| テーマ UI | `theme-ui-manager` | 同上 |
| 共有チャート部品 | `chart-component-builder` | `ui-reviewer`（melta-ui）+ `ui-consistency-reviewer` |
| page_components | `theme-component-builder` | `ui-reviewer` |
| ブログ SVG / 系譜 | `chart-author` | `blog-critic` |
| デザイン SSOT 文書 | 変更を入れた実装 agent が同一 PR で更新 | `ui-consistency-reviewer`（drift 番人） |

### Codex / Claude ドライバ割り当て（モデル A: 実装/レビュー分離）

- **Claude = 実装ドライバ**: 上記 executor で Phase を write。
- **Codex = Review ドライバ**: 同じ SSOT を根拠に差分 review + テスト（別 worktree）。
- PR ごとに役割交代も可。原則は **executor ≠ critic**（実装した側が単独で自分を採点しない）。
- `.claude/agents/*.md` は Claude のサブエージェント。Codex はこれを直接呼ばないが、`.claude/rules/` と
  `15` を読むため verdict 基準は一致する。

## 実行順とブランチ規律

1. **Phase 1 → 2 → 3** は依存順（骨格→hero→部品）。Phase 4 は独立に並行可。
2. Codex と同時に走る場合、**Phase（=対象ディレクトリ群）で担当を分割**し worktree を分ける
   （`CLAUDE.md` の git race 注意）。
3. デプロイは溜めて 1 回（`branch-workflow.md`）。各 Phase は localhost で確認し、まとまりで develop→main。
4. 各 Phase 完了時に `15_デザインシステムSSOT.md` のカタログ/例外を更新（drift 防止）。
