# テーマ指標×チャート改善運用

## 目的

テーマページごとに「読者の問いに答える指標か」「そのデータ形状を正しく伝えるチャートか」を再審査し、提案と Claude Code の実装を分離しながら、`ThemeCatalog` SSOT へ確実に反映する。

新しい管理層は作らない。既存の `packages/data-configs/src/theme-catalog/<key>.ts` を唯一の実装SSOTとし、本文書は運用フローと完了条件の正典とする。

## 現状ベースライン

2026-07-11 時点:

- 公開テーマ: 22（`ALL_THEMES`）
- `ThemeCatalog` 移行済み: 20
- legacy/別経路: `climate`、`local-finance-city`
- catalog validator: **error 0 / warn 230**
  - `no-selection`: 154
  - `dup-sortorder`: 44
  - `primary-orphan`: 28
  - `dup-key-global`: 4
- 20テーマの `selection` と `rejectedCandidates` は実質未記入

このため、当面の優先順位は「指標数を増やす」より「現在の選定と表現を証拠付きで確定する」とする。

## 採用する仕組み

```text
Theme brief
  ↓ 1. 読者の問いを固定
Official research
  ↓ 2. 白書・統計調査・データ実在確認
Proposal sheet
  ↓ 3. 採用/不採用、role、chart、表示順を提案
Human approval
  ↓ 4. 指標とストーリーの採否を確定
Claude Code
  ↓ 5. ThemeCatalog SSOT のみを編集
Code generation
  ↓ 6. IndicatorSet + page-components JSON を生成
Deterministic checks
  ↓ 7. catalog/config/type/test 検証
Local visual QA
  ↓ 8. 各幅・データなし・凡例・出典・アクセシビリティ
R2/deploy (separate approval)
  ↓ 9. まとめて1回だけ反映、本番実測
Evidence log
     10. 利用率・GSC・表示品質で継続/改定判定
```

### 工程1: Theme brief（人間と提案側）

1テーマにつき、先に次を固定する。

- 主読者: 一般読者 / 移住検討 / 企業・政策 / メディア等
- 主問: このページを見終わった時に、何が分かれば成功か
- 比較軸: 地域差 / 時系列 / 内訳 / 関係 / 将来推計のどれか
- 誤読リスク: 実数と率、比率の分母、年度差、因果と相関、予測と実績
- 上限: primary 1〜3、secondary 3〜8、主要チャート 3〜6。説明できない指標を数合わせで入れない

### 工程2: 調査ゲート（提案側）

候補指標ごとに以下を埋める。一つでも不明なら「採用」にしない。

| 項目 | 必須内容 |
|---|---|
| reader question | どの問いへ答えるか |
| rankingKey | `METRICS_REGISTRY` に実在するか |
| definition | 分子、分母、単位、対象範囲 |
| coverage | 47都道府県、利用可能年、欠損 |
| freshness | 最新年と更新周期 |
| source | 原則として公式・一次資料 URL |
| selection | `proposedBy/sourceUrl/surveyedAt/rationale` |
| caveat | 比較不可年、制度変更、誤読リスク |

新規 metric が必要な場合は、この工程で実装せず `docs/todo/03_指標バックログ.md` へ候補として入れる。e-Stat 実在確認とデータ投入は別タスクとする。

### 工程3: チャート選定（提案側）

| 問い | データ形状 | 第1候補 | 不適切な例 |
|---|---|---|---|
| 現在値はどれくらいか | 1指標×1時点 | `kpi-card` | 数値1個のための円グラフ |
| どう変わったか | 1〜2指標×時系列 | `line-chart` | 時系列の donut |
| 規模と率はどう動くか | 単位の異なる2指標×時系列 | `mixed-chart` | 同一Y軸で単位を混在 |
| 何で構成されるか | 複数セグメント×時系列 | `composition-chart` | 多時点の複数円グラフ |
| 最新年の内訳は何か | 複数セグメント×1時点 | `donut-chart` | カテゴリが多すぎる donut |
| 男女×年齢構造はどうか | 年齢階級×性別 | `pyramid-chart` | 通常の折れ線 |
| 指標間に関係があるか | 2変量×47地域 | 現行theme rendererに一般散布図なし | 相関を因果と記述 |

散布図、コロプレス、ランキング棒を page-component に必要と判断した場合は、カタログに未定義文字列を入れない。チャート追加案として切り出し、renderer、props型、catalog union、アクセシビリティ、テストを1PRで追加する。

### 工程4: Proposal sheet（提案側）

1テーマ1ファイルの作業用レビューを `docs/04_レビュー/<date>-theme-<key>.md` に作る。必須表は次の3つ。

1. 現行指標の判定: `keep / change-role / replace / remove`
2. チャートの判定: `keep / revise-props / replace / remove / new-component`
3. 不採用候補: `rankingKey / reason / reconsider condition`

各提案に「問い」「根拠URL」「利点」「誤読リスク」「実装差分」を書く。採否が決まる前に catalog を編集しない。

### 工程5: Claude Code への実装契約

人間が Proposal sheet の採否を確定した後、Claude Code へ次を渡す。

```text
対象: <theme-key>
正典: docs/04_レビュー/<date>-theme-<key>.md の「採用決定」
編集先: packages/data-configs/src/theme-catalog/<key>.ts のみ
禁止: indicator-sets/*.ts / page-components/*.json の手編集
要件:
- metrics の role/selection を決定通り反映
- 不採用は rejectedCandidates へ記録
- charts の componentType/componentProps/relatedRankingKeys/source/sortOrder を反映
- 既存で表現できない場合は勝手に近似せず停止して報告
完了条件:
- generate:catalog 後の生成物を同時反映
- validate:catalog --strict で対象テーマの warn 0
- validate:config / type-check / 対象test が成功
- localhost の指定幅で見た目とデータなし状態を確認
```

### 工程6: 生成と決定的検証（Claude Code）

```bash
npm run generate:catalog --workspace=@stats47/data-configs
npm run validate:catalog --workspace=@stats47/data-configs -- --strict
npm run validate:years --workspace=@stats47/data-configs
npm run validate:config --workspace=@stats47/data-configs
npm run type-check --workspace=@stats47/data-configs
npm run type-check --workspace apps/web
npm run test:run --workspace apps/web
```

`--strict` は全テーマの既存 warn で落ちる間、validator にテーマ絞り込みがなければ通せない。その場合は通常検証の warn 差分を保存し、**対象テーマの warn 0、全体 warn 総数を増やさない**ことを一時的な合格条件とする。

### 工程7: 視覚QA（Claude Code + 人間）

必須幅: 375 / 768 / 1024 / 1280 / 1700px。

- h1から primary までに「テーマの主問」が分かる
- 最初の3チャートだけで結論の骨格が理解できる
- 凡例、軸、単位、年度、出典が読める
- 色だけに依存せず、SVG に `role="img"` / `aria-label` がある
- 欠損時に 0 と誤表示せず empty/error state になる
- スマホでチャートやラベルが横に溢れない
- チャートの結論を周辺の文章が過剰に断定していない

## 実行単位と順序

1PR = 1テーマを原則とする。共通 renderer の変更が必要な場合は先に別PRに分ける。R2反映とデプロイはテーマごとに行わず、複数テーマをまとめてユーザー承認後に1回だけ行う。

### Wave 0: 運用基盤

- validator に `--theme <key>` または同等の絞り込みを追加し、1テーマずつ strict 化できるようにする
- proposal sheet 用のテンプレートを用意する（新規管理層ではなくレビュー書式）
- current warn のテーマ別件数を機械出力できるようにする

### Wave 1: パイロット

1. `population-dynamics`
2. `aging-society`
3. `healthcare`

理由: 自然増減・社会増減・年齢構成・医療介護の読み分けは、この仕組みの適否を検証しやすい。時系列、構成比、ピラミッド、GIS埋め込みをまたいで確認できる。

### Wave 2: 生活と経済

`living-housing` → `real-income` → `consumer-prices` → `labor-wages` → `local-economy`

### Wave 3: 交通・産業・その他

残りのテーマ。指標数の多い `occupation-salary` / `safety` / `fishery-marine` は、テンプレートと判定基準が安定した後に行う。

## パイロット: population-dynamics の調査ブリーフ

### 主問

「その地域の人口が変化しているのは、出生・死亡による自然増減なのか、転入・転出による社会増減なのか。それが年齢構成にどう現れているか」

### 現行カタログの事前仮説（未承認）

| 項目 | 予備判定 | 理由 |
|---|---|---|
| primary=`crude-birth-rate` | `change-role` 候補 | 「人口動態」全体のヘッドラインとしては、自然増減率または人口増減率の方が包括的な可能性がある |
| 出生率・死亡率 | `keep` 候補 | 自然増減の分解に必要 |
| 自然増減率・社会増減率 | `keep/promote` 候補 | 主問へ直接答える |
| 転入超過率 | `keep` 候補 | 社会増減を読者に理解しやすい形で表す |
| 年齢3区分・ピラミッド | `keep` 候補 | 人口変化の結果を構造として表す |
| 人口密度・昼夜間人口比 | `context` 候補 | 主問への距離が遠く、最初のチャート群には不要 |
| `birth-death-rate-trend` | `revise-props` 候補 | 率同士か実数同士に統一し、定義とラベルを整合させる |
| `natural-social-increase-trend` | `replace/revise` 候補 | 現在のタイトルは自然・社会増減だが、props は出生数・死亡数で社会増減を含まない。section も「移動」で不整合 |
| `theme-pop-migration-trend` | `keep` 候補 | 転入・転出の差を読むために有用。必要なら差分値の見せ方を別途検討 |
| sortOrder | `revise` | 0/10 重複があり、ストーリー順をカタログ上で表現できていない |

この予備仮説はコード読解によるもので、まだ `selection` に転記しない。次の作業は公式資料と e-Stat の実在を確認し、`docs/04_レビュー/<date>-theme-population-dynamics.md` を作ることである。

## 完了条件

各1テーマの完了は、次のすべてを満たすこと。

- primary/secondary すべてに公式根拠付き `selection`
- 不採用候補を `rejectedCandidates` に記録
- 主要チャートごとに reader question と `relatedRankingKeys`
- source、単位、年度、色、sortOrder が明示的
- 対象テーマの catalog warning 0
- 生成物とSSOTが一致
- type/test とローカル視覚QAが成功
- 本番反映は別承認、反映後に実測記録

## 禁止事項

- 出典調査なしで `selection` を埋める
- 表示を豪華にするためだけにチャートを追加する
- 同じ結論の実数・率・人口当たりをすべて primary にする
- 既存 componentType で無理に代用する
- 生成物 TS/JSON を手編集する
- データ投入、R2 push、デプロイを提案PRに混ぜる
