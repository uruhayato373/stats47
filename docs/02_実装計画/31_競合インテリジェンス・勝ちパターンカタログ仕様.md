# 競合インテリジェンス・勝ちパターンカタログ仕様

## 0. この文書の位置づけ

本仕様は、stats47に近いSNS投稿・Webサイト・検索結果を継続的に観測し、公開数値と画面上の証拠から
「何が、誰に、どの見せ方で伸びたか」を抽象化し、stats47固有の企画・画像・動画・landingへ安全に変換するための
Claude Code実装仕様である。

既存の `/x-viral-research`、`/competitor-scan`、`/buzz-map`、`/sns-gallery`、`/update-sns-metrics` を廃止しない。
本仕様はそれらの上位に横断的な検索語、競合、観測、パターン、採否、実験の共通契約を置く。

用語:

- **競合**: 同じ商品だけでなく、同じ検索意図、可処分時間、SNSフィード上の注意を奪い合う相手。
- **観測**: 公開画面または公式APIから、取得日時付きで得た事実。
- **解釈**: 観測から導いた仮説。事実と同じフィールドに混ぜない。
- **パターン**: 複数の投稿・ページに再現して現れる、題材、フック、構成、視覚、導線の組み合わせ。
- **適応**: 第三者の表現を複製せず、stats47のデータ、トークン、語り口、landingに変換すること。
- **インプレッション**: 投稿者だけが見られる非公開値を含む。第三者調査では公開view/play数等を代理指標とする。

## 1. 目的、非目的、成功条件

### 1.1 目的

1. YouTube、X、Instagram、検索結果、競合Webを同じ調査語彙で横断する。
2. 単純な総再生数ではなく、公開後日数、アカウント通常値、形式差を考慮して異常値を発見する。
3. URL、取得日時、公開数値、スクリーンショットを根拠として、勝ちパターンを再現可能な形で保存する。
4. 外部パターンをstats47の既存型、指標、データソース、landingへ接続する。
5. 制作後は自社実測で外部仮説を検証し、効かなかった型を降格できるようにする。

### 1.2 非目的

- 他者の投稿文、画像、動画、図表、サイトデザインの丸写し。
- ログイン回避、CAPTCHA回避、非公開API、規約違反の大量スクレイピング。
- 競合のPV、CVR、収益、インプレッション等の非公開値を断定すること。
- 1件のバズだけを根拠にrulesや制作テンプレートを自動変更すること。
- 調査から無審査で自動投稿すること。
- TikTokへの再参入。TikTokは検索語の参考元にも自動投稿先にも含めない。

### 1.3 成功条件

1. 検索語、競合、パターン分類、採否理由が一意IDを持つ型付きカタログになる。
2. 全観測に `source_url`、`observed_at`、`collector`、取得可否が残る。
3. 同一投稿の再観測で過去数値を上書きせず、時系列差分を計算できる。
4. YouTube、X、Instagram、Webの最低各1系統が同じgalleryから閲覧できる。
5. パターンからstats47企画へ進む際に、権利、差別化、データ、landingの4ゲートを通る。
6. 自社投稿は原則として12件かつ4週間を満たすまで観測して型別評価できる。ただしYouTube月1運用は単発勝敗を避けて逐次蓄積し、明確な安全問題は即停止する。
7. 仕様上の効果判定は `.claude/rules/evidence-based-judgment.md` を満たす。

## 2. 競合の定義と初期カタログ

競合を「都道府県統計サイト」だけに限定しない。以下の5クラスを別々に検索し、`competitorType`で区別する。

| class | 定義 | 主な観測対象 | stats47が学ぶこと |
|---|---|---|---|
| `direct` | 都道府県・市区町村の統計、ランキング、比較を主目的にする | todo-ran、uub等 | 指標網羅、情報設計、回遊 |
| `format` | 地図、グラフ、GIS、時系列動画で注意を獲得する | まちの計量舎等 | 停止力、視覚文法、尺 |
| `attention` | 治安、格差、ご当地、生活など同じ題材で感情を動かす | riskmap.jp等 | フック、コメント誘発、題材選択 |
| `search` | 同じ検索結果に出る行政、報道、調査、旅行、百科事典 | 自治体、官公庁、報道等 | 検索意図、信頼根拠、欠けた回答 |
| `amplifier` | SNS投稿を記事化・再拡散する媒体 | IT・ニュース媒体等 | 二次拡散される題材と見出し |

初期seedは既存資料で既知の以下から開始する。登録時にURL、handle、platform、確認日を再検証し、名称だけを根拠に
同一主体と決めない。

| seed | class | 初期仮説 | 必須確認 |
|---|---|---|---|
| todo-ran | direct | 都道府県ランキングの指標網羅 | 正式URL、現存、ページ数、更新日 |
| uub | direct | 自治体・都道府県データの網羅 | 正式URL、現存、URL構造 |
| まちの計量舎 / keiryosha.com | format | 日本地図×統計の表現競合 | サイトとSNSの同一性、投稿形式 |
| riskmap.jp | attention | リスク・感情系の注意競合 | 各platformの公式handle、公開指標 |
| ねとらぼ等の紹介記事 | amplifier | 地図投稿の二次拡散 | 元投稿との対応、記事公開日 |

競合は `active`、`watch`、`inactive`、`excluded` を持つ。消えた競合も削除せず、`inactive`と確認日を残す。

検索設定のSSOTは文書ではなく、型付きgit TSとする。

```text
.claude/scripts/research/data/
├── search-taxonomy.ts       # 概念軸と同義語
```

文書内の表は初期値と判断基準であり、実行時はgit TSのみを読む。生成JSONを手編集しない。

### 3.3 platform別クエリテンプレート

#### YouTube

検索APIで `q`、`type=video`、`publishedAfter`、`order=viewCount|date` を組み合わせ、候補ID取得後に
動画詳細APIで公開日、duration、viewCount、likeCount、commentCountを取得する。Shortsと通常動画を混ぜて比較しない。

```text
<axis phrase>
<axis phrase> 都道府県
<axis phrase> 市区町村
<axis phrase> shorts
```

初期セット例:

- `都道府県 ランキング shorts`
- `日本地図 データ 可視化`
- `市区町村 地図にしてみた`
- `人口 推移 都道府県`
- `鉄道網 変化 日本地図`
- `47都道府県 比較`

#### X

既存 `/x-viral-research` の軸を継承し、期間と閾値を引数化する。

```text
(<同義語 OR ...>) lang:ja -filter:replies since:<date>
(<同義語 OR ...>) min_faves:<threshold> lang:ja -filter:replies
from:<competitor_handle> since:<date>
```

総いいね閾値だけでは小規模アカウントの異常値を落とすため、`min_faves`無しのaccount定点観測も必ず併用する。

#### Instagram

公開検索で安定して取れる情報だけを使う。キーワード、ハッシュタグ、既知handle、Google/Bingのsite検索を併用する。

```text
site:instagram.com/reel/ "都道府県" "地図"
site:instagram.com/p/ "47都道府県" ランキング
site:instagram.com/reel/ "市区町村" 可視化
<既知handleのプロフィール> → 直近投稿巡回
```

ハッシュタグseed:

- `#都道府県ランキング` `#47都道府県` `#日本地図`
- `#データ可視化` `#GIS` `#地理` `#市区町村`
- `#人口減少` `#地方創生` `#ご当地` `#県民性`

ハッシュタグ件数自体を需要値とみなさない。候補発見の入口としてのみ使う。

#### Web・検索競合

```text
<topic> 都道府県 ランキング
<topic> 県別 比較
<topic> 市区町村 地図
<topic> 統計 グラフ
intitle:<topic> 都道府県
site:<competitor-domain> <topic>
<SNS投稿の固有フレーズ> -site:<SNS domain>
```

検索意図別に `know`、`compare`、`find-self`、`download-data`、`news`、`entertainment` を付与する。
検索順位は地域、端末、時点で変わるため、`rank`にはquery、取得日時、locale、device、検索手段を必須とする。

### 3.4 検索語の拡張と廃止

候補語は以下から生成する。

1. GSCのstats47実クエリ。
2. 競合タイトル・見出し・ハッシュタグの共起語。
3. 自社SNSコメントとサイト内検索語。
4. e-Stat、KSJ、GSIのデータカタログ語。
5. 季節カレンダーとニュース。ただし公開前にデータ年次を確認する。

追加条件は「既存語では拾えなかった有効候補URLが2件以上」または「GSC実クエリが確認できた」。
30日間で有効候補0件が2回続いた語は`dormant`へ移す。削除はしない。

## 4. 調査対象と取得方式

### 4.1 取得方式の優先順位

```text
公式API・公開feed
  → 通常のWeb検索
  → browser-useによる画面確認
  → 人手入力
```

モデルに決定的なHTML解析、重複排除、日時計算、スコア計算をさせない。モデルはフック、構成、視覚、差別化の
意味判断にだけ使う。

| source | 候補発見 | 数値取得 | 深掘り | 備考 |
|---|---|---|---|---|
| YouTube | Data API / Web検索 | Data API | browser-use | 最も自動化しやすい |
| X | Web/X検索 | 公開UI/APIが許す範囲 | browser-use | ログイン・UI変更に弱い |
| Instagram | Web検索/handle巡回 | 公開UIで表示される範囲 | browser-use | 半自動を既定とする |
| Web | 検索、sitemap、RSS | HTTP、構造化データ | browser-use | robots・利用条件を尊重 |

### 4.2 browser-useの役割

browser-useは次に限定する。

- 検索結果から候補URLを開き、投稿と数値が同一画面にあることを確認する。
- 冒頭3秒、画面構成、字幕、CTA、コメント傾向などAPIで取れない意味情報を観察する。
- 競合サイトのmobile表示、ファーストビュー、内部導線、広告、可視化を確認する。
- 証拠スクリーンショットを内部参照用に保存する。

終了時は `.claude/rules/browser-use-cleanup.md` のdaemon停止、Chrome終了、一時profile削除を必須とする。
認証切れ、CAPTCHA、アクセス拒否が出た場合は回避せず、`collection_status=blocked`で止める。

### 4.3 Webサイト分析項目

| layer | 観測項目 |
|---|---|
| 検索 | query、順位、title、snippet、SERP feature、競合ページ種別 |
| 情報設計 | URL階層、カテゴリ、タグ、ranking/theme/area/articleの責務 |
| ページ | H1、導入、回答までの距離、表・地図・グラフ、出典、更新日 |
| 導線 | SNS→landing、内部リンク、関連記事、CTA、検索、パンくず |
| SEO | canonical、robots、sitemap、構造化データ、metadata、indexability |
| UX | mobile first view、文字密度、操作数、表示速度の実測 |
| 収益 | 公開画面上の広告位置、affiliate導線。収益額は推定しない |
| 差別化 | stats47に有る回答、無い回答、より信頼できる一次データ |

競合サイトの全ページを保存しない。代表ページと構造の要約を保存し、ページ本文は転載しない。

## 5. データモデルとSSOT

### 5.1 保存先の原則

| データ | SSOT | 理由 |
|---|---|---|
| 検索語、競合seed、分類語彙、採用済みpattern定義 | git TS | 人手編集、型、reviewが必要 |
| 生の公開観測値・スクリーンショットmanifest | R2 `research/competitive-intelligence/` | 外部観測、高volume、追記型 |
| 最新状態・実行cursor・失敗状態 | `.claude/state/research/competitive-intelligence/` | agent用の軽量state |
| 自社SNS実績 | 既存posts.json + sns metrics snapshot | 既存SSOTを再利用 |
| 人間向け月次レビュー | `docs/04_レビュー/YYYY-MM-competitive-intelligence.md` | 意思決定・振り返り |
| gallery表示JSON | 上記SSOTから都度生成 | 派生物、手編集禁止 |
| 企画への昇格 | buzz-map curated TS / 各SNS catalog | 既存の制作SSOTを変更しない |

永続D1を追加しない。ローカル分析でSQLが必要ならDuckDBまたは`:memory:` SQLiteでR2 snapshotを読み、結果だけを
再生成可能なJSONとして出す。

### 5.2 ID体系

```text
competitorId: cmp-<canonical-slug>
accountId:    acc-<platform>-<canonical-handle>
artifactId:   art-<platform>-<native-id-or-url-hash>
observationId:obs-<artifactId>-<observedAt>
patternId:    pat-<family>-<slug>-v<n>
adaptationId: adp-<patternId>-<stats47-topic>
experimentId: exp-sns-<yyyy>-<nnn>
```

URL短縮、tracking parameter、mobile URLをcanonical化してからhashする。投稿削除後もIDは再利用しない。

### 5.3 主要型

```ts
type SourcePlatform = "youtube" | "x" | "instagram" | "web";

type Artifact = {
  id: string;
  platform: SourcePlatform;
  competitorId: string | null;
  canonicalUrl: string;
  nativeId: string | null;
  publishedAt: string | null;
  artifactType: "short" | "video" | "image" | "carousel" | "reel" |
    "thread" | "article" | "ranking" | "tool" | "landing";
  topicAxes: readonly string[];
  language: string;
};

type Observation = {
  artifactId: string;
  observedAt: string;
  collector: "official-api" | "web-search" | "browser-use" | "manual";
  metrics: {
    views?: number; plays?: number; likes?: number; comments?: number;
    reposts?: number; bookmarks?: number; followers?: number;
    searchRank?: number;
  };
  unavailable: readonly string[];
  evidence: readonly { kind: "api" | "html" | "screenshot"; uri: string }[];
  collectionStatus: "ok" | "partial" | "blocked" | "removed";
};

type PatternAssessment = {
  artifactId: string;
  hook: { family: string; textSummary: string; firstAnswerAtSec?: number };
  visual: { family: string; ratio?: string; density: string; motion?: string };
  narrative: { structure: string; payoff: string; commentPrompt?: string };
  landing: { exists: boolean; promiseMatch?: string; cta?: string };
  rights: { reuse: "structure-only" | "blocked"; notes: string };
  evidenceRefs: readonly string[];
  analystModel: string;
  confidence: "low" | "medium" | "high";
};
```

`PatternAssessment`に第三者本文の全文、画像バイナリ、動画コピーをgit commitしない。短い構造メモと証拠参照だけを持つ。

## 6. 勝ちパターン分類

### 6.1 題材パターン

- `exception`: ほぼ全部の中の唯一・少数例外。
- `self-location`: 自分の県、市、生活圏を探す。
- `boundary`: 東西、都市圏、文化圏、商圏の境界。
- `gap`: 1位と最下位、都市と地方、表と裏の差。
- `change`: 長期推移、開通、消滅、増減。
- `network`: 鉄道、道路、港、移動、流動。
- `density`: 点群、メッシュ、集中、空白。
- `paradox`: あるのに減る、無いのに増える。
- `identity`: 食、方言、地名、県民の体感。
- `utility`: 住む、旅行する、買う、働く判断。

### 6.2 フックパターン

| ID | 構造 | 適応時の注意 |
|---|---|---|
| `question` | 「全部言える？」「どこ？」 | 答えを過度に遅らせない |
| `single-exception` | 「唯一○○でない県」 | 定義と年次を明示 |
| `large-number` | 「○年分を○秒で」 | 数字を誇張しない |
| `versus` | A対B、東西、あり/なし | 二分法で連続値を歪めない |
| `counterintuitive` | 体感とデータの逆転 | 因果と相関を分ける |
| `personal` | 「あなたの県は？」 | コメント誘導だけにしない |
| `reveal` | 先に問い、後で地図全体を公開 | 結論到達秒を記録 |
| `news-bridge` | ニュースから長期統計へ | ニュース寿命とデータ年を分離 |

### 6.3 視覚パターン

既存buzz-map A〜F、flowを優先語彙とし、追加で以下を持つ。

- `rank-list`、`top3-card`、`versus-split`、`small-multiples`
- `timeline`、`bar-chart-race`、`counter-animation`
- `before-after`、`zoom-reveal`、`annotation-led`
- `photo-plus-data`、`text-only-number`、`source-led`
- 未分類は `new:<slug>`。2件以上で再現した場合だけtaxonomy追加候補にする。

### 6.4 Webパターン

- `answer-first`: 冒頭で順位・数字・地図を提示。
- `explore-first`: selectorや地図から自分で探す。
- `definition-first`: 調査定義を先に説明。
- `story-first`: 背景やニュースからデータへ接続。
- `hub-spoke`: テーマhubから多数のrankingへ回遊。
- `sns-landing-match`: SNSの問いとlandingの第一回答が一致。
- `download-tool`: CSV、計算、比較等の実用価値。

## 7. 公開実績の正規化とスコア

### 7.1 原則

総数だけで勝ちを決めない。platform、format、公開後時間、account規模が異なるものを直接比較しない。
第三者の正確なimpression、CTR、retentionは不明として扱う。

### 7.2 決定的に計算する派生値

```text
ageHours          = max(1, observedAt - publishedAt)
viewsPerDay       = views / max(1, ageHours / 24)
engagementPublic  = likes + comments + reposts
engagementRate    = engagementPublic / views          # viewsが公開時のみ
accountLift       = artifact views / 同一account・同形式・直近20件のmedian views
velocityLift      = artifact viewsPerDay / 同一bucketのmedian viewsPerDay
```

Instagram等でviewsが無い場合、likesをviewsの代用にして`engagementRate`を作らない。欠損は0ではなく`null`にする。

### 7.3 discovery score（0〜100）

| 要素 | 点 | 根拠 |
|---|---:|---|
| 同一account通常値からのlift | 25 | accountLift percentile |
| 同形式・同年齢bucketの速度 | 20 | velocityLift percentile |
| 公開engagementの深さ | 10 | comment/repost等、取得可能範囲 |
| stats47題材との適合 | 10 | taxonomy一致、モデル判断 |
| パターンの再現数 | 10 | 別主体2件以上で加点 |
| データ・権利の実現可能性 | 10 | 一次データ、商用可否 |
| landingへの接続可能性 | 10 | live/ready/blocked |
| 差別化可能性 | 5 | exact複製でない |

公開実績の母数が不足する場合は`scoreConfidence=low`とし、70点でも自動昇格しない。
exact重複、権利不明、高sensitivity、landing無しは点数にかかわらずhard gateで止める。

### 7.4 勝ち判定

- `signal`: 単一投稿で高いlift。仮説候補。
- `repeated`: 異なる主体または時期で同型が2件以上。
- `validated-external`: 3件以上かつ2主体以上、取得根拠あり。
- `validated-stats47`: stats47で同型を3件以上実施し、baseline比を満たす。
- `rejected`: 自社で再現しない、ブランド不適合、権利・安全上不可。

外部で伸びたことはstats47での効果を保証しない。`validated-external`と`validated-stats47`を統合しない。

## 8. Claude Codeエージェント分業とモデル割り当て

### 8.1 最小構成

エージェントをplatformごとに乱立させない。既存agentを中心に、収集workerと月次criticだけを追加する。

| agent | model | 責務 | write boundary |
|---|---|---|---|
| `trend-scout` | Sonnet | orchestrator、検索計画、候補統合、調査割当、週次要約 | research latest state、レビューdraft |
| `competitive-research-collector` | Haiku | 決められたquery実行、URL/公開値/証拠収集、再試行 | raw observationのみ |
| `creative-pattern-analyst` | Sonnet | 上位候補のフック、映像、ページ、差別化を構造化 | assessment candidateのみ |
| `competitive-strategy-critic` | Opus | 月次の採否、競合仮説、blind spot、pattern昇格審査 | verdict proposalのみ |
| `sns-metrics-sync` | Sonnet | stats47投稿の実測同期 | 既存SNS metrics SSOTのみ |
| `strategy-advisor` | Sonnet | 月次・週次計画へ採択実験を接続 | current plan、既存手順経由 |

| `sns-renderer` | Sonnet | 既存token/specによる派生素材生成 | Remotion spec、派生素材 |

### 8.2 モデル選択原則

- **コードで処理**: URL canonical化、API呼出、HTML selector、重複排除、集計、スコア、status遷移。
- **Haiku**: 定型収集、分類候補、欠損検査、既知taxonomyへの一次タグ付け。最終的な競合戦略を決めない。
- **Sonnet**: 視覚・文章・導線の意味分析、複数証拠の統合、stats47適応案。
- **Opus**: 毎回使わない。月次上位候補、互いに矛盾する証拠、ブランド変更、型追加、高sensitivityだけを審査。

ユーザーの「fable」が軽量モデルを意味する場合も、Claude Code上の実装名は利用可能な正式model IDへ解決し、
本仕様上の役割はHaiku相当とする。存在しないmodel名をagent frontmatterへ書かない。

### 8.3 Opusへのエスカレーション条件

以下のいずれかでのみ起動する。

1. pattern taxonomyまたはSNS rulesの変更提案。
2. exact競合と差別化案の境界が曖昧。
3. 災害、治安、医療、教育、差別等の高sensitivity。
4. 3件以上の外部証拠が互いに矛盾する。
5. 月次で制作予算を配分する上位5pattern。

Opusは収集をしない。入力は証拠参照付きの短いcandidate packetに限定する。

### 8.4 Agent Output Contract

すべてのsubagent prompt冒頭に `.claude/rules/agent-output-contract.md` 準拠のOutput Formatを置く。

Collector:

```text
OUTPUT FORMAT: JSONL only. One observed artifact per line.
Required keys: artifact_id, source_url, observed_at, metrics, unavailable, evidence, status.
Do not infer missing metrics. Use null, never 0.
```

Analyst:

```text
OUTPUT FORMAT: 1 markdown table only.
Columns: Artifact | Evidence | Hook | Visual | Narrative | Landing | Risk | Pattern Candidate | Confidence.
Every interpretation must cite an evidence ID.
```

Critic:

```text
OUTPUT FORMAT: report with exactly 4 sections.
Sections: Verdict / Supporting evidence / Counter-evidence / Required next experiment.
Verdict: promote | hold | reject | escalate-human.
```

### 8.5 並行境界

- query/platform/date shard単位でcollectorを並行化できる。
- collectorはraw observation以外を書かない。
- analystは同一artifactを同時編集しない。
- git TS catalogへのwriteはorchestratorが提案をまとめ、人間承認後に1プロセスで行う。
- `docs/04_レビュー`月次レポートへのwriteはtrend-scoutだけ。
- browser-useはprofileを共有して並行起動しない。1セッションずつ実行しcleanupを確認する。

## 9. 実行ワークフロー

### 9.1 日次またはオンデマンド discovery

1. query catalogからplatform、axis、期間を決定。
2. API/Web検索で候補URLを広く取得。
3. canonical URLでdedup。
4. 既存artifactなら観測値をappend、新規ならartifactを作成。
5. 決定的スコアで上位候補だけを深掘りqueueへ送る。

日次はbrowser-useを必須にしない。API障害やUI変更を「トレンド無し」と誤認しないよう、coverageを別に記録する。

### 9.2 週次 deep review

1. 上位20〜30件をbrowser-useで確認。
2. 動画は冒頭3秒、10秒、結論、終了CTAを記録。
3. Webはmobile first view、回答までの距離、内部導線を記録。
4. creative-pattern-analystが既知taxonomyへ分類。
5. 新型、反証、データ不足を別queueに分ける。
6. stats47のmetric registry、buzz-map catalog、既存landingと突合する。

### 9.3 月次 synthesis

1. competitor account差分。
2. platform別の外部repeated pattern。
3. stats47自社実測との一致・不一致。
4. 検索競合の新規ページ、更新、SERP変化。
5. 上位5patternをOpus criticへ渡す。
6. `promote/hold/reject`を人間向けレビューに出す。
7. 承認されたものだけを制作カタログまたは改善バックログへ移す。

### 9.4 障害時

```text
API quota/失敗 → retry budget内で決定的再試行 → Web検索へdegrade
ログイン切れ/CAPTCHA → blocked、手動確認queue
selector変更 → collector failure、0件成功として扱わない
投稿削除 → removed観測をappend、過去証拠は保持
数値非表示 → null + unavailable reason
```

同一障害を無限再試行しない。credentialやログイン情報をログ・スクリーンショット・agent outputへ出さない。

## 11. 権利、倫理、ブランドガード

### 11.1 保存できるもの

- 公開URL、handle、公開日時、公開数値、取得日時。
- 内部研究用スクリーンショットと構造メモ。
- 自分の言葉で抽象化したフック・構成・視覚の分類。
- 公開された事実と一次データへの参照。

### 11.2 制作へ流用しないもの

- 第三者の画像、動画、イラスト、地図、音源、ナレーション。

- 利用許諾が不明なデータや地理素材。

### 11.3 適応ゲート

1. **rights**: 一次データと商用条件を確認したか。
2. **differentiation**: stats47固有の問い、データ、比較、landingのいずれか2つ以上があるか。
3. **truth**: 年次、単位、母集団、欠損、因果表現を説明できるか。
4. **brand**: 信頼性×網羅性を損なう煽り、恐怖、地域蔑視になっていないか。
5. **landing**: SNSの約束に直接答えるlive/readyページがあるか。

## 12. stats47への変換契約

外部artifactから直接SNS specを作らない。必ず`Pattern → Adaptation → Experiment`を通す。

```text
External artifacts N件
  → Pattern candidate
  → external validation
  → stats47 adaptation
  → data/license/landing gates
  → platform draft
  → human approval
  → post
  → own metrics
  → validated-stats47 / reject
```

`Adaptation`必須項目:

- `patternId`
- stats47で答える具体的な問い
- 使用するmetric/KSJ/GSI/MLITデータと年次
- 既存buzz-map型または新型提案
- X/IG/YouTube別の変更点
- landing URLとpromise match
- 外部例との差分3点
- sensitivityとrights判定
- baseline、primary metric、検証日

制作カタログ反映先:

| adaptation | 反映先 |
|---|---|
| 地図・GIS | buzz-map curated ideas / combo catalog |
| X caption/画像 | `sns-content-standards.md`の承認ゲート |
| IG carousel/reel | Instagram strategistの既存schedule/draft |
| YouTube | 月1ガード付きexperiment、既存YouTube実験ログ |
| Web landing | ranking/blog/themeの既存SSOTとpublisher |

## 13. 継続計測と改善

### 13.1 外部観測KPI

- `query_coverage`: 計画queryのうち正常取得できた割合。
- `candidate_precision`: 深掘り候補のうち有効artifactだった割合。
- `new_pattern_rate`: 新規candidate pattern / 深掘り件数。
- `repeat_evidence_rate`: 2主体以上で再現したpattern割合。
- `observation_freshness`: 最新正常観測からの日数。
- `blocked_rate`: 認証、selector、quota等で失敗した割合。

外部投稿の総view合計をチームKPIにしない。大規模accountの1件で歪むためである。

### 13.2 自社検証KPI

platformごとにprimaryを分ける。

| platform | primary | secondary | guardrail |
|---|---|---|---|
| X | account baseline比のimpression/view lift | engagement、profile/landing click | hide/report、誤読 |
| Instagram | reach/play baseline比 | saves、shares、profile action | unfollow、低品質comment |
| YouTube | qualified views、視聴維持 | CTR、平均視聴時間、subscriber | 月1、重複、pause event |
| Web | landing session、SNS UTM CTA | engaged session、回遊 | promise mismatch、直帰 |

取得できない指標は代替値で偽装しない。例えばIG profile経由を投稿別CTRとして断定しない。

### 13.3 実験設計

- 1実験で主に変える軸は1つ。題材、フック、visual、尺、CTAを同時に全変更しない。
- 同platform・同format・近いaccount状態のbaselineを使う。
- 最低3投稿/variantを目標とし、YouTube月1では単発勝敗を決めず逐次蓄積する。
- 事前にprimary metric、baseline window、判定日、停止条件を書く。
- 外部成功を根拠に期待値を置く場合も、stats47内baselineとは別に表示する。

### 13.4 status machine

```text
observed
  → candidate
  → repeated
  → validated-external
  → adaptation-proposed
  → approved
  → experiment-running
  → validated-stats47 | inconclusive | rejected
```

分岐:

- `needs-more-evidence`
- `needs-rights-review`
- `needs-data`
- `needs-landing`
- `needs-renderer`
- `blocked-collection`
- `rejected-exact-overlap`
- `rejected-brand`

statusを後段から自動で巻き戻さない。再評価は新versionのpatternまたはexperimentとして残す。

### 13.5 月次レビュー出力

`docs/04_レビュー/YYYY-MM-competitive-intelligence.md`:

1. coverageと障害。
2. 新規・上昇・下降競合。
3. repeated/validated-external pattern。
4. stats47実験の結果と反証。
5. promote/hold/reject。
6. 次月の検索語追加・dormant。
7. 改善バックログへ移す項目。

効果判定は想定、実測、経過日数、取得コマンド、判定期日を含む。未実測を`effect`にしない。
